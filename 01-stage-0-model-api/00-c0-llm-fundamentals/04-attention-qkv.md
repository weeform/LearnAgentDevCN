# C0-4 · 注意力与 Q / K / V
> 这是 C0 的核心篇，也是读懂 C2 的最后一关。如果只能读一篇，读这篇。

## 1. 先说清楚注意力要解决什么问题

看这两个句子：

```
A: 我 吃 苹果
B: 苹果 发布 新 手机
```

两个"苹果"的初始向量是**完全相同的**（同一个 token id，查同一张表）。但显然它们的含义不同：一个是水果，一个是公司。

所以模型必须做到一件事：

> **让同一个 token 的表示，根据它的上下文发生变化。**

这就是注意力的全部目的：**让每个 token 去"参考"周围的 token，把相关的信息揉进自己的向量里**。

处理完之后，"苹果"在 A 里的向量应该靠近水果，在 B 里的向量应该靠近公司。

## 2. 三个角色：Q / K / V

注意力为了实现"参考别人"，给每个 token 配备了三个向量。这三个向量都是**由该 token 自己的输入向量，分别乘三个不同的可学习矩阵**得到的：

```python
q_i = x_i @ W_Q      # Query
k_i = x_i @ W_K      # Key
v_i = x_i @ W_V      # Value
```

三个角色用一句话区分：

| 角色 | 含义 | 一句话 |
|---|---|---|
| **Q（Query，查询）** | 这个 token「想找什么」 | 我关心什么样的信息 |
| **K（Key，键）** | 这个 token「能被怎样匹配」 | 我是什么，拿这个来检索我 |
| **V（Value，值）** | 这个 token「携带的信息」 | 匹配上了，我把这个内容给你 |

> **程序员类比：这就是一次"可微分的数据库查询"。**  
> Q 是你的查询条件，K 是每条记录的索引键，V 是记录体。  
> 差别在于：数据库查询返回命中的那几条，而注意力**返回所有记录的加权混合**——谁跟 Q 越像，谁的 V 占的权重越大。

**为什么 V 要单独存在，不直接用 token 自己的向量？**  
因为"用来被匹配的特征"（K）和"匹配上了要交出去的内容"（V）是两回事。分开之后，模型可以学出"按语法角色去检索，但交出语义内容"这种复杂度。

## 3. 计算过程：四步

对第 i 个 token，算出它更新后的表示：

```
① 打分：用 q_i 和每个 k_j 做点积，得到"我该关注 j 多少"
   score_ij = q_i · k_j

② 缩放：除以 sqrt(d)，防止点积数值过大把 softmax 压成极端分布
   score_ij = score_ij / sqrt(d)

③ 归一化：softmax 变成权重（加起来 = 1）
   w_ij = softmax(score_i)

④ 加权求和：用权重把所有 v_j 混起来
   output_i = Σ_j  w_ij · v_j
```

`output_i` 就是 token i 在这一层更新后的新表示。

> 点积为什么能表示"相似度"？两个向量方向越接近，点积越大。这是最基础的高中数学，不需要更多解释。

## 4. 手算一遍（数字是真的，可以自己验）

为了让上面的公式不再是符号，我们用一个极简例子算一遍。

假设序列是 `[我, 吃, 苹果]`，我们正在算"苹果"这个位置。为简化，向量维度取 2（真实模型是几千维，但原理完全一样，而且我们跳过 ② 的缩放以免数字太难看）。

**每个 token 投影出的 Q / K / V：**

```
        Q          K          V
我     [?, ?]     [0, 1]     [0, 1]
吃     [?, ?]     [1, 1]     [2, 0]
苹果   [1, 0]     [1, 0]     [1, 3]
```

（"我"和"吃"的 Q 用不到，因为我们现在只算"苹果"的注意力。）

**① 打分：**用 `q_苹果 = [1, 0]` 去和所有的 K 做点积

```
score(苹果, 我)   = [1,0] · [0,1] = 1×0 + 0×1 = 0
score(苹果, 吃)   = [1,0] · [1,1] = 1×1 + 0×1 = 1
score(苹果, 苹果) = [1,0] · [1,0] = 1×1 + 0×0 = 1
```

**③ softmax：**`[e⁰, e¹, e¹] / (e⁰ + e¹ + e¹) = [1, 2.72, 2.72] / 6.44`

```
w = [0.155, 0.422, 0.422]
```

**④ 加权求和：**

```
output_苹果 = 0.155 × [0,1]  +  0.422 × [2,0]  +  0.422 × [1,3]
            = [0, 0.155]     +  [0.844, 0]     +  [0.422, 1.266]
            = [1.266, 1.421]
```

**结果**：`[1, 3]`（苹果自己的原始 V）被更新成了 `[1.27, 1.42]`——它现在混入了"吃"这个词的信息。

**这就是"上下文相关表示"的诞生过程。**如果句子是"苹果发布新手机"，K、V 相同但参与加权的邻居不同，得到的 output 就完全不同——于是同一个"苹果"有了不同的含义。

## 5. 一个对 C2 至关重要的观察

回头看上面那张 Q/K/V 的表，注意一件事：

> **`k_j` 和 `v_j` 只由 token j 自己决定**，跟当前在算哪个位置毫无关系。

j = "吃" 的 `k` 永远是 `[1,1]`，`v` 永远是 `[2,0]`——不管现在是"苹果"在查询，还是后面某个新 token 在查询。

而 `q_i` 不同：它是**查询方**才有的，用完这一次查询就不再需要了。

把这个观察记牢，它就是 C2-2 那个核心结论的全部来源：

> **K 和 V 是"跨步骤复用"的（所以能缓存），Q 是"一次性"的（所以不缓存）。**

## 6. 多头注意力（Multi-Head Attention）

真实模型不会只做一次上面那套计算，而是**并行做很多次**，每次用不同的 `W_Q / W_K / W_V`。每一次叫一个"头（head）"。

为什么要多个头？因为**"相关"有很多种**：

- 一个头可能专门关注**语法关系**（主谓、指代）
- 一个头可能专门关注**相邻词**
- 一个头可能专门关注**同义词/重复出现的实体**

单头的话，一次加权平均会把这些不同维度的相关性糊在一起；多头让模型在不同子空间里各自检索，最后拼接起来。

> 类比：一次 SQL 查询 vs 同时跑多条不同 WHERE 条件的查询，最后把结果拼起来。

头的数量是模型的一个固定参数（比如 32 个头）。**C2-3 算显存时会用到这个数**——因为 K/V 是"每个头各一份"。

## 7. 因果掩码：为什么必须遮住未来

生成时有个约束：**预测第 i 个 token 时，不能让它看到 i 以后的 token**。否则模型在训练时会"偷看答案"，学到的东西在真实生成场景完全用不上。

做法简单粗暴：把 `j > i` 的所有 score 置成 `-inf`，softmax 之后这些位置的权重就变成 0。

```
         j=1   j=2   j=3   j=4
i=1    [  ✓     ✗     ✗     ✗  ]      只看自己
i=2    [  ✓     ✓     ✗     ✗  ]
i=3    [  ✓     ✓     ✓     ✗  ]
i=4    [  ✓     ✓     ✓     ✓  ]
```

这个掩码是**因果关系（causal）**的体现，也是 C2-2 里"为什么 K/V 不会变"的根源：正因为第 j 个 token 永远看不到未来，它的表示才不会随生成过程改变。

## 8. 代价：O(N²)

注意打分的规模：**每个 token 要和所有 token 打分，所以是 N × N 个分数**。

| 序列长度 | 注意力分数个数 |
|---|---|
| 1,000 | 100 万 |
| 10,000 | 1 亿 |
| 100,000 | 100 亿 |

这就是长上下文昂贵的根本原因：

- **计算量**随长度平方增长。
- **注意力矩阵本身**也要占显存（不过实际实现中通过 KV Cache 分块计算规避了 N×N 矩阵的显式存储，这是工程细节）。

这也直接解释了：为什么"输入 100K token"比"输入 1K token"贵得多，而且不是 100 倍的关系。C3-3 讲成本模型时会回到这一点。

## 9. 这一篇要带走的结论

1. 注意力的目的是**让同一个 token 的表示随上下文变化**。
2. Q = 我要找什么，K = 我怎么被检索，V = 匹配上了我给出什么。本质是一次可微分的加权查询。
3. 计算四步：点积打分 → 缩放 → softmax → 加权求和 V。
4. **K 和 V 只由该 token 自己决定，Q 是查询方一次性的**——这是 KV Cache 的全部依据。
5. 多头 = 多个子空间并行检索；因果掩码 = 遮住未来；复杂度 O(N²) = 长上下文昂贵的根源。
