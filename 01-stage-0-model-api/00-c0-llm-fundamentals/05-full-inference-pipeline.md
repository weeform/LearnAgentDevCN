# C0-5 · 一次推理的完整流程
## 1. 把前四篇拼起来

现在把 C0-1 到 C0-4 串成一次完整的推理。假设你发了一句 `"今天天气"` 给模型，让它续写。

```
① 分词
   "今天天气" → [38102, 5521]                    （C0-2）

② 查 embedding + 加位置编码
   得到 2 × d 的矩阵                              （C0-2）

③ 过 L 层 Transformer，每层做：                    （C0-3）
     - 每个 token 投影出 Q / K / V                 （C0-4）
     - 每个 token 用 Q 去和前面所有 K 打分
     - softmax 加权求和所有 V → 更新该行
     - 再过 FFN 逐行加工
     - 残差 + LayerNorm

④ 取最后一层、最后一个位置的向量                    （C0-3）

⑤ 乘词表矩阵 → logits（长度 = 词表大小）             （C0-2）

⑥ softmax → 概率分布 → 采样出下一个 token            （C1-2 的主场）

⑦ 把新 token 拼回序列，回到 ③
```

**这是你读 C1 和 C2 时脑子里应该有的那张图。**

## 2. 一个关键的转折：输入和输出的处理方式完全不同

第 ③ 步里藏着一个极其重要的不对称性，它决定了整个推理系统的架构：

**输入部分**：`今天` 和 `天气` 两个 token 是**同时**进来的，可以一次性并行算完。

**输出部分**：下一个 token 还没生成出来，没法并行——必须等第 1 个 token 生成完，才能算第 2 个。

于是推理被天然切成两个阶段：

| 阶段 | 处理对象 | 一次处理多少 | 能否并行 |
|---|---|---|---|
| **prefill（预填充）** | 你输入的 prompt | 全部 token，一次性 | 完全并行 |
| **decode（解码）** | 模型的输出 | 每次 1 个 token | 严格串行 |

这个不对称带来一系列你能直接感受到的现象：

- **首 token 延迟（TTFT）**主要由 prefill 决定——输入越长，等得越久。
- **生成速度**（每秒多少 token）由 decode 决定——它是一步一步来的。
- **为什么"输入便宜、输出贵"**：prefill 一次并行算完所有 token，利用率高；decode 每步为了生成 1 个 token，要把整个模型和历史 K/V 读一遍，利用率低。C3-3 讲价格时会回到这点。

## 3. prefill 阶段：不只是"算一遍"

prefill 干的事，比"把输入过一遍网络"要多一件：

它**顺带把每个 token、每一层、每个注意力头的 K 和 V 全部算了出来，并写进缓存**。

```
prefill 结束时，缓存里已经有：
  - 第 1 层：K/V of [今天], [天气]        （每个头一份）
  - 第 2 层：K/V of [今天], [天气]
  - ...
  - 第 L 层：K/V of [今天], [天气]
```

同时，prefill 还顺手算出了**第一个输出 token**（用最后一层的最后一个位置）。

这就是 prefill 的全部产出：**一份完整的 K/V 缓存 + 第一个输出 token**。

## 4. decode 阶段：每步的"算"与"读"

进入 decode，每一步只做三件事：

```
第 t 步（生成第 t 个输出 token）：

  算：只算「上一步刚生成的那个 token」的这一份
      - 过 L 层，每层算出它的 q、k、v
  读：把缓存里所有历史 token 的 K / V 读出来
      - 用它自己的 q 去和全部 K 打分，加权全部 V
  写：把它自己的 k、v 追加进缓存，供下一步使用
```

用一张表看清楚，生成第 5 个 token 时，工作量是多少：

| 操作 | 涉及多少个 token |
|---|---|
| **新算**Q / K / V | **1 个**（刚生成的那个） |
| **读取**历史 K / V | 全部（输入 + 已生成的） |
| **重算**历史 K / V | **0 个**（直接从缓存读） |

最后一行是关键。**如果没有缓存，那一行就会变成"全部重算"**——每生成一个 token，都要把前面所有 token 重新过一遍 L 层网络。

## 5. 这也解释了为什么缓存必须是"精确的"

decode 每步读的是缓存里的 K/V。而 K/V 是由 token 内容决定的——**所以只要输入前缀里任何一个 token 变了，那个位置及其之后所有 token 的 K/V 全都得重算**。

这就是 C2-2 那两条铁律的来源：

1. 前缀必须逐 token 精确匹配，缓存才能复用。
2. 稳定内容（system prompt、工具定义）放前面，可变内容（用户问题、本轮结果）放后面。

现在这两条对你来说应该不再是"要背的规则"，而是**机制的自然推论**。

## 6. 这一篇要带走的结论

1. 一次推理 = 分词 → embedding → L 层 Transformer → 取最后一行 → logits → 采样 → 拼回循环。
2. 推理天然分成**prefill（输入，并行）**和**decode（输出，串行）**两个阶段，这解释了 TTFT 和生成速度的区别。
3. prefill 的产出是**完整的 K/V 缓存 + 第一个输出 token**。
4. decode 每步只**新算 1 个 token**，其余全是**读缓存**。
5. 缓存命中的前提是前缀精确匹配——这是机制决定的，不是厂商的规矩。

## 7. 接下来

到这里，你已经具备了读 C2 的全部前置知识。

**C2 讲的就是这份缓存本身**：它占多少显存（C2-3）、工业界怎么把它压小（C2-4）、各家厂商怎么把它包装成"上下文缓存"卖给你、以及 Agent 该怎么利用它省钱（C2-5）。

如果暂时不读 C2，也可以直接去 C1（调用参数）——C0-1、C0-2 已经给了你足够的基础。推荐顺序是：

```
C0 → C1（参数）→ C3（成本）→ C4（流式/结构化）→ C5（稳定性）→ C2（原理深化）
```
