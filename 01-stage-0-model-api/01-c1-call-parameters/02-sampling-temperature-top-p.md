# C1-2 · 采样参数：temperature 与 top_p 的原理
## 1. 起点：logits 是什么

模型前向推理结束后，在最后一个位置输出一个长度等于词表大小（通常 5 万-20 万）的向量，叫**logits**。每一维是一个实数，代表模型认为「下一个 token 是这个」的**未归一化打分**。

假设词表只有 5 个 token，logits = [2.0, 1.0, 0.5, -1.0, 0.1]。

要把它变成概率，需要 softmax：

```
softmax(z_i) = exp(z_i) / Σ exp(z_j)
```

算出来大概是：

| token | logit | 概率 |
|---|---|---|
| A | 2.0 | 0.55 |
| B | 1.0 | 0.20 |
| C | 0.5 | 0.12 |
| D | -1.0 | 0.03 |
| E | 0.1 | 0.08 |

然后从这个分布里**抽**一个 token。注意是「抽」，不是「取最大」。这正是同一个 prompt 每次结果可能不同的根本原因。

## 2. temperature：在 softmax 之前除以 T

```
p_i = exp(z_i / T) / Σ exp(z_j / T)
```

- **T = 1**：原式，不变。
- **T \< 1**：logits 之间的差值被放大。原本 2.0 和 1.0 差 1，除以 0.5 后变成 4.0 和 2.0，差 2。指数放大后高概率 token 的概率更高，分布更陡 → 更确定、更保守。
- **T → 0**：分布退化成 one-hot，等价于**贪心解码**（每次取概率最大的 token）。多数实现里 `temperature=0` 就是贪心，但仍然**不保证 100% 可复现**，因为浮点并行归约的顺序可能变化。
- **T > 1**：差值被压缩，分布变平，小概率 token 也有机会被抽中 → 更有创意，也更容易胡说。

用上面的例子：T=0.5 时 A 的概率从 0.55 升到约 0.76；T=2.0 时降到约 0.37。

**Agent 视角**：你要的是稳定、可复现、格式正确的输出，不是创意。所以 Agent 主循环里 `temperature=0` 或 `0.1-0.2` 是常态。只有「生成文案 / 头脑风暴 / 生成多个候选」这类子任务才调高。

## 3. top_p（核采样）：先砍掉长尾，再采样

temperature 是「整体缩放」，top_p 是「截断」。

做法：

1. 把候选 token 按概率从高到低排序。
2. 从高往低累加概率。
3. 一旦累加值超过 p 就停。
4. **只在这一批 token 内**重新归一化并采样，其余 token 概率直接置 0。

`top_p=0.1` 就是「只考虑累计概率占前 10% 的那批 token」。

它的好处是**自适应**：

- 模型很确定时（某个 token 概率 0.95），候选集可能只有 1-2 个，等价于贪心。
- 模型很不确定时（概率均匀分散），候选集会包含几十个，保留多样性。

这是它比固定 k 的 `top_k` 更聪明的地方。

**常见误区**：以为 top_p 越小越确定。其实 top_p 只在模型本身不确定时才起作用；模型已经确定的情况下，top_p 从 1.0 调到 0.1 可能毫无变化。

## 4. top_k：固定保留 k 个

按概率排序，只保留前 k 个，其余置 0。简单粗暴，但 k 固定，无法自适应。

- OpenAI 官方 Chat Completions API**不支持**top_k（传入会被忽略）。
- Anthropic Claude、vLLM、部分国产模型支持。
- 部分网关（如 OpenRouter）会接受并转发给支持的后端。

## 5. 三者同时存在时的顺序

典型实现（以 vLLM 等推理框架为例）：

```
logits → top_k 截断 → top_p 截断 → temperature 缩放 → softmax → 采样
```

OpenAI 官方建议：**temperature 和 top_p 只调一个**。两个都调，效果难以预测，也不好复现。

## 6. seed：尽力而为的确定性

设了 `seed` 后，服务端会「尽最大努力」让相同 seed + 相同参数 + 相同输入得到相同输出。但：

- **不保证**。模型版本更新、批处理批次变化、后端硬件变化都可能让结果漂移。
- 响应里的 `system_fingerprint` 字段标识后端配置，它变了说明结果可能变。
- 真正需要严格可复现，只能在 temperature=0 的基础上做，并且接受偶发差异。

**Agent 视角**：调试阶段设 seed 有助于对比「改了 prompt 之后效果有没有变化」；生产环境不要依赖 seed 做正确性保证。

## 7. frequency_penalty 与 presence_penalty

两者都是**在采样前修改 logits**：

- `frequency_penalty`：惩罚力度 ∝ token**出现次数**。出现越多，压得越狠。作用是减少逐字重复。
- `presence_penalty`：只要**出现过**，就给一个固定惩罚，不累加次数。作用是鼓励换新话题。

范围都是 [-2.0, 2.0]，负值会反过来鼓励重复。

**Agent 视角**：基本不用。原因——

1. 它会污染工具调用参数的生成（比如让模型不敢输出合法的重复字符）。
2. Agent 的重复问题应该靠 prompt 和上下文管理解决，而不是靠惩罚项掩盖。
3. 它让结果更难复现。

## 8. 一张决策表

| 场景 | temperature | top_p | 说明 |
|---|---|---|---|
| Agent 主循环 / 工具调用 | 0 | 1（默认，不动） | 要稳定 |
| 分类、抽取、结构化输出 | 0 | 1 | 要一致 |
| 代码生成 | 0 - 0.2 | 1 | 低容错 |
| 常规问答 | 0.3 - 0.7 | 0.9 | 平衡 |
| 文案、起名、头脑风暴 | 0.8 - 1.2 | 0.95 | 要多样性 |
| 需要多个候选方案 | 0.8 - 1.0 | 0.95 | 配合 n>1 或多次调用 |
