# C2-3 · 模型内部流程：prefill 与 decode
> 这一篇回答「一次请求，模型内部到底在干什么」。理解这两个阶段，你就理解了所有性能指标（TTFT、TPOT、吞吐）和成本曲线的来源。

## 1. 一次推理 = 两个阶段

任何一次 LLM 推理，都被拆成两个性质完全不同的阶段：

|  | prefill（预填充 / 提示处理） | decode（解码 / 逐 token 生成） |
|---|---|---|
| 处理什么 | 整段输入（prompt） | 每次 1 个新 token |
| 并行度 | **全部输入 token 并行** | **严格串行**（下一个依赖上一个） |
| KV Cache | 一次性写入全部输入的 K/V | 每步追加 1 个 token 的 K/V |
| 瓶颈 | 算力（compute-bound） | 显存带宽（memory-bound） |
| 决定指标 | TTFT（首 token 延迟） | 生成速度（TPOT，每个 token 的延迟） |

## 2. prefill：一次性把输入「读」完

用户把 prompt 发来后，模型**一次性**把整段输入的每个 token 都算好 K、V，存进 KV Cache，并在最后一个位置输出「下一个 token」的 logits，采样出第一个生成 token。

- 因为所有输入 token 事先已知，这一步是**高度并行**的，主要烧 GPU 算力。
- 输入越长，prefill 越久 →**TTFT（Time To First Token）越大**。这是用户「发了消息半天没动静」的原因。
- prefill 和输入长度大致呈**线性甚至超线性**关系（注意力本身对序列长度是平方复杂度，长输入尤其明显）。

## 3. decode：逐 token「挤牙膏」

拿到第一个 token 后，进入 decode：每生成一个 token，只做三件事——

1. 算这个新 token 的 Q、K、V。
2. 用新 Q 对**缓存的全部 K**打分（读缓存）。
3. 加权求和全部 V，得到下一个 token 的 logits，采样。

然后循环，直到碰到停止条件。

关键：decode 的每一步，**新计算量很小（1 个 token），但要从显存里把整个 KV Cache 读一遍**。当序列很长时，「读 KV Cache」的时间远超「算 1 个 token」的时间，于是瓶颈从算力变成**显存带宽（HBM 带宽）**。这是为什么 decode 阶段 GPU 利用率反而低、但延迟降不下来。

## 4. 显存账本：KV Cache 到底吃多少

每个 token 的 KV Cache 大小，可以精确算：

```
每 token 的 KV 大小 = 2 × 层数 L × KV 头数 H_kv × 每头维度 d × 每个数的字节数
```

- 前面的 `2` 代表 K 和 V 各一份。
- 字节数取决于精度：FP16/BF16 = 2 字节，FP8 = 1 字节。

**经典例子：Llama-2 7B**（L=32 层，H=32 头，d=128 维，FP16）：

```
每 token = 2 × 32 × 32 × 128 × 2 = 524,288 字节 ≈ 0.5 MB
```

于是：

| 上下文长度 | KV Cache 显存 |
|---|---|
| 1,024 token | ≈ 0.5 GB |
| 2,048 token | ≈ 1 GB |
| 8,192 token | ≈ 4 GB |
| 100,000 token | ≈ 50 GB |

注意这还只是**一个请求**的 KV Cache。加上模型权重本身、以及同时并发服务的几十上百个请求，显存很快就被吃光。

这就是为什么：

- 长上下文模型要配超大显存，或靠量化/压缩（见 C2-4）。
- 并发服务的成本里，KV Cache 是隐形大头。
- 「上下文窗口」不是随便设的，是显存和带宽的物理约束。

## 5. 为什么长上下文「又贵又慢」

把上面串起来：

1. **贵**：KV Cache 随长度线性涨显存，长上下文直接拉高单请求资源占用。
2. **慢**：prefill 阶段注意力平方复杂度，输入越长首 token 越慢；decode 阶段每步都要读完整段 KV，带宽压力大。
3. **缓存打折省的就是这个**：如果前缀不变，这段 KV 不用重新 prefill（省算力）、不用重新占一份新的（省显存），只要「读」——于是厂商才愿意给到 50%-90% 的缓存折扣。

## 6. 两个阶段如何体现在你看到的指标里

- **TTFT（首 token 延迟）**：主要被 prefill 决定。长 prompt 命中缓存时，prefill 被跳过，TTFT 大幅下降——DeepSeek 官方实测 128K 输入、大部分重复的请求，首 token 从 13 秒降到 500 毫秒。
- **TPOT / 生成速度**：主要被 decode 决定。它随「已生成 + 输入的总长度」缓慢变慢，因为每步要读的 KV 越来越多。
- **吞吐（并发处理能力）**：被「KV Cache 显存总量」卡死。显存装得下的并发请求数有限。
