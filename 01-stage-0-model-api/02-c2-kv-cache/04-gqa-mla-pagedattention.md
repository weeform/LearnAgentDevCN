# C2-4 · 压缩与优化：GQA / MLA / PagedAttention / 量化
> 这一篇把「KV Cache 太吃显存」这个问题的工业级解法过一遍。你不需要实现它们，但要知道它们各自解决什么问题——因为其中几个直接决定了厂商的缓存产品形态。

## 1. GQA / MQA：减少 KV 的头数

回想 C2-3 的公式，KV 大小正比于 `KV 头数 H_kv`。

- **标准多头注意力（MHA）**：每个 Q 头都配一个独立的 K/V 头。KV 头数 = Q 头数，缓存最大。
- **多查询注意力（MQA）**：所有 Q 头**共享同一个**K/V 头。KV 头数 = 1，缓存最小，但质量略有损失。
- **分组查询注意力（GQA）**：折中——把 Q 头分成若干组，每组共享一个 K/V 头。比如 32 个 Q 头分成 8 组，KV 头数 = 8，缓存缩到 1/4。

Llama-2 70B、Llama-3 等都用了 GQA。这是「在几乎不损质量的前提下，把 KV Cache 缩水数倍」的第一板斧。

## 2. MLA：DeepSeek 的低秩压缩

DeepSeek-V2 提出的**MLA（Multi-head Latent Attention，多头潜在注意力）更进一步：把 K 和 V 压缩到一个低秩的潜在向量**里缓存，推理时再「解压」出来用。

效果：KV Cache 大幅缩小。这带来两个重要后果——

1. DeepSeek 能以极低成本跑超长上下文。
2. **KV Cache 小到可以放进磁盘**，于是 DeepSeek 才能做「上下文硬盘缓存」（见 C2-5），把缓存从显存扩展到分布式硬盘阵列，进一步压低价格。

一句话：**模型架构设计，直接决定了厂商能不能、以及以多低的成本做缓存产品。**

## 3. PagedAttention（vLLM）：像操作系统一样管显存

传统做法给每个请求**预分配一段连续显存**放 KV Cache。问题：

- 请求长度不同，预分配会浪费大量显存（碎片）。
- 并发请求一多，显存很快被碎片吃光。

vLLM 的**PagedAttention**借用了操作系统「分页 + 虚拟内存」的思想：把 KV Cache 切成固定大小的「页」，按需分配、不连续存放、按页索引。

收益：

- 显存利用率大幅提升，同样显存能服务更多并发。
- 为「共享前缀」的复用铺路——如果两个请求前缀相同，可以**共享同一批物理页**，这正是 prefix caching 的底层支撑之一。

## 4. KV 量化：FP16 → FP8 / INT8

KV Cache 存的是浮点数。把 2 字节（FP16）压到 1 字节（FP8/INT8），显存直接减半，代价是轻微的精度损失。

现代推理框架基本都支持 KV 量化，是「显存不够又想跑长上下文」时的标准解法。

## 5. 滑动窗口注意力（Sliding Window）

Mistral 等模型引入滑动窗口：每个 token 只关注**最近 W 个 token**，更远的直接不计算、不缓存。

- KV Cache 被硬性限制在窗口大小 W 内，显存与长度解耦。
- 代价是「看不了窗口外的历史」——对需要全局依赖的任务有损，所以不是所有模型都用。

## 6. 前缀缓存（Prefix Caching）：和你最相关的一个

前面几个是「把单请求的 KV Cache 做小」，**前缀缓存**是「让多个请求 / 多轮对话共享同一段 KV」。

原理直接来自 C2-2 的铁律一：如果两次请求的**前缀完全相同**，那这段前缀的 K/V 完全一样，可以直接复用，不用重新 prefill。

- 单请求内部：KV Cache 一直在用。
- 跨请求 / 跨轮次：把「共享前缀」的 KV 存下来，下一次命中就跳过计算、按折扣计费。

**这就是各家「prompt caching / context caching」产品的底层机制。**厂商做的事情，本质上是「识别出你请求里的稳定前缀，把它的 KV 存起来，下次复用，并把省下来的算力/显存成本折算成折扣给你」。

## 7. 一张总览表

| 优化 | 解决什么 | 效果 |
|---|---|---|
| MQA / GQA | KV 头数太多 | 缓存缩至 1/2 ~ 1/8 |
| MLA | KV 维度冗余 | 低秩压缩，可落盘 |
| PagedAttention | 显存碎片 | 利用率提升、并发增加 |
| KV 量化 | 精度过剩 | 显存减半 |
| 滑动窗口 | 长上下文显存爆炸 | 显存与长度解耦 |
| 前缀缓存 | 跨请求重复计算 | 跳 prefill、折扣计费 |
