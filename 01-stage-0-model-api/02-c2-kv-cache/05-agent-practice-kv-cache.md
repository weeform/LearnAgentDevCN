# C2-5 · Agent 实战：如何利用 KV Cache
> 前四篇讲清了「KV Cache 是什么、为什么能复用」。这一篇把它落地成 Agent 开发者可执行的手段。

## 1. 先统一概念：KV Cache vs Prompt Caching

- **KV Cache**：单次请求内部，逐 token 生成时复用 K/V 的机制，所有推理都在用，你无法关闭。
- **Prompt / Context Caching（前缀缓存）**：厂商把「跨请求的共享前缀 KV」存起来复用的**产品化能力**，通常自动开启或用一个参数控制，你**能通过工程手段提高命中率**。

Agent 开发者要优化的，是后者。下面「缓存」都指前缀缓存。

## 2. 三条铁律（记住就够）

1. **稳定内容放最前，可变内容放最后**——缓存只认前缀。
2. **逐字节精确匹配**——一个空格、一个大小写、一个工具定义字段的改动，都会让缓存从断裂点起作废。
3. **前缀要够长**——各家都有最小缓存门槛（普遍 1024 token 起），太短的 system prompt 根本不触发缓存。

## 3. 三家厂商速查（以官方最新文档为准，价格会变动）

### Anthropic Claude

| 项 | 值 |
|---|---|
| 触发方式 | 顶层 `cache_control: {"type":"ephemeral"}` 自动缓存；或内容块上手动设断点（最多 4 个） |
| 最小可缓存 | Sonnet/Opus 4.x 为 1024 token；Haiku 3.5 为 2048；Haiku 4.5 为 4096 |
| TTL | 5 分钟（默认）或 1 小时（写入更贵） |
| 计费 | 缓存写入 1.25 倍（5m）/ 2 倍（1h）输入价；缓存命中**0.1 倍**输入价 |
| 观测字段 | `cache_creation_input_tokens`（写入）/ `cache_read_input_tokens`（命中） |
| 失效顺序 | tools → system → messages 级联失效：改 tools 会让后面全失效 |

### OpenAI

| 项 | 值 |
|---|---|
| 触发方式 | 自动，无需改代码（prompt ≥ 1024 token；部分旧模型门槛 1024-2048） |
| 粒度 | 命中按 128 token 递增 |
| 计费 | 命中折扣随模型而异：gpt-4o 约 50% off，gpt-4.1 75%，gpt-5.2 约 90%；GPT-5.6 及以后缓存**写入**收 1.25 倍 |
| TTL | 内存缓存空闲约 5-10 分钟失效、1 小时内必清；部分模型支持 24h 长留存、30m 显式 TTL |
| 观测字段 | `usage.prompt_tokens_details.cached_tokens`（命中）/ `cache_write_tokens`（写入，新模型） |
| 进阶 | `prompt_cache_key` 把共享前缀的请求路由到同一台机器提高命中（建议每 key ~15 req/min）；GPT-5.6+ 可设 `prompt_cache_breakpoint` 显式断点 |

### DeepSeek

| 项 | 值 |
|---|---|
| 触发方式 | 自动，无需改代码；**磁盘缓存**（靠 MLA 把 KV 压缩到可落盘） |
| 匹配规则 | 只认**从第 0 个 token 起**的相同前缀；中间开始的重复不命中 |
| 存储单元 | 64 token；不足 64 token 不缓存 |
| 计费 | 命中价远低于未命中（早期约 0.1 元/百万 vs 1 元/百万；V4 后分峰谷价，命中约 0.05-0.3 元/百万） |
| 观测字段 | `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` |
| 效果 | 128K 输入、大部分重复时，首 token 从 13s 降到 500ms |

> 结论：**OpenAI 与 DeepSeek 全自动，你只要「把稳定前缀放前面」就能白捡；Anthropic 需要显式控制，但控制粒度更细。**

## 4. Agent 设计模式

### 模式一：让 system prompt + 工具定义成为稳定前缀

Agent 循环里，每一步都会把 system prompt、工具定义、历史消息重发一遍。只要前两者**每步都完全一致**，它们就是每次请求的共享前缀，每一步都命中缓存。

- 不要在循环过程中改 system prompt 或工具定义（Anthropic 下这会级联失效整个前缀）。
- 工具定义（JSON Schema）一旦定了就别动，改字段等于换前缀。

### 模式二：多轮对话里「保留历史，别重写」

多轮对话天然是前缀增长结构：第 N+1 轮的前缀 = 第 N 轮全部 + 一轮新内容。

- **不要重新排序、不要改写、不要压缩历史**。任何对历史消息的改动都会破坏前缀。
- 需要裁剪上下文时，优先**从尾部/中部丢弃**，或接受「裁剪点之后的缓存重新建立」，而不是重写已有消息。

### 模式三：RAG / 文档问答——文档放前，问题放后

把同一篇长文档注入上下文，连续问多个问题：文档是稳定前缀，每次都命中。这是缓存收益最大的场景（文档越长越明显）。

### 模式四：警惕 compaction / summary 破坏缓存

很多 Agent 会在上下文过长时做「摘要压缩」。要意识到：摘要一旦替换历史，**缓存前缀被整体打碎**，代价是把省下的 token 重新 prefill 一遍。做压缩时要权衡「省 token」与「丢缓存」哪个更划算。

### 模式五：短前缀不吃缓存，但别为凑长度注水

system prompt 不足 1024 token 时不会触发缓存。但**不要为了凑门槛去注水**——水货内容污染输出质量，得不偿失。缓存是锦上添花，正确性优先。

### 模式六：并发场景用 prompt_cache_key（OpenAI）

大量并发请求共享同一长前缀时，设一个稳定的 `prompt_cache_key`，把请求路由到同一台机器，显著提高命中率。

## 5. 在代码里监控命中

每次循环都打印这几个字段，画成曲线：

- OpenAI：`usage.prompt_tokens_details.cached_tokens` 占 `prompt_tokens` 的比例。
- Anthropic：`cache_read_input_tokens` 占输入的比例。
- DeepSeek：`prompt_cache_hit_tokens` 占输入的比例。

**命中率是 Agent 成本健康度的核心指标。**命中率暴跌，通常意味着某个「应该稳定」的东西（system prompt、工具定义、历史处理逻辑）在不经意间变了。

## 6. 一张 Agent 视角速查表

| 场景 | 正确做法 | 会破坏缓存的做法 |
|---|---|---|
| system prompt | 全局稳定，放最前 | 每次请求动态拼一段 |
| 工具定义 | 定义一次，全程复用 | 循环里增删工具字段 |
| 多轮历史 | 原样追加，不动旧消息 | 重排、改写、重新摘要 |
| RAG 文档 | 同一文档连续多问 | 每次重排文档块顺序 |
| 用户输入 | 放最后 | 塞进前缀中间 |
| 上下文超限 | 尾/中裁剪，接受重建 | 重写全部历史 |

## 7. 自测题（先答再看）

1. KV Cache 里存的是 Q、K、V 中的哪两个？为什么不是 Q？
2. 为什么「前缀必须逐字节精确匹配」才能命中缓存？
3. prefill 和 decode 两个阶段，各自的瓶颈是什么？分别影响哪个延迟指标？
4. 7B 模型每 token 的 KV Cache 约多大？1000 token 呢？
5. GQA 和 MLA 分别用什么思路减小 KV Cache？
6. Agent 循环里，为什么 system prompt 和工具定义要全程保持稳定？
7. Anthropic 下，改了 tools 会发生什么？改 system 呢？
8. 多轮对话里，为什么「压缩/摘要历史」可能反而更贵？
9. 用什么字段监控缓存命中率？三家各是什么？
10. DeepSeek 的缓存为什么能放在磁盘上？（提示：和模型架构有关）

### 答案要点

1. 存 K 和 V。因为 K、V 会被后续所有 token 反复使用，且不再变化；Q 只在生成「当前 token」这一步用一次，用完即弃。
2. 缓存的键是前缀 token 的 K/V，任何一个 token 变了，从该位置起所有 K/V 全变，缓存从断裂点作废。
3. prefill 是算力密集，决定 TTFT（首 token 延迟）；decode 是显存带宽密集，决定 TPOT（每 token 延迟/生成速度）。
4. 约 0.5 MB/token，1000 token 约 0.5 GB（以 Llama-2 7B、FP16 为例）。
5. GQA 减少 KV 头数（多 Q 头共享 KV 头）；MLA 把 K/V 低秩压缩成潜在向量再缓存。
6. 它们构成每次请求的共享前缀；一旦变化，缓存从断裂点级联失效，命中率归零。
7. 改 tools 会让 tools、system、messages 全部级联失效；改 system 让 system 和 messages 失效（messages 单独改只影响 messages）。
8. 摘要替换历史会打碎缓存前缀，被替换部分要重新 prefill；省下的 token 可能抵不上丢掉的缓存收益。
9. OpenAI 看 `cached_tokens`；Anthropic 看 `cache_read_input_tokens`；DeepSeek 看 `prompt_cache_hit_tokens`。
10. 因为 MLA 把 KV 压缩得足够小，可以放进分布式硬盘阵列，缓存才能从显存扩展到磁盘。

## 8. 收尾：三条带走

1. **KV Cache 是「用显存换算力」**，前缀缓存是「用一次写入换多次便宜读取」。
2. **命中率的敌人是「不必要的变动」**——system、工具、历史、文档顺序，能不动就不动。
3. **先监控命中率，再谈优化**。没有 `cached_tokens` 数据，所有缓存优化都是盲人摸象。
