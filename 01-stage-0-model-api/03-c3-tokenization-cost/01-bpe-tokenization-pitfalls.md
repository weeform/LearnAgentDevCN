# C3-1 · Token 与分词：BPE 直觉与 6 个坑
> 阅读约 12 分钟。这一篇不要求你记住 BPE 算法，只要求你建立「看到一段文本就能估出 token 量级」的直觉。

## 1. 模型眼里没有字符

你发给 API 的是字符串，模型看到的是一串整数。中间这一步叫**分词（tokenization）**：

```
"今天天气不错"  →  [37241, 872, 5530, 2210]  →  模型
```

模型算的是第二个序列。所以：

- **计费按 token，不按字符**；
- **上下文窗口按 token，不按字符**；
- **截断也发生在 token 边界上**。

字符数只是个粗略代理，而且这个代理的误差会随语言和内容类型剧烈变化。

## 2. BPE：三句话讲清它怎么切

主流分词算法是**BPE（Byte Pair Encoding，字节对编码）**，原理可以用三句话概括：

1. **起点**：所有文本先拆成最小单位（字节或字符），词表就这么大。
2. **合并**：统计训练语料里哪两个相邻单位出现得最频繁，把它们合并成一个新单位，加入词表；重复这一步几万次。
3. **结果**：得到一个 5 万～20 万的词表，高频的整词（如 `the`、`function`、常见中文词）是**一个 token**，罕见的东西只能退化成一堆碎片 token。

推论非常直接：**越常见的表达越便宜，越罕见越贵。**这解释了后面所有的坑。

> 词表规模参考：OpenAI 的 GPT-4o 与 GPT-5 全系共用 `o200k_base`（约 20 万）。同一家族共用分词器是个好消息——你量一次 token，换模型不必重量。

## 3. 先建立一把「感觉尺」

以 `o200k_base` 这类主流分词器为基准，粗略感受（**不同分词器会有出入，量级对就行**）：

| 内容类型 | 典型 token 密度 |
|---|---|
| 英文散文 | 1 token ≈ 4 个字符 ≈ 0.75 个单词 |
| 代码（Python/JS） | 1 token ≈ 3～3.5 个字符 |
| 中文 | 1 个汉字 ≈ 0.7～1.5 token |
| JSON（带缩进） | 1 token ≈ 2～2.5 个字符 |
| 数字串 | 极不稳定，见坑 2 |
| emoji / 罕见符号 | 1 个可能占 2～6 token |

记住三个锚点就够用：

- **1000 英文单词 ≈ 1300 token**
- **1000 汉字 ≈ 1000～1500 token**
- **A4 页中文（约 1000 字）≈ 1.5 页上下文的千分之一**—— 也就是说 128K 上下文大约能装 100 页中文

## 4. 六个坑（Agent 场景专属）

### 坑 1：以为「1 汉字 = 1 token」

这是最普遍的误判。真实情况：

- 常用汉字、常见词往往**合并成词**，一个双字词可能只要 1～2 token；
- 生僻字、专名、混合了英文的内容会退化成**单字甚至字节级碎片**，1 个字能吃掉 2～3 token；
- **不同厂商差异很大**：Anthropic 官方文档明确说明，Claude 4.7 及以后的模型换用了新分词器，**同样的英文文本大约多出 30% 的 token**，中文同样受影响。

**后果**：同一份 system prompt，从 Claude 4.6 迁到 4.8，token 数可能涨三成——价目表没变，账单涨了。

**做法**：换模型必须重量一次 token，不能沿用旧数字。

### 坑 2：数字被切成碎片

BPE 对数字的处理很不友好，`2024` 可能被切成 `20` + `24`，`3.14159` 被切成好几段。

两个后果：

1. **模型算数差**：它看到的不是"三千二百五十一"，而是几个互不相干的数字碎片，这是大模型做算术容易翻车的底层原因之一。
2. **ID 类字段特别费**：订单号、UUID、时间戳这类长 ID，一个可能吃掉 10～20 token。Agent 里如果你把一堆 ID 列表塞进上下文，成本会很可观。

**做法**：给模型看的 ID 尽量短或用短别名（`"订单A": "20240909xxxx"`），列表优先用紧凑格式。

### 坑 3：JSON 的空格和缩进也在烧钱

同一份数据：

```json
// pretty：约 90 token
{
  "name": "search",
  "arguments": { "query": "kv cache" }
}

// minified：约 45 token
{"name":"search","arguments":{"query":"kv cache"}}
```

缩进、换行、空格**全都是 token**。工具返回值如果 pretty-print，可能白花一倍的钱。

**做法**：**进模型的内容一律 minify**，给用户看的再格式化。

### 坑 4：工具定义是隐形的固定成本

你在 `tools` 里传的每个函数，都会被序列化成一段 schema 文本，塞进 prompt 前面。一个中等复杂度的工具定义大约**50～300 token**；带 10 个工具的 Agent，光工具定义就 1000～3000 token。

关键在于：**每一次请求都要重新发一遍**，10 步循环就是 10 遍。

**做法**：

- 工具描述写清楚但别啰嗦（描述本身也是 token）；
- 工具多的场景做**工具筛选**，每步只传相关的 3～5 个；
- 工具定义放在 prompt 最前且保持稳定（接 C2-5，能吃到前缀缓存）。

### 坑 5：按字符截断会切坏内容

你想"保留最后 8000 字符"：

```python
text[-8000:]   # 危险
```

两种坏法：

- 切在**token 中间**，产生乱码 token，模型行为变得不可预测；
- 切在**多字节字符中间**（中文、emoji），直接产生非法字符串，某些 API 会报 400。

**做法**：截断必须在 token 层面做——先编码成 token 序列，切，再解码回文本（`tiktoken` 支持 encode/decode）。

### 坑 6：换模型 = 换账本

分词器不通用，所以：

- 从 GPT-4o 迁 GPT-5：**不用重量**（共用 `o200k_base`）；
- 从 Claude 4.6 迁 4.7+：**要重量**（约 +30%）；
- 跨厂商迁移：**一定重量**。

**做法**：把"每个模型的 token 系数"记进配置，别写死字符数阈值。

## 5. 一句话直觉

> **重复出现的东西便宜，罕见的东西贵；结构化的开销（JSON 括号、工具 schema）是固定税；模型看到的每一个字符，你都要为它付钱，而且是重复付。**
