# C4-4 · 解析容错、失败恢复与自测
> 阅读约 12 分钟。目标：把"模型偶尔吐出坏 JSON"从一个玄学 bug，变成一个可度量、可恢复的流程。

## 1. 模型输出的八种坏法

即使你在 prompt 里写了"只输出 JSON"，仍可能遇到：

| 坏法 | 示例 |
|---|---|
| markdown 围栏 | `json\n{...}\n` |
| 前缀寒暄 | "好的，这是结果：{...}" |
| 后缀解释 | "{...}\\n希望对你有帮助！" |
| 尾随逗号 | `{"a":1,}` |
| 单引号 / Python 字典 | `{'a': 1}` |
| 注释 | `{ /* 注释 */ "a": 1 }` |
| 键名不加引号 | `{a: 1}` |
| **被截断** | `{"a": 1, "b": "这是一段很长的文字…` |

前七种能救，第八种**必须重来**。

## 2. 四级流水线

```
原始文本 → ① 剥离 → ② 解析 → ③ 校验 → ④ 修复
```

### ① 剥离（本地，零成本）

- 去掉 `` 围栏（`^``(?:json)?` 与结尾 ```）；
- 取**第一个 `{` 到最后一个 `}`**（或 `[` 到 `]`）之间的内容；
- 去掉首尾空白与控制字符。

> 这一步不要过度设计。用正则取最外层括号，比手写一堆规则稳。

### ② 解析（本地）

```python
try:
    obj = json.loads(cleaned)
except json.JSONDecodeError:
    obj = None
```

需要更强的容错时，可用社区库（如 `json-repair` 一类）处理尾随逗号、单引号等情况——但**不要把它当银弹**：修复出来的结构未必符合你的语义预期。

### ③ 校验（本地，最关键）

**解析成功 ≠ 可信。**必须做结构校验：

- 用**JSON Schema**（`jsonschema` 库）校验字段与类型；
- 或用**Pydantic**直接把 dict 转成强类型对象，同时完成类型转换与校验；
- 业务规则单独校验（金额非负、日期不晚于今天、枚举值合法……）。

校验是你和模型之间最后一道闸门，**永远不要跳过**。

### ④ 修复（三级，逐级升价）

| 级别 | 动作 | 代价 |
|---|---|---|
| L1 本地修复 | 剥离、去尾逗号、补全括号 | 几乎为 0 |
| L2 自修复重发 | 把**原始输出 + 报错信息**回传给模型，让它改 | 一次调用 |
| L3 降级 | 换 strict / 工具模式 / 换更强模型 / 转人工 | 依场景 |

L2 的 prompt 模板（很有效）：

```
你上一次的输出无法被解析：
<原始输出>
{raw}

解析器报错：
{error}

请严格遵守以下要求重新输出，只输出 JSON，不要任何解释：
{schema 或 要求}
```

要点：**把报错原文给它**，模型能看懂自己错在哪；**限制重试次数**（2 次足够），超过就走 L3。

## 3. 截断：唯一必须重来的情况

判据来自 API，不来自文本：

```python
if finish_reason == "length":
    # 输出被 max_completion_tokens 截断，JSON 必然不完整
```

处理方式：

1. **不要尝试解析**，直接判失败；
2. 重试时可以：提高 `max_completion_tokens`、要求"更简洁"、或拆分任务（先输出一半结构）；
3. 长期方案：按 C3-4 的预算表，给输出**预留足够额度**。

另一个隐蔽情况：流式场景下连接中断（C4-1），表现同样是"JSON 不完整"——所以**失败原因要记录清楚**：`length` / `network` / `parse_error` 是三种不同的病。

## 4. 记录与评测

每次解析失败都记下：

```
request_id, model, prompt_version, schema_version,
raw_output (截断保存), error_type, repair_level, final_status
```

这批数据有两个用途：

- **定位**：发现"某个模型 + 某类输入"失败率异常，针对性改 prompt 或换模型；
- **回归**：把失败样例攒成评测集，改 prompt / 换模型时跑一遍（阶段 5 的核心资产，现在就该开始攒）。

## 5. 安全提醒（提前预告）

模型输出要当**不可信输入**处理：

- 不要 `eval()` / `exec()` 它给的代码或表达式；
- 塞进数据库/SQL 前走参数化；
- 渲染到页面前做转义；
- 交给下游工具前校验参数范围（比如路径不能是 `../../etc/passwd`）。

这一条在阶段 5「安全」里会展开，但从你写第一个 Agent 起就该遵守。

## 6. 自测题（10 道）

1. 流式输出中，`usage` 字段默认能拿到吗？怎么才能拿到？
2. SSE 帧的分隔符是什么？结束标志是什么？
3. 工具调用的 `arguments` 为什么不能单片 `json.loads`？
4. 并行工具调用时，为什么必须按 `index` 分槽累加？
5. 回传工具结果时必须带什么字段？少了会怎样？
6. strict 模式下，"可选字段"应该怎么写？
7. `response_format: json_object` 能保证什么、不能保证什么？
8. 为什么 schema 要尽量保持稳定（从约束解码角度回答）？
9. 输出被截断时，判据是什么？应如何处理？
10. 自修复（L2）时，应该把哪些信息回传给模型？

### 答案要点

1. 默认拿不到；传 `stream_options: {"include_usage": true}`。
2. 空行（`\n\n`）；`data: [DONE]`。
3. 它是字符串分片，单片几乎必然不是合法 JSON，需累加后解析。
4. 多个工具的参数分片会交错到达，用单变量会互相污染。
5. 必须带 `tool_call_id`，且与请求时一致；缺失/错误会报 400。
6. 用联合类型 `"type": ["string", "null"]`，同时仍要列入 `required`。
7. 保证输出是合法 JSON；**不保证**字段结构符合你的预期。
8. schema 会被编译成状态机并缓存，频繁变化会触发反复编译，增加延迟。
9. `finish_reason == "length"`；不要解析，提高长度上限或压缩输出后重试。
10. 原始输出 + 解析器报错原文 + 明确的格式要求（schema）。
