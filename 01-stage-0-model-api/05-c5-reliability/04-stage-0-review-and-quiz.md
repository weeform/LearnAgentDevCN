# C5-4 · 阶段 0 总复习：速查表、交付物与综合自测
> 阅读约 15 分钟。这一篇是阶段 0 的收尾：**把知识压缩成能查的东西、能交付的东西、能自测的东西。**

## 1. 参数速查大表

### 输入与结构

| 参数 | 作用 | 备注 |
|---|---|---|
| `model` | 选模型 | 决定能力、价格、分词器 |
| `messages` | 对话数组 | **无状态**，每次全量重发 |
| `system` / developer | 系统指令 | 放最前，保持稳定以吃缓存 |
| `tools` | 工具定义 | 隐形固定成本，每次都发 |

### 采样（推理类模型不支持）

| 参数 | 作用 | 常用值 |
|---|---|---|
| `temperature` | 缩放 logits，控随机性 | 0～0.3 稳定；0.7～1.0 创意 |
| `top_p` | 累计概率截断 | 0.9 左右；**一般与 temperature 二选一** |
| `top_k` | 保留前 k 个候选 | 部分厂商支持 |
| `seed` | 尽力复现 | 配合固定参数，**不保证完全一致** |
| `presence/frequency_penalty` | 抑制重复 | 谨慎使用，易损伤质量 |
| `reasoning_effort` / `thinking` | 推理强度 | 推理模型的"档位"，**替代 temperature** |

### 长度与停止

| 参数 | 作用 | 备注 |
|---|---|---|
| `max_completion_tokens` | 输出上限 | **必设**：护栏 + 成本上限 |
| `stop` | 停止串 | 老用法，优先用结构化/工具 |
| `stream` | 流式 | 见 C4 |
| `finish_reason` | **返回的**结束原因 | `stop`/`length`/`tool_calls`/`content_filter`，**Agent 循环的方向盘** |

### 工具与结构化

| 参数 | 作用 |
|---|---|
| `tools` | 声明可调用的函数 |
| `tool_choice` | `auto` / `none` / 指定某个（跨家做结构化输出的常用技巧） |
| `parallel_tool_calls` | 是否允许一次调多个工具 |
| `response_format` | `text` / `json_object` / `json_schema`（strict） |

### 工程与观测

| 项 | 作用 |
|---|---|
| `stream_options.include_usage` | 流式下拿 usage（否则成本统计为 0） |
| `usage` | `prompt_tokens` / `cached_tokens` / `completion_tokens` |
| `service_tier` / fast mode | 付费换低延迟 |
| request id 响应头 | **必存**，排查的唯一凭据 |

## 2. 阶段 0 知识地图

| 课 | 回答的问题 | 一句话结论 |
|---|---|---|
| C1 | 有哪些旋钮，各有什么用 | 参数是 Agent 的行为开关与成本开关 |
| C2 | 请求在服务端经历了什么 | KV Cache 单请求内永远在跑；**跨请求前缀缓存才是你能优化的点** |
| C3 | 钱花在哪 | 输出最贵；Agent 成本**平方增长**；稳定前缀决定缓存收益 |
| C4 | 怎么可靠地拿到结构化结果 | 工具参数要**累加后解析**；strict schema 保证结构 |
| C5 | 失败怎么办 | 分类处理 + 指数退避 + 降级链 |

**贯穿阶段 0 的三条暗线**（总纲第 7 节）：

1. 成本意识：这会增加多少 token？
2. 可复现性：同样的输入，明天还能得到同样的结果吗？
3. 上下文预算：这段内容值得占用上下文吗？它稳定吗？

## 3. 阶段 0 的交付物：调用层自检清单

学完阶段 0，你应该有一个自己的**调用层封装**。用这份清单自检（12 项）：

- [ ] 统一的 `chat()` 入口，屏蔽厂商差异
- [ ] 必设 `max_completion_tokens`
- [ ] 采样参数按场景分档（稳定/创意），不混用 temperature 与 top_p
- [ ] 推理模型走 `reasoning_effort`，不传 temperature
- [ ] 稳定内容（system + tools）放最前且内容固定
- [ ] 记录 `usage`（含 `cached_tokens`）与 request id
- [ ] 错误按 code 分类，只对瞬时错误重试
- [ ] 指数退避 + full jitter + 重试次数与总时长双预算
- [ ] 连接 / 首 token / 整体三层超时
- [ ] 流式工具调用有按 index 累加的收集器
- [ ] 结构化输出优先用 strict schema 或"工具当结构体"
- [ ] 模型分级与降级链（主 → 备 → 兜底）

**打勾少于 8 项，说明阶段 0 还没真正落地**——补完再进阶段 1，否则后面写 Agent 会反复踩坑。

## 4. 综合自测（15 道）

> 覆盖 C1–C5。答对 11 道以上，可以进入阶段 1。

1. API 是无状态的，这带来哪三个工程后果？
2. `finish_reason == "length"` 意味着什么？Agent 里应该怎么处理？
3. 为什么推理类模型传 `temperature` 会报错？应该改用什么参数？
4. KV Cache 缓存的是 K/V 还是 Q？为什么？
5. 单请求内的 KV Cache 与跨请求的 Prompt Caching，哪个是 Agent 开发者能优化的？
6. 什么情况下前缀缓存不会命中？（举 3 种）
7. 为什么 `max_tokens` 被 `max_completion_tokens` 取代？
8. 一个 20 步的 Agent，稳定前缀 3000、每步新增 800，总输入大约是多少？（给量级即可）
9. 为什么"模型分级"是收益最大的降本手段？
10. 流式下为什么默认拿不到 `usage`？怎么解决？
11. 工具调用的 `arguments` 应该如何处理才不会报错？
12. strict 模式下，可选字段必须怎么写？
13. 什么 HTTP 状态码**绝对不应该**重试？举两个并说明原因。
14. 为什么重试必须加 jitter？
15. 有副作用的操作（如下单）重试时，必须有什么保证？

### 答案要点

1. 成本随上下文线性增长、上下文管理成为核心工程、状态必须由你自己维护。
2. 输出被长度上限截断，内容不完整。应提高上限或压缩输出后重试，**不要尝试解析**。
3. 推理模型不接受采样参数（传非默认值直接 400）；改用 `reasoning_effort` / `thinking` 控制推理强度。
4. K 和 V。因果注意力下已生成 token 的 K/V 不再变化，而 Q 只在生成当前 token 时用一次。
5. **跨请求的 Prompt Caching**。单请求内 KV Cache 由服务端自动完成，你无法干预。
6. 前缀不足最小门槛；前缀内容发生任何变化（含 tools 顺序）；TTL 过期；并发未命中路由（任举 3 种）。
7. 因为输出可能包含推理 token，旧名字无法涵盖语义；新参数明确指"完成内容"的上限。
8. `20×3000 + 800×(0+…+19) = 60,000 + 152,000 ≈ 212,000` token（量级约 20 万）。
9. 同家族模型价差可达 25 倍，是唯一能带来数量级变化的手段（前提是有评测集）。
10. 默认不返回；传 `stream_options: {"include_usage": true}`。
11. 按 `index` 分槽累加 `arguments` 字符串，等 `finish_reason == "tool_calls"` 后再 `json.loads`。
12. 用联合类型 `["string", "null"]`，且仍要列入 `required`。
13. 400（参数错，重试必再失败）、401（鉴权失败）；应修代码/配置并告警。
14. 否则所有客户端同步重试，造成惊群，把刚恢复的服务再次打垮。
15. 幂等保证：业务幂等键 + 工具层去重；否则宁可失败并提示人工。

## 5. 阶段 0 完成

到这里，你具备了写第一个 Agent 的**全部调用层基础**。

- 怎么防提示词注入。
