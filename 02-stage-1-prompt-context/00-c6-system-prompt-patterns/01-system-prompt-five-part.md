# C6-1 · 五段式模板：system prompt 的结构化写法
> 阅读约 12 分钟。目标：把你现在「想到哪写到哪」的 prompt，改写成能复用、能版本化、能回归的结构。

## 1. 为什么需要模板

多数人的 prompt 是这样写的：

```
你帮我分析一下这份数据，找出异常，然后告诉我结论。
```

这条 prompt 的问题不是「错」，而是**不可控**：模型怎么定义「异常」、结论要什么格式、发现不确定时说不说，全凭它自己发挥。同样的输入，今天和明天的输出可能完全不一样——违反了阶段 0 贯穿全程的「可复现性」暗线。

模板的价值，是把**每一次都要靠猜的东西，固化成稳定的前缀**。而稳定的前缀能命中**前缀缓存**（Prompt Caching，见 C2-5），既稳又省钱。

## 2. 五段式模板

一个结构化的 system prompt，通常包含五段。**不是每段都必需**，但「约束」和「输出格式」几乎永远值得写。

| 段 | 回答的问题 | 例子 |
|---|---|---|
| 角色 | 你是谁 | 「你是一个订单分析助手」 |
| 目标 | 要做什么 | 「找出上周订单数据的异常点」 |
| 约束 | 不能做什么 / 必须怎么做 | 「不确定时明确说不知道，禁止编造」 |
| 输出格式 | 结果长什么样 | 「输出 JSON，字段为 …」 |
| 示例 | 长什么样才算对 | 给 1–2 个输入输出对 |

## 3. 一个完整例子：从散文到模板

**改前**（散文）：

```
帮我分析订单数据，找出问题。
```

**改后**（五段式）：

```markdown
# 角色
你是电商平台的订单数据分析助手。

# 目标
分析给定的订单数据，找出值得关注的异常点。

# 约束
- 只依据给出的数据得出结论，不得引入数据之外的事实。
- 无法从数据中确认的结论，必须标注「数据不足，无法判断」。
- 不要给出未经数据支撑的改进建议。

# 输出格式
输出 JSON，结构如下：
{
  "anomalies": [{"type": "string", "detail": "string", "evidence": "string"}],
  "summary": "string"
}
每个 anomaly 的 evidence 必须是从数据里摘出的原句。

# 示例
输入：
日期,订单号,金额,状态
2026-10-01,A-1024,299,已完成
2026-10-02,A-1025,-150,已完成

输出：
{
  "anomalies": [
    {"type": "负金额", "detail": "A-1025 金额为 -150",
     "evidence": "2026-10-02,A-1025,-150,已完成"}
  ],
  "summary": "1 条异常：A-1025 出现负金额，需确认是否为退款单。"
}
```

看出来了吗：改前模型可以自由发挥，改后每一步都被框住了。**「约束」和「输出格式」贡献了大部分稳定性，角色和目标只是让模型「进入状态」。**

## 4. 五段的权重：别平均用力

一个常见的误解是「五段都写满才算专业」。实测结论是**权重差别很大**：

1. **约束**（权重最高）—— 直接改变模型行为边界。写得好能压掉大部分翻车。
2. **输出格式** —— 决定结果能不能被代码直接消费。能用 JSON Schema / 工具就别用纯文本描述（见 C4）。
3. **示例** —— 对「格式敏感、判断标准模糊」的任务（抽取、分类、改写）提升最明显。
4. **目标** —— 一句话说清即可，写太长反而稀释重点。
5. **角色** —— 见 C6-2，它的实际作用远小于直觉。

**工程建议**：先写「目标 + 约束 + 输出格式」三段，跑不通再加示例，角色段最后再补、甚至可以不写。

### 4.1 三种「看起来像约束、其实不是」的写法

约束段最容易写废。判据只有一条：**换一个工程师来读，能不能不靠猜就判定「这次输违反了没有」**。

| 写成这样 | 问题 | 改成这样 |
|---|---|---|
| 输出要专业、要有洞察 | 不可判定，模型只能自由解释 | 每条结论必须附一个数据字段作为依据；禁止使用「赋能」「闭环」「抓手」这类词 |
| 不要啰嗦 | 不可判定 | 正文不超过 150 字；不给总结段；不复述输入 |
| 尽量准确 | 不可判定 | 无法从数据确认的，字段填 `null`，并在 `notes` 说明缺什么 |
| 注意安全 | 不可判定 | 涉及金额、URL、外部链接的输出必须经二次确认 |
| 保持客观 | 不可判定，且与任务无关 | 删掉（无信息量的约束是纯 token 开销） |

一个可操作的检验：**给每条约束配一个「违反样例」**。配不出来，说明这条约束空泛到连你自己都无法判定。

## 5. 怎么验证模板真的有用

改完 prompt 觉得「好像好多了」，这是最危险的信号。必须落到可重复的验证上。

**第一步：攒一个小回归集。** 20 条真实输入就够（不必 200 条），要覆盖三类：常规样例、边界样例、以前翻过车的样例。这份集合是后面所有 A/B 的地基。

**第二步：一次只改一处。** 想同时加约束、换模型、调 temperature，结果变好了你也说不清是谁的功劳——这就是消融的意义。

```
基线：v2 prompt + 模型 A
实验：v3 prompt + 模型 A      ← 只改了 prompt，差异归因清楚
对照：v3 prompt + 模型 B      ← 另开一轮，判断提升是否被模型覆盖
```

**第三步：看三个指标，不看「感觉」。**

| 指标 | 怎么算 | 关注什么 |
|---|---|---|
| 格式合规率 | 能直接 `json.loads` 成功的比例 | 低于 100% 说明结构约束没兜住 |
| 字段正确率 | 抽 20 条人工核对关键字段 | 这是真正的效果指标 |
| 平均输出长度 | completion tokens 均值 | 涨太多要查是不是变得啰嗦 |

经验值：格式合规率必须做到 100%（做不到就上结构化输出，别靠 prompt 喊）；字段正确率提升 5 个百分点以下，通常不值得为它增加 30% 的 token。

这一节讲的是「改一次、验一次」；要让每次改动都被自动验、而不是靠人记得跑，见 C6-5 的回归流水线。

## 6. 三条纪律

1. **约束要具体、可验证**。「不要废话」不可验证；「回答不超过 100 字」可验证。
2. **格式优先用结构化手段**。输出 JSON 就用 `response_format` 或工具，别只靠 prompt 里喊「只输出 JSON」（原理见 C4-3）。
3. **版本化**。给 prompt 加版本号，改动时记下「为什么改、改了哪里」。这决定你半年后还能不能复现、能不能回归。

版本号分两处放，各有用途：

```markdown
# meta.yaml —— 给人看：为什么改、能不能回滚
version: 3
changes:
  - v3: 新增「evidence 必须摘原文」；原因：v2 出现编造引用（case-114）
rollback_to: 2
```

```python
# 运行时拼在 system prompt 末尾 —— 给机器看：日志里能反查是哪一版
SYSTEM = TEMPLATE.format(...) + f"\n[prompt:v{VERSION}]"
```

拼在**末尾**而不是开头：前面那一大段模板是稳定前缀，版本一变整段都 miss；放末尾能让 v2→v3 的改动尽量不伤前缀命中（原理见 C2-5）。

不要用 `prompt_final.md`、`prompt_final2.md` 这种命名——半年后你分不清哪个是线上版。**版本指纹进 prompt** 还有个额外好处：输出漂移时，你能从 trace 里直接看出是哪一版在跑。

版本管理还有下半场：回归集怎么建、什么该拦发布、不改 prompt 为什么也会变差——C6-5 专门讲。

## 7. 小结

- 五段式：角色 / 目标 / 约束 / 输出格式 / 示例。
- 权重：约束 > 输出格式 ≈ 示例 > 目标 > 角色。
- 约束的可验证标准：能配出一个「违反样例」；配不出来就是废话。
- 验证靠「小回归集 + 一次改一处 + 三个指标」，不靠感觉。
- 价值：把「靠猜」变成「靠稳定前缀」，既稳又省缓存。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 五段式里哪两段「几乎永远值得写」，哪一段「经常可以不写」？为什么是这个排序？
2. 用「换一个工程师来读，能不能不靠猜就判定违反没违反」这把尺子，改写一条你自己项目里的约束。
3. 「输出 JSON」为什么不该只靠 prompt 里喊？如果不靠 prompt，靠什么？

<summary>参考思路</summary>

1. 约束和输出格式永远值得写，因为它们决定结果能不能验收；角色段最可以不写，它主要影响语气，不影响任务能否完成（C6-2）。
2. 把「不要废话」改成「回答不超过 100 字」，把「尽量准确」改成「不确定时输出 unknown，并给出处」。可验证是唯一标准。
3. 用 response_format / json_schema strict 或工具定义来强制结构（C4-3）。纯 prompt 约束是「请求」，结构化手段才是「保证」。
