# C6-4 · CoT 的反例与提示词模式清单
> 阅读约 12 分钟。目标：不盲目套用思维链，并建立一份可复用的模式库。

## 1. CoT 什么时候反而更差

思维链不是万金油。以下场景**强制加 CoT 往往得不偿失**：

1. **简单任务**：答案一步就能得出（如「把这句话翻成英文」）。加「先分析再回答」只会多出一段无意义的推理、更慢、更贵，还可能节外生枝。
2. **创造性 / 发散任务**：写诗、起名、头脑风暴。这类任务要的是跳跃和多样性，强制「先推理」会压抑灵感。
3. **已有更好结构化手段的任务**：能用 JSON Schema、工具、代码确定性解决的部分，交给 CoT 是浪费（见 C4-3）。
4. **模型本身就是推理模型**：这类模型已在内部做扩展思考（见 C1-1 的 `reasoning_effort`），再在外面加一层「先分析」大概率是重复且干扰。

**判断句**：任务是否需要**多步、可验证的中间推理**？不需要就别上 CoT。

### 1.1 一条更实用的判据：中间步骤能不能被验算

「多步推理」这个说法太模糊，容易自己骗自己。更硬的判据是：

> 中间步骤**能不能被检查**？能检查才是真需要 CoT；检查不了，CoT 只是让模型多写一段没人看的解释。

| 任务 | 中间步骤可验算吗 | 该不该上 CoT |
|---|---|---|
| 算「退货率 = 退货单数 / 总单数」 | 能，每步可对账 | 该上（或直接给代码工具） |
| 判断工单属于哪个类别 | 不能，本质是一次匹配 | 不该上 |
| 检查合同条款是否与法条冲突 | 能，可逐条对照 | 该上 |
| 给文章起 10 个标题 | 不能，也没有唯一对错 | 不该上 |
| 多条件筛选（按地区+金额+时间过滤） | 能，但更适合交给代码 | 不该上，交给工具 |

注意到最后一行：**能验算 ≠ 该用 CoT**。凡是能被代码确定性完成的部分，优先写代码——CoT 是「没有工具时用模型硬算」的退路，不是首选。

## 2. 一个「CoT 反而更差」的典型场景

任务：从一段客服对话里抽取工单字段（类别、金额、摘要）。

- **错误做法**：让模型「先逐步分析对话，再输出工单」——它可能输出一大段分析，还可能在分析里「脑补」对话没有的信息。
- **正确做法**：直接给 JSON Schema + few-shot 范例，让模型**直接抽**，字段用 `enum` 收窄（见 C4-3 的工单例子）。

抽取类任务要的是**忠实**，不是推理。CoT 的「自由联想」在这里是风险而非收益。

### 2.1 差在哪里：同一段输入的两份输出

输入（节选）：

```
客户：我上周买的那个耳机，右耳没声音了。
客服：方便提供一下订单号吗？
客户：找不到了，好像是 8 月底买的。
```

**加了 CoT 的输出**：

```
分析：客户购买的耳机出现单边无声，属于质量问题。根据描述"上周买的""8 月底"，
推测购买时间约为 8 月下旬，仍在 7 天无理由和 15 天换新期内，应属于换新范畴。
金额方面，该型号耳机市场价约 500–800 元，推测订单金额约 600 元。

{"category": "质量-换新", "amount": 600, "summary": "耳机右耳无声，申请换新"}
```

**不加 CoT 的输出**：

```
{"category": "质量-售后", "amount": null, "summary": "耳机右耳无声，客户无法提供订单号，购买时间约8月底"}
```

差别在哪：`amount: 600` 是**凭空编的**（对话里没有任何金额），`category` 也被推到了更具体的「换新」——而对话里客户根本没提换新诉求。这两处错误都由「先分析」这一步产生：**分析过程必须有内容，模型就会去填它没有的信息**。

而正确版本用 `null` 表达了「我不知道」，这正是抽取任务该有的行为。`null` 是可消费的，编造的数字不可消费。

## 3. 提示词模式清单（可复用）

把常见手法抽象成「模式」，写 prompt 时按需取用，比背模板更灵活：

| 模式 | 一句话 | 适用 |
|---|---|---|
| 角色化 | 身份翻译成行为约束（见 C6-2） | 风格、领域术语 |
| 结构化输出 | 用 Schema / 工具框住输出 | 所有需代码消费的结果 |
| 少样本 | 给 2–5 个范例对齐 | 格式敏感、抽取、分类 |
| 思维链 | 先推理后结论 | 多步推理 |
| 自一致性 | 多次采样取多数 | 有唯一解的难题 |
| 反幻觉约束 | 「不确定就说不知道」+ 要求引用证据 | 事实问答、RAG |
| 分步约束 | 「一次只做一件事」「先 X 再 Y」 | 复杂流程拆解 |
| 反面约束 | 「不要用形容词开头」「禁止输出解释」 | 需要克制输出的场景 |
| 兜底兜口 | 明确「不知道」的合法回答 | 所有事实型任务 |
| 输出自检 | 输出前按清单逐项核对（如「字段是否齐全 / 是否引用原文」） | 长输出、多字段任务 |

最后一条「输出自检」值得单独说：它不是 CoT，而是**让模型在生成后回看自己的结果**。对多字段抽取特别有用，因为模型在写完 JSON 后扫一眼「有没有空字段」的成本很低，但能抓掉相当一部分遗漏。写法是给它一个极短的检查项，而不是让它重新分析整段输入：

```
输出前自检（不要输出自检过程）：
- 三个字段是否都有值或明确为 null？
- summary 是否包含输入里没有的信息？若有，删除。
```

关键词「不要输出自检过程」——否则你会在 JSON 前面多收到一段自检文字，格式又坏了。

## 4. 组合优于单点

现实里的好 prompt 通常是**几个模式的组合**，而不是某一个手法用到底。例如一个 RAG 问答的 system prompt：

- 结构化输出（引用字段）+ 反幻觉约束（必须标注出处）+ 兜底（检索不到就明说）。

关键是：**每个模式都要有它存在的理由**，而不是「教程说该加」。

判断「有没有理由」的方法是反推：**删掉这一段，输出会变成什么样？** 如果答不上来，说明你并不知道它在防什么，那它大概率可以删。

## 5. 小结

- CoT 反例：简单任务、创造性任务、有结构化替代方案、推理模型。
- 硬判据：中间步骤**能不能被验算**；能验算但能被代码做的，交给代码。
- 抽取要「忠实」不要「推理」；CoT 会逼模型去填它本来没有的信息，`null` 比编造的数字值钱。
- 模式清单是「按需取用」的零件库，组合优于单点；删掉说不出用途的那一段。
