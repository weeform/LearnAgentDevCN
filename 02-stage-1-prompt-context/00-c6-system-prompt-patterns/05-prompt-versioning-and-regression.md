# C6-5 · Prompt 版本管理与回归测试
> 阅读约 14 分钟。C6-1 讲的是「这一次改动对不对」，这一篇讲「改了一百次之后还稳不稳」——把 prompt 当资产管，而不是当草稿改。

## 1. Prompt 为什么比代码更容易失控

代码有编译器、有测试、有 git diff，改错了跑不起来。Prompt 什么都没有：它是一段自然语言字符串，改一个词系统照常运行，只是悄悄变差。

失控通常长成这三个样子：

| 形态 | 现场 | 后果 |
|---|---|---|
| 无版本 | 目录里躺着 `prompt.md`、`prompt_new.md`、`prompt_final_v2.md` | 分不清哪个在线上跑，出问题无法回滚 |
| 无回归集 | 改完看几条输出「感觉好多了」 | 修好 A 撞坏 B，两周后才发现 |
| 无归属记录 | 不知道这行为什么这么写 | 没人敢删任何一句，prompt 只增不减 |

三者会互相喂养：没版本 → 不敢改 → 不敢删 → prompt 越来越长 → 固定成本上升 → 更不敢动。**打破循环的入口是版本号，支点是回归集。**

## 2. 版本号不是自增整数，是「可追溯的变更单元」

先把常见误解拆掉：版本号的作用不是「表示新旧」，而是**让每一次线上行为都能反查到是哪段文字造成的**。

### 2.1 什么时候该 bump

判据只有一条：**模型的输入变了，就要 bump**。

| 改动 | bump？ | 原因 |
|---|---|---|
| 改约束、改输出格式、增删示例 | **要** | 模型看到的 token 变了，行为可能变 |
| 调 temperature / max_tokens | **要** | 没改 prompt，但改了输出分布 |
| 换模型版本 | **要** | 同 prompt 换模型等于换了半个系统 |
| 修注释里的错别字（在注释行内） | 不要 | 注释也是 token，但它不改指令语义——**为省事，把变更记录放在 prompt 外的 sidecar 文件更干净** |
| 改代码里拼接的变量顺序 | 要 | 位置变了，缓存前缀就断了 |

最后一条容易被忽略：prompt 的逻辑边界不是「那个 .md 文件」，而是**最终发给 API 的那串 token**。所以版本号应该覆盖「模板 + 变量装配顺序」，不只是模板文本。

### 2.2 版本号写在哪里

两个位置都要，各有用途：

```markdown
<!-- prompts/order_extract/meta.yaml —— 给人看的变更史 -->
version: 3
updated: 2026-10-28
changes:
  - v3: 新增「evidence 必须摘原文」；原因：v2 在 case-114 编造了金额
  - v2: 输出改为 JSON Schema；原因：v1 格式合规率 87%
rollback_to: 2
```

```python
# 运行时拼进 system prompt 的最后一行 —— 给机器看的
SYSTEM = TEMPLATE.format(...) + f"\n\n[prompt:v{VERSION} model:{MODEL_ID}]"
```

拼在末尾而不是开头，是为了不打断前缀缓存（见 C2-5、C7-2）。这样每条 trace 里都带着版本指纹，线上效果突然下滑时，先看是不是版本变了，而不是先怀疑模型。

## 3. 把 prompt 当文件资产：一个够用的目录结构

```
prompts/
  order_extract/
    v3.md                ← 当前线上版（模板，含 {{variables}}）
    v2.md                ← 保留，回滚用
    meta.yaml            ← 版本号、变更原因、回滚目标
    evalset.jsonl        ← 回归集（用例只增不删）
  reply_rewrite/
    ...
```

四条约定，每条都对应一个具体的坑：

1. **旧版本不删**。回滚的成本应该是一次配置改动，不是一次重写。磁盘很便宜，凌晨三点重写 prompt 很贵。
2. **模板用显式占位符**（`{{order_json}}`），不要用 f-string 直接拼。占位符能静态检查「变量漏传」，f-string 漏了就是 `NameError` 或者更糟——悄悄拼成字符串 `"None"`。
3. **prompt 与代码同仓、同一次提交**。改了 prompt 却不改代码，等于线上行为在代码没动的情况下变了，这是最难查的一类故障。
4. **回归集跟着 prompt 走**，放在同一目录。跨目录的评测集，半年后一定和 prompt 对不上号。

## 4. 回归集是核心资产，不是附庸

C6-1 说过「20 条真实输入就够」。这一节讲这 20 条该怎么组织和判定。

### 4.1 三类样例，缺一不可

| 类别 | 数量占比 | 作用 | 从哪来 |
|---|---|---|---|
| 常规 | ~50% | 防止改动把主路径改坏 | 线上抽样，脱敏 |
| 边界 | ~30% | 空输入、超长、格式错乱、语言混杂 | 主动构造（对着约束逐条造） |
| 翻车复现 | ~20% | 每修一个 bug 就固化成一条 | 线上事故 / badcase |

第三类最关键也最容易被跳过。**修完 bug 不补用例，等于这个 bug 会以另一种形态再回来一次。**

### 4.2 期望值怎么写：三种判据，成本递增

不要强求「完全等于某个字符串」——大模型输出天然有波动，精确匹配会让回归集天天飘红，最后没人看。

```jsonl
{"id":"c-001","input":{...},"expect":{"type":"exact","value":"拒答"},"tags":["常规"]}
{"id":"c-014","input":{...},"expect":{"type":"schema","required":["amount","currency"]},"tags":["边界"]}
{"id":"c-114","input":{...},"expect":{"type":"rubric","must":["金额为 null","不得出现具体数字"]},"tags":["翻车"]}
```

| 判据 | 判定方式 | 适合 | 缺点 |
|---|---|---|---|
| `exact` | 字符串 / 枚举完全相等 | 分类、路由、拒答 | 对措辞敏感，只适合窄输出 |
| `schema` | 结构 + 必填字段 + 类型校验 | 抽取、结构化输出 | 校验不了内容对错 |
| `rubric` | 一组「必须满足 / 禁止出现」的断言，或模型打分 | 开放问答、改写 | 有主观性，**必须人工抽检** |

选择顺序是 **exact > schema > rubric**：能用确定性判据就别用模型判。原因很实际——rubric 判据自己也会漂移，用一个会漂的东西去测另一个会漂的东西，结论不可信。

所以有一条硬规矩：**rubric 用来当硬门禁时，其中的断言必须是程序可判定的**（包含 / 不包含 / 正则 / 字段值比较），不能是「让模型打个 1–5 分」。后者只能算软指标，用来提示人去看。

### 4.3 一个致命错误：拿当前输出当标准答案

「先跑一遍现有 prompt，把输出存成 expected，以后就照这个比对」——这是把当前行为（包括它的 bug）固化成基线。之后所有改动只要「和以前一样」就算通过，**回归集从防线变成了守旧派**。

期望值必须来自**外部真相**：业务规则、人工标注、数据库实际值。写不出来的时候，就退化成 `schema` + `rubric` 断言，而不是抄模型输出。

## 5. 回归怎么跑：硬门禁与软指标

不是所有指标都该拦发布。分两类：

| 类型 | 指标 | 阈值 | 不达标怎么办 |
|---|---|---|---|
| **硬门禁** | 格式合规率 | 必须 100% | 拦住，不许合 |
| **硬门禁** | 翻车复现样例通过率 | 必须 100% | 拦住 |
| 软指标 | 字段正确率 | 不得低于基线 −2pp | 告警，人工判断 |
| 软指标 | 平均输出长度 | 不得高于基线 +30% | 告警（通常意味着变啰嗦） |
| 软指标 | 单次成本 | 不得高于基线 +20% | 告警 |

硬门禁的判据必须**确定性可复现**，否则 CI 会随机阻塞，团队三周内就会把它关掉。软指标的意义是「提醒人看」，不是「替人决策」。

一个够用的执行骨架（`call_model` / `assertion_holds` 是需要你自己实现的桩函数，其余部分可直接用）：

```python
import json, yaml
from pathlib import Path

def check(case, output):
    e = case["expect"]
    if e["type"] == "exact":
        return output.strip() == e["value"]
    if e["type"] == "schema":
        obj = json.loads(output)                 # 解析失败即失败
        return all(k in obj for k in e["required"])
    if e["type"] == "rubric":
        return all(assertion_holds(a, output) for a in e["must"])
    raise ValueError(e["type"])

def run(prompt_dir: Path, model: str):
    meta = yaml.safe_load((prompt_dir / "meta.yaml").read_text())
    tpl = (prompt_dir / f"v{meta['version']}.md").read_text()
    cases = [json.loads(l) for l in (prompt_dir / "evalset.jsonl").read_text().splitlines() if l.strip()]

    fails, guard = [], [c for c in cases if "翻车" in c["tags"]]
    for c in cases:
        try:
            ok = check(c, call_model(tpl, c["input"]))
        except Exception:          # 解析失败也算失败，不能让一条坏样例中断整轮
            ok = False
        if not ok:
            fails.append(c)

    blocked = [c for c in fails if "翻车" in c["tags"]]
    return {"total": len(cases), "fail": len(fails), "guard_total": len(guard),
            "gate": "PASS" if not blocked else f"BLOCK ({len(blocked)} 条翻车用例)"}
```

那个 `except Exception: ok = False` 不是随手防御，它对应的指标就是**格式合规率**：`json.loads` 抛异常 = 格式不合规。如果让异常往外冒，第一条坏输出就会中断整轮，你会误以为「回归跑挂了」，而真相是「这一版格式全崩了」——两种信息的处置完全不同。

跑一次的成本要算清楚：20 条用例、每条 2k tokens 输入，一次回归约 40k tokens。**这个成本远低于一次线上事故**，所以「用例少所以不跑」是个坏理由；真正的约束是「跑一次要 10 分钟，等不及」——那就把它做成异步，提交后跑，不阻塞本地。

## 6. CI 与线上：在两个位置设卡

```
提 PR（改了 prompt）
  → CI 跑回归集：硬门禁失败 = 红，禁止合并
  → 硬门禁通过 + 软指标无异常 = 可合
  → 灰度：新版本按 5% 流量分流，观察 24h
  → 指标持平或更好 = 全量；变差 = 改回 meta.yaml 的 version 字段
```

三个细节：

- **改 prompt 的 PR 要单独提，别和业务代码混在一起**。混在一起时，回归失败你分不清是 prompt 变了还是代码变了。
- **灰度看的是业务指标，不是回归集**。回归集是离线防线，它测不到「用户是不是更爱点这个按钮」。
- **回滚演练要做一次**。写了「改回 version 字段即可回滚」但从来没试过，那条路径大概率是坏的（比如 v2.md 其实被覆盖了）。

## 7. 不改 prompt 也会变差：漂移监控

回归全绿、prompt 一个字没动，效果照样可能下滑。三个来源：

| 漂移来源 | 表现 | 应对 |
|---|---|---|
| 模型版本升级 | 供应商静默更新模型，同 prompt 输出变了 | 锁模型版本（能锁就锁）；升级前跑一遍全量回归 |
| 输入分布漂移 | 新业务线接入，输入变长、领域变了 | 监控输入长度 / 领域分布，超阈值重跑回归 |
| 上游数据变脏 | 工具返回格式变了，prompt 里的示例不再匹配 | 对工具输出加 schema 校验（见 C10-3） |

落地的做法很轻：留 5 条「金丝雀」用例，每天定时跑一次，任一失败就告警。**这 5 条不追求覆盖率，只追求「系统还活着」的最小信号。**

## 8. 与阶段 5 的分工

这一篇给的是**最小可用版**：一个目录 + 一个 jsonl + 一个脚本 + 两条硬门禁。它能防住 80% 的「改坏了不知道」。

阶段 5 的 C19（可观测性）和 C20（评测体系）会往上接：trace 里带上 prompt 版本 → 线上 badcase 自动回流成用例 → 回归集变成持续增长的数据资产。**没有这一篇的版本指纹，C19 的 trace 只是一堆无法归因的日志。**

其中 C20-4 专讲评测真正接进 CI 之后才会暴露的问题：通过线怎么定、judge 也要花钱、flaky 用例怎么处置。本篇的两条硬门禁是它的最小形态。

## 9. 小结

- Prompt 失控的三形态：无版本、无回归集、无归属；入口是版本号，支点是回归集。
- 版本号的判据是「发出去的 token 变了就 bump」，逻辑边界是最终拼装结果，不是那个 .md 文件。
- 版本指纹拼在 prompt 末尾，不打断前缀缓存，且能在 trace 里反查。
- 回归集 = 常规 + 边界 + 翻车复现；翻车样例永久保留，只增不删。
- 期望值必须来自外部真相，别拿模型当前输出当标准答案。
- 硬门禁（格式 100%、翻车 100%）拦发布，软指标只告警——否则没人会认真看。
- 不改 prompt 也会漂移：锁模型版本 + 金丝雀用例日跑。
