# C7-1 · 上下文预算：窗口多大、钱花在哪、为什么增长
> 阅读约 14 分钟。目标：为上下文建立「预算」视角，在动手裁剪前先知道钱是怎么花出去的。

## 1. 上下文就是每次请求的「记忆重放」

API 是**无状态**的（见 C1-1）：模型记不住上一轮，所以每轮都要把**全部历史**重新发一遍。这就是上下文的本质——**你每多一轮对话，就要为前面的所有内容再付一次 token**。

一句话记住这个代价：

> 第 N 轮的输入 = system + 第 1 轮到第 N-1 轮的全部内容。

## 2. 为什么成本会「平方增长」

假设每轮新增约 `t` 个 token：

- 第 1 轮输入：约 `system + t`
- 第 2 轮输入：约 `system + 2t`
- 第 N 轮输入：约 `system + Nt`

把 N 轮加起来，总输入量级约为 `N × system + t × (1+2+…+N)`，即**与 N² 同阶**。这就是阶段 0 反复强调的「Agent 成本平方增长」（见 C3-3）。

一个 20 步的 Agent，若每步新增 800 token，总输入会到 20 万量级——哪怕每千 token 只有几厘钱，长期、多用户跑下来也是可观的数字。

### 2.1 把「平方」摊开看

还是上面那组数（每步 800 token、20 步），逐轮累计：

| 轮次 | 本轮输入 tokens | 累计输入 tokens |
|---|---|---|
| 第 1 轮 | 800 | 800 |
| 第 5 轮 | 4,000 | 12,000 |
| 第 10 轮 | 8,000 | 44,000 |
| 第 20 轮 | 16,000 | 168,000 |

两个结论直接可读：

- **最后 5 轮（16–20）贡献了 72,000 tokens，占全部的 43%**。前面 15 轮加起来才 96,000。
- 单轮输入也在涨。第 20 轮的一次调用，输入是第 1 轮的 20 倍。

这就是为什么「把工具返回压小」的收益远大于直觉：**它不是省一次，是省后面每一次**。把每步的 800 降到 500，末轮输入从 16,000 降到 10,000，总成本下降约 37%。

## 3. 上下文预算的三笔账

| 组成 | 特点 | 能否优化 |
|---|---|---|
| system prompt | 固定、每次都发 | 能：保持稳定吃缓存（C2-5） |
| tools 定义 | 隐形固定成本 | 能：按任务类型**静态划分**工具子集（勿在单次循环内动态增删，否则打碎前缀缓存） |
| 历史消息 | 随轮数线性增长 | 能：裁剪 / 摘要（C7-2、C7-3） |
| 工具返回 | 可能巨大（查库结果、网页全文） | 能：落盘 + 摘要（C7-4） |

其中**工具返回**是最容易被忽略的「预算黑洞」：一次 `search` 返回 5000 token 的原始 JSON，模型可能只需要其中两三个字段。

一个典型的 Agent 请求，四部分的比例大致是这样（工具型 Agent、已跑十几轮）：

| 组成 | 占比 | 备注 |
|---|---|---|
| system + tools | 15–25% | 固定，但常被当成"不算钱" |
| 历史消息 | 30–40% | 其中大部分是旧的工具返回 |
| 本轮工具返回 | 25–40% | 波动最大的一项 |
| 用户输入 | 1–5% | 几乎可忽略 |

**注意第一行和第三行**：它们都不是"用户说了什么"，但加起来常常超过一半。优化上下文，本质上就是优化这两项。

## 4. 窗口上限 vs 你的可用预算

模型有**上下文窗口上限**（如 128K、200K），但**不等于**你该把它用完。用满窗口有实打实的代价：

1. **成本**：prompt tokens 线性涨。
2. **延迟**：prefill 阶段要处理全部输入（见 C2-3），输入越长首 token 越慢。
3. **质量**：模型对**中部信息**的处理能力下降（「lost in the middle」，经验现象，常被解释为注意力稀释），塞太多反而抓不住重点。

所以「预算」的第一条原则是：**能用小就别用大，能精简就别堆满。**

关于第 3 点，有个容易误读的地方：**它不是「超过某个长度就变差」，而是「关键信息落在中段时容易被忽略」**。同样的 50K 上下文，关键信息在开头和结尾时表现明显好于放在正中间。所以工程上的对策不是一味缩短，而是**把真正重要的东西放在两端**（system 里放约束、最后一条消息放当前任务），中间允许放可牺牲的细节。

## 5. 先量后裁

在动手裁剪前，先回答三个问题：

1. 现在每轮平均多少 token？system / 历史 / 工具返回各占多少？
2. 增长最快的部分是哪个？（几乎总是历史消息和工具返回）
3. 哪些内容模型**每轮都真的需要**，哪些是「历史包袱」？

没有这组数字就裁剪，等于盲切。**先埋点统计 usage（含 cached_tokens，见 C5-4），再决定裁哪里。**

### 5.1 埋点要看的最小字段集

不用一开始就上完整的可观测性体系（那是阶段 5），但下面五个字段必须记，否则后面所有讨论都是拍脑袋：

```python
def log_usage(turn: int, resp, label: str):
    u = resp.usage
    print({
        "turn": turn,                          # 第几轮 → 看增长曲线
        "label": label,                        # 哪一步（plan / tool / answer）
        "input": u.input_tokens,               # 本轮输入总量
        "cached": getattr(u, "cached_tokens", 0),  # 命中缓存的部分
        "output": u.output_tokens,
    })
```

有了 `turn` 和 `input` 就能画出增长曲线；有了 `cached` 才知道你的「省」是真省还是被缓存掩盖了（缓存降的是单价，不降 token 量）。如果 `cached` 长期接近 0，说明前缀一直在变——先别急着裁内容，去查 C7-2 讲的缓存友好排序。

### 5.2 一个反直觉的量法

想知道「哪部分真的被用到了」，可以做一个便宜的实验：**把某一类内容整体删掉，跑同一批任务，看成功率掉多少**。

- 删掉旧的工具返回 → 成功率几乎不掉 → 它确实是包袱，放心裁。
- 删掉中间某次失败的尝试记录 → 成功率明显下降 → 模型在靠它避免重复踩坑，不能简单删，要压成一句话摘要。

这个方法的成本是几十次调用，比读十篇「最佳实践」有用。**上下文管理没有通用最优解，只有你自己业务上的取舍**——而取舍只能靠这一类实验得到。

## 6. 小结

- 上下文是每次请求的「记忆重放」，成本随轮数**平方增长**。
- 平方增长的直观含义：最后几轮占总成本的大头，所以早一步压缩的收益会被后续每一轮放大。
- 预算四组成：system / tools / 历史 / 工具返回；工具返回常是黑洞。
- 窗口上限 ≠ 该用满；lost-in-the-middle 的实质是关键信息别放中段。
- 先量后裁：五个 usage 字段 + 一次「删掉看影响」的实验，比盲切可靠。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 「第 N 轮的输入 = system + 前 N-1 轮全部内容」——为什么这会带来平方增长，而不是线性？
2. 窗口上限和你的可用预算为什么不是一回事？两者差在哪里？
3. 「先量后裁」是什么意思？不量就裁会犯什么错？

<details>
<summary>参考思路</summary>

1. 每轮都要重发全部历史，第 k 轮发 k·t，累加 Σk·t 就是 n²/2 量级。放大来自「重发」这个动作，不是单轮变长。
2. 窗口上限是模型的天花板（比如 128k），可用预算是你为了成本、延迟、注意力质量而自愿留出的额度，通常远小于天花板。贴天花板跑一定又贵又慢。
3. 先统计各类内容的实际 token 占比（system / 工具 schema / 历史 / 检索片段），再决定砍谁。不量就裁，通常砍掉了最便宜的部分，留下最贵的。
