# C7-2 · 裁剪与 KV Cache：砍哪里的内容才能保命中
> 阅读约 14 分钟。目标：理清「裁哪里」和「缓存命不命中」的因果关系，做出真正省钱的裁剪。

## 1. 先回顾：缓存只认「完全相同的前缀」

阶段 0 的 C2-5 给过一条铁律：

> 跨请求的 Prompt Caching（前缀缓存），只对**从第一条消息开始、完全相同**的前缀生效。前缀一旦有任何变化，从变化点起全部失效（后面的 KV 都要重新计算）。

这条铁律直接决定裁剪该怎么做。它带来一个反直觉的结论：

**你「省 token」的裁剪，可能反而让缓存失效，最终更贵。**

## 2. 两个正交维度：追加 vs 删改

先把两件事拆开看，别混在一起：

**维度一：追加（最省，永远优先）**

- 只在**末尾追加**新内容，前缀不变 → 缓存**继续命中**。
- 这是唯一「零缓存代价」的做法。所以上下文管理的第一原则是：**能追加就追加，先别急着删。**

**维度二：删改（伤缓存，但有时必须做）**

- **删除 / 改写头部或中部**的内容，会从改动点起**破坏前缀**，缓存整体失效（最多保住 system 段）。
- 这是裁剪历史时**无法回避的代价**——不是「选错了位置」，而是「只要动了历史，就必然伤缓存」。

## 3. 一个关键的澄清：「删尾部保缓存」仅指「尾部大块」

缓存维度上，「删尾部」确实不伤前缀（前面内容没变）。但要注意两件事：

1. 历史消息里的「尾部」= **最新消息**，恰恰是语义上**最该保留**的。为了保缓存去删最新消息，是丢了西瓜捡芝麻。
2. 真正值得「在尾部动手」的，是那些**还没进入前缀的尾部大块**——最典型的是**刚拿到、还没喂回上下文的工具返回**。在它成为前缀的一部分之前就压缩它（落盘 + 摘要），**既省 token 又不伤缓存**，这才是「删尾部保缓存」的正确用法。

一句话总结：

> 「末尾追加」保命中；「删改历史」必然伤缓存；唯一「不伤缓存又能省」的，是压缩尚未进入前缀的尾部大块（工具返回）。

## 4. 正确的裁剪顺序（从省到费）

当上下文确实要裁剪时，按这个顺序来：

1. **稳定 system prompt + 固定工具定义放最前**，永不动它——这是缓存的地基。
2. **压缩「还没进入前缀的尾部大块」**：工具返回落盘，上下文只留摘要 / 关键字段（见 C7-4）。**这一步不伤缓存，性价比最高。**
3. **对早期历史做摘要**（见 C7-3），用短摘要替换一整段历史。**注意：改头部会伤缓存**，但摘要的价值是「保留信息 + 减少未来轮次 token」，用「缓存这次失效」换「后续每轮都更省」，通常划算。
4. **不得已才直接删最老的消息**。删头部伤缓存、又丢信息，是最差的一步——但比起「什么都不做等窗口爆」，它仍好过崩溃。

### 4.1 算清楚：「伤一次缓存」到底值不值

「通常划算」不是感觉，可以算。关键是分清两笔钱：

- **破坏缓存的代价** = 这一次要为**整段前缀**付全价（而不是缓存价）。这是一次性支出。
- **压缩的收益** = 后续每一轮都少发那部分 token。这是持续性收入。

设当前上下文 40,000 tokens，压缩后变 10,000，之后还剩 10 轮。缓存价按全价的 10% 计（各厂商不等，按你账单替换）。**注意必须折算成钱来比，因为命中缓存的 token 单价低得多**，直接比 token 数会得出错误结论：

| 项 | 计算（统一折算成「等效全价 token」） | 结果 |
|---|---|---|
| 不压缩，跑 10 轮 | 40,000 × 0.1 × 10 | 40,000 |
| 压缩后，跑 10 轮 | 10,000 × 0.1 × 10 | 10,000 |
| 压缩这一轮多付的钱 | 10,000 从缓存价变全价：10,000 × (1 − 0.1) | +9,000 |
| 合计 | 10,000 + 9,000 | 19,000 |
| 净省 | 40,000 − 19,000 | **21,000，约 52%** |

反过来看什么时候**不**划算：同样压到 10,000，但只剩 2 轮。

- 不压缩：40,000 × 0.1 × 2 = 8,000
- 压缩：10,000 × 0.1 × 2 + 9,000 = 11,000

**更贵了。** 所以判据是：

> 每轮省下的量 × 剩余轮数 × 缓存单价 **>** 压缩后前缀长度 × (全价 − 缓存单价)，才值得压缩。

这也解释了为什么「长任务才值得做摘要」——短对话压完就结束，一次失效的成本永远收不回来。**剩余轮数是可以估的**（任务还剩几步、用户还会追问几轮），估不出就别压。

### 4.2 缓存友好排序：把「易变的放最后」

同样一批内容，顺序不同，命中率差很多。原则只有一句：**变化频率低的往前放，变化频率高的往后放**。

```
❌ 差：每轮都变的东西夹在最前
[当前时间戳] [用户画像(每轮更新)] [system] [tools] [历史] ...

✅ 好：稳定段在前，易变段在后
[system] [tools] [历史] [本轮工具返回] [当前时间] [用户输入]
```

差的那版里，时间戳一变，**后面全部失效**——你等于每轮都在付全价。这是最常见的「缓存命中率莫名很低」的原因，而且改动成本极低，只是挪个位置。

## 5. 一个可落地的规则

```
if 上下文即将超预算:
    # 1. 先压「尚未进入前缀的尾部大块」（工具返回）—— 不伤缓存
    for tool_result in recent_large_results:
        store_full_result_to_disk(result_id)
        replace_in_context(summarize(tool_result))

    # 2. 还不够，再对「早期历史」做滚动摘要 —— 伤缓存但省未来轮次
    if still_over_budget and worth_breaking_cache(saving_per_turn, remaining_turns):
        summary = summarize(old_messages)
        replace old_messages with summary

    # 3. 最后手段：直接删最老消息 —— 伤缓存又丢信息
```

核心思想：**先压「尾部大块」（不伤缓存），再摘要「早期历史」（伤缓存但值得），最后才硬删（最差）。**

`worth_breaking_cache` 就是这个判据的函数化：**省下的钱 > 失效一次的钱**才返回 True（算法见 4.1）。写成一个具名函数而不是硬编码 `remaining_turns > 3`，是因为阈值依赖你的缓存折扣、上下文长度和任务剩余步数——**这几个数一变，阈值就变**，写死迟早错。

### 5.1 怎么验证缓存真的命中了

只看「总 token 降了」不够，因为降 token 和保缓存可能同时发生，也可能互相抵消。看这一个指标：

```
缓存命中率 = cached_tokens / input_tokens
```

- 稳定在 70% 以上 → 前缀结构基本健康；
- 长期低于 30% → 八成是排序问题（见 4.2）或每轮都在改 system；
- **某轮突然掉到 0** → 就是这一轮动了历史，属于预期内的一次性代价，不必惊慌。

把这个指标按轮次打出来，你会看到一条锯齿线：**大部分时候高位，压缩那一下掉到底再爬回来**。这条线本身就是「缓存是否被滥用」最直观的证据。

## 6. 小结

- 缓存只认完全相同的前缀；**末尾追加保命中，删改历史必然伤缓存**（从改动点起失效）。
- 「删尾部保缓存」只适用于「压缩尚未进入前缀的尾部大块」，不是让你去删最新消息。
- 伤一次缓存值不值，能算：**剩余轮数 × 每轮省下的量 > 一次全量 prefill 的额外成本**。
- 排序原则：稳定段在前、易变段在后；时间戳放最前是命中率杀手。
- 正确顺序：保 system → 压工具返回 → 摘要早期历史 → 最后才硬删。
