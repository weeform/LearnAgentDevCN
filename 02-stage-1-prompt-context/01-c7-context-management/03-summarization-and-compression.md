# C7-3 · 摘要与压缩：滚动摘要、分层摘要、结构化压缩
> 阅读约 14 分钟。目标：掌握三种压缩手法，知道各自适用场景和坑。

> **本篇只管「怎么压」**：三种压缩手法的机制与取舍。**压什么、什么绝不能压**，是阶段 3 的 C13-2 在讲——那篇站在「会话记忆该留什么」的角度，两篇一起看才完整。

## 1. 压缩的本质

压缩 = 用**更少的 token** 保留**够用的信息**。关键在「够用」二字——压掉什么、留什么，取决于下游任务需要什么。

一个贯穿的提醒：**摘要是有损的**。你省了 token，但丢掉了原文里的细节。所以任何压缩，都要给「需要原文时还能找回来」留条后路——这正是「落盘 + 引用」的意义（见 C7-4）。

## 2. 滚动摘要（rolling summary）

**做法**：对话每进行若干轮，就把「已经处理完的部分」压成一段固定长度的摘要，往后只带着摘要走。

```
system | 摘要(前20轮) | 第21轮 | 第22轮 | ...
         ↑ 每 5 轮更新一次，替换旧的摘要
```

**优点**：简单、可控，能把历史压到一个常数规模。

**坑**：
- 摘要会**逐次累积误差**（摘要的摘要会越来越失真），需要定期「回头补原文」校验。
- 摘要本身也要占 token，若历史本来就不长，摘要反而更贵。
- 替换早期（头部）历史会**破坏前缀缓存**（见 C7-2），但换来「后续每轮都更省」，通常划算。

**适用**：长对话、长任务（客服、辅导、多步骤工作流）。

### 2.1 累积误差长什么样

滚动摘要最危险的不是「压得不全」，而是**每一轮压一点的误差会复利**。示意（数字为示意值）：

| 更新次数 | 关键事实留存 | 典型失真 |
|---|---|---|
| 1 | 完整 | 只做了省略，无损 |
| 3 | 约 9 成 | 把「用户说预算 3000 左右」写成「预算 3000」 |
| 6 | 约 7 成 | 「左右」消失，「大约」被去掉，数值变成硬约束 |
| 10 | 约 5 成 | 上一轮的「待确认项」在下一轮被当成「已确认」 |

最后一行是最典型的翻车形态：**"待确认" 在传递中变成 "已确认"**。因为摘要模型倾向于把模糊状态写成明确状态——短、干净、看起来更像结论。这类错误不会报错，只会让 Agent 信心满满地做错事。

两个对抗手段：

1. **状态字段用枚举，不让模型自由措辞**（「pending / confirmed / rejected」三选一），这样"待确认"不可能漂成"已确认"。这就是下面第 4 节的结构化压缩。
2. **摘要里保留关键实体原文**：金额、日期、订单号、人名这类，要求逐字复制，禁止概括。写进摘要 prompt 即可：`金额、日期、编号必须原文照抄，不得改写或省略`。

### 2.2 摘要 prompt 该怎么写

自由发挥的「请总结以上对话」会产出漂亮但没用的东西。给它一个固定骨架：

```
把以下对话压缩为 JSON，不要输出其他内容：
{
  "facts": ["已确认的事实，每条不超过 25 字，金额/日期/编号必须原文照抄"],
  "decisions": ["已经做出的决定"],
  "open_questions": ["尚未解决的问题"],
  "user_preferences": ["用户明确表达的偏好"],
  "artifacts": ["产生的文件/结果 ID，供后续取回原文"]
}

要求：
- 只写对话中出现的信息，不得推断或补全。
- 不确定的内容放进 open_questions，不要写进 facts。
- 总长度不超过 300 字；超了优先删 facts 中的次要项。
```

三个细节都值得注意：**「不确定的进 open_questions」**防止状态漂移；**「artifacts 存 ID」**是找回原文的后路；**「超了优先删 facts」**给了模型一个明确的裁剪优先级——否则它会随机删，可能删掉最关键的一条。

## 3. 分层摘要（hierarchical summary）

**做法**：不压成一段，而是按**主题/时间**压成多层摘要，需要哪层取哪层。

```
总摘要（一句话）
├── 话题A摘要
├── 话题B摘要
└── 话题C摘要
```

**优点**：比滚动摘要**保真度更高**，支持「按需深入」。

**坑**：结构设计复杂，需要额外的「分层」逻辑（哪些消息归到哪个话题）。

**适用**：话题切换频繁的对话、知识密集场景。

### 3.1 分层摘要的真实价值：按需加载

分层摘要如果只是「摘要的摘要」，那它没比滚动摘要强多少。它真正的价值在于**允许你只加载相关的层**。

一个客服 Agent 处理了 5 个问题，用户现在回到第 2 个问题追问。此时你需要的是：

- 总摘要（知道整体聊了什么）—— 50 token
- 话题 2 的摘要 —— 150 token
- 话题 2 的原始消息 —— 按需，可能完全不加载

而滚动摘要只有一段「混在一起」的文字，你没法只取第 2 个话题——要么全带上，要么全丢。**这就是分层摘要省 token 的机制：不是压得更狠，而是加载得更准。**

代价是你需要一个「话题归属」的判断（新消息属于哪个话题、是否开新话题）。简单做法是让模型每次返回 `{topic_id, is_new_topic}`，两个字段的成本远低于它省下的量。

## 4. 结构化压缩（structured compression）

**做法**：不是让模型「自由总结」，而是**用结构化输出**把历史压成一张表 / 一个对象——只保留下游真正要用的字段。

例如一个订单处理对话，压缩成：

```json
{
  "confirmed_items": ["A x2", "B x1"],
  "open_questions": ["收货地址还没确认"],
  "decisions_made": ["同意退差价 10 元"],
  "next_action": "等待用户确认地址"
}
```

**优点**：信息密度最高，且**能直接被代码消费**（配合 C4-3 的 Schema）。这是 Agent 场景最推荐的方式——因为 Agent 的下一步决策，需要的就是这些「状态字段」，而不是整段对话原文。

**坑**：需要你先想清楚「下游到底需要哪些字段」，这本身就是设计工作。

再补一个坑：**字段一旦定死，新出现的信息就只能丢**。比如 schema 里没有 `user_sentiment`，用户第三次表达不满这件事就消失了。缓解办法是留一个 `misc: string[]` 兜底字段装「不属于任何已知字段但可能有用」的内容——它会被噪声填满，但比静默丢失好。

## 5. 三种手法的取舍

| 手法 | 保真度 | 复杂度 | 适用 |
|---|---|---|---|
| 滚动摘要 | 中 | 低 | 长对话、长任务 |
| 分层摘要 | 高 | 高 | 多话题、知识密集 |
| 结构化压缩 | 高（按需） | 中 | Agent 状态维护（推荐） |

实践里通常**混用**：结构化压缩管状态（决策、待办），滚动摘要管叙事（聊过什么），分层只在前两者都撑不住时上。

## 6. 一个反直觉的提醒

**不是所有「压缩」都划算**。若一段内容模型下一轮仍要高频引用，压成摘要反而让模型「拿不到细节」，可能答错。压缩的判据不是「它很长」，而是「它还会不会再被用到」。

- 还会反复用 → 保留原文（或结构化保留关键字段）。
- 已经处理完、不会再用 → 压掉。

判断「还会不会用」有个便宜的近似：**看这段内容之后被引用过几次**。引用 0 次且已过 3 轮，基本可以压；引用 2 次以上，说明它是当前任务的核心，压了必然掉质量。

## 7. 小结

- 三种压缩：滚动摘要（简单）、分层摘要（保真）、结构化压缩（Agent 首选）。
- 摘要的累积误差会复利，最典型的翻车是「待确认」漂成「已确认」；用枚举字段 + 原文照抄来防。
- 分层摘要的价值是「按需加载」，不是「压得更狠」。
- 摘要是有损的，永远给「找回原文」留后路（artifacts 存 ID）。
- 压缩判据是「还会不会被用到」，不是「长不长」。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 压缩的本质是「丢掉什么」？为什么不能靠一句「帮我总结一下」了事？
2. 滚动摘要和分层摘要各自的失效模式是什么？
3. 为什么压缩完的摘要要放在「稳定前缀」里，而不是每轮重新生成一段？

<details>
<summary>参考思路</summary>

1. 本质是有损信息取舍：必须明确哪些事实绝不能被丢（订单号、金额、约束、待办），其余才可概化。不指定保留项，模型会丢掉你后面要用的关键字段。
2. 滚动摘要会随轮次累积漂移、早期细节层层丢失；分层摘要保真度高但归类逻辑复杂，容易把跨话题的上下文切错。
3. 每轮重新生成摘要意味着前缀天天变，缓存全失效，而且摘要内容不稳定会导致行为漂移。正确做法是压缩后固化成文本块、放在稳定位置。
