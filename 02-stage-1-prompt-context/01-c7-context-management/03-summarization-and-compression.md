# C7-3 · 摘要与压缩：滚动摘要、分层摘要、结构化压缩
> 阅读约 12 分钟。目标：掌握三种压缩手法，知道各自适用场景和坑。

## 1. 压缩的本质

压缩 = 用**更少的 token** 保留**够用的信息**。关键在「够用」二字——压掉什么、留什么，取决于下游任务需要什么。

一个贯穿的提醒：**摘要是有损的**。你省了 token，但丢掉了原文里的细节。所以任何压缩，都要给「需要原文时还能找回来」留条后路——这正是「落盘 + 引用」的意义（见 C7-4）。

## 2. 滚动摘要（rolling summary）

**做法**：对话每进行若干轮，就把「已经处理完的部分」压成一段固定长度的摘要，往后只带着摘要走。

```
system | 摘要(前20轮) | 第21轮 | 第22轮 | ...
         ↑ 每 5 轮更新一次，替换旧的摘要
```

**优点**：简单、可控，能把历史压到一个常数规模。

**坑**：
- 摘要会**逐次累积误差**（摘要的摘要会越来越失真），需要定期「回头补原文」校验。
- 摘要本身也要占 token，若历史本来就不长，摘要反而更贵。
- 替换早期（头部）历史会**破坏前缀缓存**（见 C7-2），但换来「后续每轮都更省」，通常划算。

**适用**：长对话、长任务（客服、辅导、多步骤工作流）。

## 3. 分层摘要（hierarchical summary）

**做法**：不压成一段，而是按**主题/时间**压成多层摘要，需要哪层取哪层。

```
总摘要（一句话）
├── 话题A摘要
├── 话题B摘要
└── 话题C摘要
```

**优点**：比滚动摘要**保真度更高**，支持「按需深入」。

**坑**：结构设计复杂，需要额外的「分层」逻辑（哪些消息归到哪个话题）。

**适用**：话题切换频繁的对话、知识密集场景。

## 4. 结构化压缩（structured compression）

**做法**：不是让模型「自由总结」，而是**用结构化输出**把历史压成一张表 / 一个对象——只保留下游真正要用的字段。

例如一个订单处理对话，压缩成：

```json
{
  "confirmed_items": ["A x2", "B x1"],
  "open_questions": ["收货地址还没确认"],
  "decisions_made": ["同意退差价 10 元"],
  "next_action": "等待用户确认地址"
}
```

**优点**：信息密度最高，且**能直接被代码消费**（配合 C4-3 的 Schema）。这是 Agent 场景最推荐的方式——因为 Agent 的下一步决策，需要的就是这些「状态字段」，而不是整段对话原文。

**坑**：需要你先想清楚「下游到底需要哪些字段」，这本身就是设计工作。

## 5. 三种手法的取舍

| 手法 | 保真度 | 复杂度 | 适用 |
|---|---|---|---|
| 滚动摘要 | 中 | 低 | 长对话、长任务 |
| 分层摘要 | 高 | 高 | 多话题、知识密集 |
| 结构化压缩 | 高（按需） | 中 | Agent 状态维护（推荐） |

## 6. 一个反直觉的提醒

**不是所有「压缩」都划算**。若一段内容模型下一轮仍要高频引用，压成摘要反而让模型「拿不到细节」，可能答错。压缩的判据不是「它很长」，而是「它还会不会再被用到」。

- 还会反复用 → 保留原文（或结构化保留关键字段）。
- 已经处理完、不会再用 → 压掉。

## 7. 小结

- 三种压缩：滚动摘要（简单）、分层摘要（保真）、结构化压缩（Agent 首选）。
- 摘要是有损的，永远给「找回原文」留后路。
- 压缩判据是「还会不会被用到」，不是「长不长」。
