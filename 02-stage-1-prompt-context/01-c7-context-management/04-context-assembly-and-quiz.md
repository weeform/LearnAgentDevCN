# C7-4 · 上下文装配与裁剪策略
> 阅读约 15 分钟。目标：产出一份**自己的、有明确规则的**上下文装配 + 裁剪策略。这是本课的交付物。

## 1. 上下文装配（Context Assembly）

装配 = 每次请求前，决定**把什么放进上下文、按什么顺序放**。好的装配遵循三条：

1. **稳定在前，变动在后**：system + 固定工具定义永远在最前（吃缓存）；每轮新增内容往后追加。
2. **按需加载**：不是把所有历史全塞进去，而是只放「这一轮决策需要的」。多余内容既是成本又是噪声。
3. **外部内容隔离**：检索来的文档、网页、工具返回，用明确标记框住（`<document>` / `<tool_result>`），既防注入（见 C8），也让模型知道「哪部分是数据、哪部分是任务」。

## 2. 一份裁剪策略模板（可直接改）

```
## 上下文裁剪策略 v1

### 预算
- 单次请求输入上限：____ token（约为窗口上限的 30–50%，预留输出空间）
- 触发裁剪的阈值：达到上限的 ____% 时开始裁剪

### 裁剪顺序（先压尾部大块，最后才碰头部）
1. 工具返回 > ____ token 时：原始结果落盘（存引用），上下文只留摘要/关键字段
2. 历史消息累计 > ____ token 时：对「已处理完」的部分做滚动/结构化摘要
3. 仍超预算：按「最不相关优先」删除旧消息（接受本次缓存失效）

### 保底
- 永不裁剪：system prompt、任务目标、用户最新一条输入
- 任何被摘要替换的原文，都必须能通过引用找回
```

这份模板的价值不在「填空」，而在**逼你显式写下规则**——有了规则，裁剪才从「感觉」变成「可复现」（三条暗线之二）。

## 3. 工具返回处理：最该先做的一步

工具返回是预算黑洞（见 C7-1），处理它性价比最高。标准做法是「**落盘 + 引用 + 摘要**」：

```
原始结果 → 存到磁盘/对象存储，分配一个 result_id
         → 上下文里只放：{result_id, 摘要, 关键字段}
         → 模型后续需要原文时，用「取回工具」按 result_id 加载
```

这样上下文里是一个**稳定的短引用**，而不是一大坨原始数据；需要原文时再「按需加载」，符合装配原则。

## 4. 三条暗线在此汇聚

| 暗线 | 在 C7 的体现 |
|---|---|
| 成本意识 | 压工具返回、摘要历史，都是直接省 prompt tokens |
| 可复现性 | 裁剪策略显式成文，同样的输入走同样的裁剪 |
| 上下文预算 | 预算 + 阈值 + 裁剪顺序，全部围绕「这段内容值不值得占上下文」 |

## 5. 自测（7 道）

> 答对 5 道以上，本课通过。

1. 为什么「第 N 轮输入 ≈ system + 前 N-1 轮全部内容」？这导致成本怎么增长？
2. 窗口上限为什么「不等于」你该用的预算？（至少说两个代价）
3. 缓存只对什么前缀生效？删头部和删尾部各有什么影响？
4. 为什么「砍掉最老的几条」是最差策略？
5. 正确的裁剪顺序是什么？
6. 工具返回的「落盘 + 引用 + 摘要」三步分别解决什么问题？
7. 压缩的判据是「长不长」还是「还会不会被用到」？为什么？

### 答案要点

1. API 无状态，每轮全量重发历史；总输入与轮数平方同阶（平方增长）。
2. 成本线性涨、prefill 变慢首 token 延迟、中部信息注意力稀释（lost in the middle）。
3. 从首消息起逐 token 完全相同的前缀；删尾部前缀不变仍命中，删头部前缀变、缓存全废。
4. 既让缓存整体失效，又可能丢掉关键上下文。
5. 保 system → 压工具返回 → 摘要早期历史 → 最后才删头部。
6. 落盘保原文、引用保可找回、摘要省上下文 token。
7. 「还会不会被用到」；因为压缩有损，反复要用的内容压掉会答错。
