# C8-3 · 防御清单：白名单、权限与人工确认
> 阅读约 13 分钟。目标：落地一份「即使被注入也做不了坏事」的权限层防御清单。

## 1. 为什么权限层才是真正的底线

C8-2 讲过：prompt 技巧堵不死注入。那安全的真正来源是什么？答案是——**让模型即使被诱导，也没有能力造成伤害**。

这属于「最小权限」（least privilege）原则：给 Agent 的能力，恰好够它完成任务，多一分都不给。

换个角度说：**前面两层在跟模型"商量"，这一层是代码在"拦"**。商量可能失败，拦不会。所以判断一个 Agent 的安全性，不看它的 prompt 写得多严，而看**它的工具列表里有什么、参数能不能被校验**。

## 2. 工具调用白名单

**做法**：把工具分成「安全 / 敏感」两类，敏感工具不直接对模型开放。

| 类别 | 例子 | 处理 |
|---|---|---|
| 安全（只读） | 查库、检索、计算 | 直接开放给模型 |
| 敏感（有副作用） | 发邮件、下单、删数据、转账 | 默认**不暴露**，或走人工确认 |

关键动作：**从工具列表的源头就控制**——模型只能调用「你放进 tools 数组」的工具。一个危险工具根本不放进上下文，模型连「尝试调用」的机会都没有。这是最可靠的一条。

### 2.1 按「可逆性 × 影响面」分级

二分太粗，实际用四象限更有操作性：

| | 影响面小 | 影响面大 |
|---|---|---|
| **可撤销** | 写草稿、加标签 → 直接开放 | 批量改状态 → 开放但限批（如单次 ≤ 20 条） |
| **不可撤销** | 发单条消息 → 需确认 | 转账、退款、删库 → **不暴露给模型**，只允许「提出申请」 |

注意右下角那一格的处理方式：**不是"加个确认就行"，而是彻底不让模型碰**。因为一旦工具在 tools 里，模型就可能在多轮对话中被逐步说服；而"提出申请"是个纯数据动作，申请单交给人处理，模型全程没有执行权。

「限批」这一行也值得说：批量操作的风险不在单次，而在**被循环调用**。加一个 `count <= 20` 的硬限制，就能把"一次误操作"和"一次灾难"区分开。

## 3. 敏感操作人工确认（HITL）

对「必须暴露、但有副作用」的操作，加一道**人工闸门**：

- 模型输出「意图」→ **暂停，等人类批准** → 才真正执行。
- 典型实现：`tool_choice` 强制模型先调一个 `request_approval` 工具，人点了「同意」，副作用工具才被调用（见 C1-4 的 tool_choice 用法）。

这条把「模型自主行动」变成「模型建议 + 人拍板」，是最直接的风险闸门。

### 3.1 确认框里必须有什么

HITL 最容易做成摆设：弹一个"是否同意执行？"，用户看都不看就点确定。要让确认有意义，确认框必须显示**模型自己决定不了的信息**：

| 要素 | 例子 | 为什么必要 |
|---|---|---|
| 具体动作 | 「向 zhang@xx.com 发一封邮件」 | 不能只说"执行工具"，要展开成人能判断的话 |
| 关键参数原文 | 收件人、金额、目标 ID | 这是人唯一能核对的地方 |
| 不可撤销提示 | 「此操作不可撤回」 | 醒目程度决定用户会不会看 |
| 触发原因 | 「根据网页 example.com 的建议」 | 暴露注入痕迹：人一看来源可疑就会拒 |

最后一行是关键设计：**把「这条指令从哪来」写进确认框**。如果是模型自己检索到的网页建议，人看到"根据某不知名网站的建议"就会本能拒绝——这是最便宜、最有效的注入拦截点，且完全不依赖模型判断。

### 3.2 一个常见错误：确认在错误的层

```python
# ❌ 错误：模型调了工具，你执行完再"确认"
result = send_email(to, body)
ask_user("邮件已发送，是否同意？")     # 毫无意义

# ✅ 正确：先拦，再执行
if not await request_approval(action="send_email", params={"to": to, "body": body}):
    return "用户拒绝，未执行"
result = send_email(to, body)
```

差别看起来低幼，但真实系统里"先执行后提示"并不罕见——尤其当工具是异步的、或者确认被做成了 UI 层的 toast。**确认必须发生在副作用之前，且拒绝路径要真的能中断执行**（不是捕获异常后继续）。

## 4. 参数白名单与校验

即便模型能调某工具，也要**限制它传什么参数**：

- 金额、收件人、URL 这类关键参数，在**代码层**二次校验（范围、白名单、格式），不能只信模型的输出。
- 例如「发邮件」工具：收件人必须是通讯录白名单内的地址，正文里的外链一律剥离。

参数校验要防的不只是"模型乱填"，还有**注入后的定向利用**：

| 攻击意图 | 校验手段 |
|---|---|
| 把数据发到攻击者邮箱 | 收件人白名单（域名 + 具体地址） |
| 通过 URL 参数外带数据 | 域名白名单 + 禁止 query 里带长随机串 |
| 构造超出业务范围的金额 | 上下限 + 与订单原始金额比对 |
| 用 `../` 或绝对路径读敏感文件 | 路径规范化后校验是否在允许目录内 |
| SQL 拼接 | 参数化查询（这条是老规矩，但 Agent 场景常被忘） |

最后一条值得强调：Agent 生成的 SQL 看起来"人模人样"，很容易让人放松警惕直接拼字符串。**凡是模型生成的、要进数据库的东西，都按不可信输入处理**。

## 5. 输出过滤

模型输出进入下一环节（展示给用户、发给第三方、执行）前，做检查：

- 是否包含**要泄露的敏感信息**（内部密钥、他人隐私、对话历史）。
- 是否包含**可疑外链 / 指令片段**。

这是「事后兜底」，不能替代前面几层，但能拦住一部分漏网之鱼。它的边界是：**只能拦「已知模式」**——对从未见过的新泄露方式、绕过规则的对抗样本，规则过滤往往失效，所以不能把它当成最后防线。

具体到「图片外带」这种泄露（C8-1 形态二），输出过滤要能识别：**模型生成的 Markdown 图片 URL 里带查询参数**。这条规则很具体，但就是它能挡住一整类泄露——只要你的渲染层执行了 `![](https://...)`，数据就已经出去了，来不及再拦。

## 6. 一份可落地的防御清单

- [ ] 危险工具（副作用）默认不暴露给模型
- [ ] 敏感工具走人工确认（HITL）闸门，**确认在副作用之前**
- [ ] 确认框显示具体动作、关键参数原文、来源、不可撤销提示
- [ ] 关键参数在代码层二次校验（白名单 / 范围 / 格式）
- [ ] 批量操作有数量硬上限
- [ ] 外部内容做隔离标记 + 「视为数据」声明（C8-2）
- [ ] 外部内容入口做基础清洗（去控制字符、限长）
- [ ] 模型输出经「敏感信息 / 外链」过滤后再流出
- [ ] 模型生成的 Markdown 图片链接需重写或拦截
- [ ] 记录完整的 trace 与工具调用日志（便于事后审计，见阶段 5）

## 7. 小结

- 最小权限：给 Agent 的能力恰好够用，多一分都不给。
- 工具按「可逆性 × 影响面」分级：不可撤销 + 大影响面的，直接不给执行权。
- HITL 的意义全在**确认框显示什么**：参数原文 + 来源，比"是否同意"有用得多。
- 白名单（工具 / 参数）+ 人工确认 + 输出过滤，是真正的安全底线。
- prompt 防御降噪，权限层兜底，两者缺一不可。
