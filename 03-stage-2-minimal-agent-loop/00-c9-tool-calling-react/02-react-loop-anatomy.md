# C9-2 · ReAct 三段式：Thought / Action / Observation
> 阅读约 10 分钟。目标：理解 ReAct 的循环结构，以及「让模型先想」为什么有效。

## 1. ReAct 是什么

ReAct（Reasoning + Acting）把一次 Agent 决策拆成三段，循环往复：

```
Thought（想）    → 我该做什么、为什么
Action（做）     → 调用某个工具，带参数
Observation（看）→ 工具返回了什么
```

这三段串起来就是：

```
Thought: 用户想知道北京天气，我需要先查。
Action:  get_weather("北京")
Observation: {"city":"北京","temp":18,"condition":"晴"}

Thought: 拿到了温度，可以回答用户了。
Answer:  北京今天晴，18 度。
```

## 2. 为什么「先想」有用

核心原因是**把一个复杂任务，拆成一串小的、可验证的步骤**（这正是 C6-4 里 CoT 有效的那类任务）。每一步：

1. **Thought** 强制模型在动手前**明确当前状态和下一步意图**——减少「凭感觉乱调工具」。
2. **Action** 把意图变成**具体、可执行**的工具调用。
3. **Observation** 给模型**真实的反馈**，而不是让它继续「脑补」。

三者形成闭环：**想 → 做 → 看 → 再想**。模型的每一次「想」，都建立在真实环境反馈之上，而不是一次性的自由发挥。

## 3. 两种实现形态

> 先补一句出处：严格说，ReAct 论文（Yao et al., 2022）的原始形态就是下面「形态 B」的文本交织。工程界现在习惯把「用 tool_calls 驱动的循环」也叫「ReAct 循环」，这是**借名**——核心思想（想 → 做 → 看 → 再想）一致，只是「想」从显式文字变成了模型内部隐含。本课沿用工程界的宽泛叫法。

**形态 A：原生 tool_calls（推荐）**

直接靠模型的 function calling 能力。模型内部隐含了「想」，你拿到的 `tool_calls` 就是「做」。这种实现最简单、最稳（见 C9-3）。

**形态 B：纯文本 ReAct**

不依赖 function calling，让模型**用文字**输出 `Thought: ... / Action: ... / Observation: ...`，你用正则解析。适合极老的模型或教学演示，但**脆弱**——解析出错、格式漂移是常态。生产环境一律优先形态 A。

本课用**形态 A**（C9-3 的代码即如此）；第 4 节讲「显式 Thought」这个可选增强，需要时再手动加。

## 4. 显式 Thought 怎么加

原生 tool_calls 不暴露「思考」，但可以在 system prompt 里要求模型**先输出一段文字想法，再调用工具**。

注意区分两种「思考」，别混为一谈：

- **显式 Thought**：你在 prompt 里要求、模型以普通文本输出的想法，可自由改写、可控。
- **推理模型的隐式 reasoning tokens**：模型内部扩展思考（见 C1-1 的 `reasoning_effort`），通常不直接暴露、不可改写。

本节讲的是第一种。

```
在调用工具前，先用一句话说明你这一步要做什么、为什么。
```

代价是**多花 token**（每轮多一段想法）。对复杂任务值得，对简单任务就是浪费——这和 C6-4 的 CoT 取舍是同一个判断。

## 5. Observation 的质量决定循环质量

Observation 是模型「看世界」的唯一窗口。工具返回要是**含糊、超长、报错不清**，模型下一步就会跑偏。所以：

- 工具返回要**结构化、精简、带明确状态**（成功 / 失败 / 数据）。
- 报错要**回传**给模型（不是吞掉），让它有机会自我修正——详见 C11-2。

## 6. 小结

- ReAct = Thought → Action → Observation 循环，把大任务拆成可验证的小步。
- 原生 tool_calls 是生产首选；纯文本 ReAct 脆弱，只用于教学。
- 「先想」有用，但要按需加，别为简单任务付 token。
