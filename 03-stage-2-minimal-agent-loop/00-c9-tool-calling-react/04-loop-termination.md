# C9-4 · 循环终止条件：让循环可靠地停下来
> 阅读约 16 分钟。目标：设计出「该停就停、绝不失控」的终止条件。

## 1. 终止条件的本质

Agent 循环的终止，不是一个点，而是一组**必须覆盖所有出口**的分支。漏掉任何一个，循环要么提前断（任务没做完），要么永远跑（烧钱）。

一条请求结束，你拿到的 `finish_reason`（见 C1-3）就是第一个方向盘：

| `finish_reason` | 含义 | 循环该怎么走 |
|---|---|---|
| `stop` | 模型正常结束（给了最终答案） | **终止，返回内容** |
| `tool_calls` | 模型要调工具 | 执行工具，**继续** |
| `length` | 输出被截断 | **终止并报错**，别硬解析 |
| `content_filter` | 被安全过滤 | **终止**，给兜底话术 |

## 2. 终止的三道防线

**第一道：模型主动停止（`stop`）**

模型不再输出 `tool_calls`，直接给文本——这是最自然的终止。信任它，但要防「模型该调工具却提前停了」，靠第二道兜底。

**第二道：最大步数（`MAX_STEPS`）**

无论模型多「上头」，步数一到就强制停。这是**死循环的物理保险**。

- 设多少？看任务的正常步数，取 2–3 倍。单步工具调用任务一般 8–12 步足够；太大会白烧钱，太小会截断正常任务。
- 到了上限怎么办？**不要假装成功**。明确返回「未完成」，并附上已执行的步骤（trace），让人判断。

**第三道：明确停止信号（可选增强）**

给模型一个「显式宣布完成」的手段。常见做法是定义一个 `submit_final_answer` 工具，或让模型输出特定标记。好处是**终止意图更明确**，坏处是**多一次调用开销**。生产里通常用「原生 stop + 最大步数」就够，停止信号在需要严格流程时再加。

### 2.1 模型也会「停错地方」：两种假终止

第一道防线最容易被信任过度。实际跑起来，模型主动停的时候有两种是「假停」：

**提前终止**——模型回了「已完成」，但关键工具根本没调。典型如「查了库存就直接说能发货」，跳过了「扣减库存」那一步。它不是在骗你，是**把计划当成了结果**。

**格式终止**——输出一段看起来很像结论的文本，实际是「接下来我打算……」的复述。用户读起来像答复，程序判定为 `stop`，任务其实没开始。

两者的共同点：**`finish_reason` 都是正常的 `stop`**。所以单看 `finish_reason` 判不出来，得再加一条**业务侧的完成判据**——比如「必须存在一次成功的 `issue_refund` 调用」。有这条判据，假终止就变成「未完成」，走第二道或少步重试。

### 2.2 为什么只数步数不够

步数是最粗的计量单位：同样 8 步，一步可能只花 300 token（查天气），也可能花 3 万（把整份合同塞回上下文）。**步数管不住钱**，尤其在工具返回很大的场景（见 C13-3 的预算黑洞）。

## 3. 预算型终止：三个额度，不止步数

生产里真正有效的终止条件通常是**三个额度独立生效、谁先到谁触发**：

| 额度 | 计量 | 典型阈值 | 触发后 |
|---|---|---|---|
| 步数 | 循环次数 | 正常步数 × 2–3 | 收口，标注「未完成」 |
| token | 累计 input + output | 单任务预算的 80% 预警、100% 硬停 | 收口或降级到便宜模型 |
| 墙钟时间 | 从开始到现在 | 用户能忍的上限（常是 60–120 秒） | 收口，返回已有结果 |

三者必须**同时检查**，而不是只在上限那一刻查。一个够用的写法是在每轮循环开头统一检查：

```python
def should_stop(state, budget):
    if state.steps >= budget.max_steps:                 return "limit"
    if state.tokens_used >= budget.max_tokens:          return "budget"
    if time.time() - state.started_at > budget.max_sec: return "timeout"
    return None
```

注意最后返回的是**原因**而不是布尔值。原因要一路传到返回体里（见第 6 节），否则事后分不清「它做完了」和「它被掐断了」。

## 4. 停不下来的四种真实形态

「死循环」这个词太笼统，实际有四类，检测手段各不相同：

| 形态 | 长什么样 | 检测方法 |
|---|---|---|
| 原地打转 | 同样的工具、同样的参数，调了 3 次以上 | 对 `(工具名, 归一化后的参数)` 取哈希计数，超阈值即触发 |
| 参数抖动 | 每次参数差一点点（`2024-01-01` → `2024-01-02`） | 对同工具连续调用做相似度判断，≥90% 视为重复 |
| 反复确认 | 反复问用户同一个问题 | 记录已问过的问题，重复即停 |
| 重规划循环 | 每隔几轮就「重新梳理一遍任务」 | 连续两次 plan 文本相似度超阈值即停 |

第一类是绝大多数，也最好抓：**用参数哈希去重**，不需要模型配合。第二类容易漏——因为参数确实不同，看起来像在推进，实际是在日期、页码、偏移量上反复横跳。

这四种都属于「模型认为自己在推进、实际没有」。检测到之后不要直接抛错，正确做法是**把重复信号回传给模型**（见 C11-2）：「你已经用相同参数调过 3 次，结果一样，请换方法或直接回答」。很多时候它换个思路就出来了。

## 5. 四个易漏的边界

1. **`length` 截断**：输出没写完。此时 `msg.content` 是残缺的，**绝不能当最终答案返回**，也不能 `json.loads` 半截 JSON。正确做法：提高 `max_completion_tokens` 重试，或压缩输出。
2. **空 `tool_calls` 又无 content**：某些模型可能返回「既无工具调用、也无文本」。要当异常分支处理，避免 `return None` 污染下游。
3. **工具调用失败后的终止**：工具连续报错 N 次还没修好，就该**主动终止并降级**（报错回传策略见 C11-2），而不是让模型无限重试。
4. **并行调用有依赖**：若多个 `tool_calls` 之间有先后依赖，强行并行会得到错误结果（见 C1-4）。必要时关掉 `parallel_tool_calls` 或拆成多轮。

## 6. 终止之后：怎么把半成品交出去

终止条件写对了，下一个问题才出现：**被掐断的任务，返回什么？**

直接抛异常最省事，也最浪费——用户丢掉已经查到的信息，还得从头再问一遍。合理的返回体长这样：

```python
{
  "status": "partial" | "done",
  "reason": "stop" | "limit" | "budget" | "timeout" | "error",
  "answer": "已确认 A 供应商 3 天内可发货，B 供应商未回复",   # 已有的结论，哪怕不完整
  "pending": ["确认 B 供应商库存", "生成采购单"],              # 还差什么
  "steps": 12,
  "trace_id": "...",
}
```

三个要点：

- **`reason` 必须枚举**，不要只给 `success: false`。「被预算掐断」和「工具报错」的处理方式完全不同，前者加钱就行，后者要修。
- **`answer` 给已有结论**，`pending` 给未完成项。这两项分开，用户才知道能不能凑合用。
- **`trace_id` 带上**，失败任务的价值一半在复盘（见 C11-5 的失败复盘作业）。

## 7. 一份终止条件自检清单

- [ ] `stop` → 返回最终答案（且通过业务侧完成判据）
- [ ] `tool_calls` → 执行 + 继续
- [ ] `length` → 报错，不硬解析
- [ ] `content_filter` → 兜底话术
- [ ] 步数上限 → 强制停 + 报未完成 + 附 trace
- [ ] token 预算 → 同样收口，reason 记 `budget`
- [ ] 墙钟超时 → 收口，返回已有结果
- [ ] 重复调用检测 → 回传信号让模型换路子
- [ ] 连续失败 N 次 → 主动终止 + 降级
- [ ] 空输出 / 异常返回 → 有兜底分支
- [ ] 返回体带 `reason` 与 `pending`

## 8. 小结

- 终止条件要**覆盖所有 finish_reason 出口**，一个都不能漏。
- 三道防线：模型主动停 → 最大步数 → 停止信号；但第一道会出现「假终止」，需要业务侧完成判据兜底。
- 只数步数管不住钱，**步数 / token / 时间三个额度要各自独立生效**。
- 死循环有四种形态，最难抓的是「参数抖动」，用参数哈希和相似度判断，别指望模型自觉。
- 掐断之后**要给半成品**：`status` + `reason` + `answer` + `pending` + `trace_id`。
