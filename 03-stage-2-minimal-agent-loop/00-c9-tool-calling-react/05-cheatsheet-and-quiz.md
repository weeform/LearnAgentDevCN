# C9-5 · 工具调用与 ReAct 速查表与自测
> 阅读约 10 分钟。这一篇把 C9 压成能查、能自测的东西。

## 1. 一轮工具往返速查

```
messages 变化：
  system, user
→ + assistant(tool_calls)      # 模型表达调用意图
→ 执行工具（你的代码）
→ + tool(tool_call_id, result) # 结果回填，id 必须对上
→ 再次请求
```

- `tool` 消息是**你的代码**塞进去的，别漏。
- 并行调用：按 `tool_call_id` 一一对应；流式 `arguments` 按 index 累加再 `json.loads`。

### 四种角色，谁写的、能不能改

| 角色 | 谁写 | 循环里能不能改 | 常见错误 |
|---|---|---|---|
| `system` | 你 | 不建议每轮改（破坏前缀缓存，见 C7-2） | 把每轮变的参数塞进 system |
| `user` | 用户 / 你的代码 | 只追加 | 把工具结果塞进 user（会丢 `tool_call_id`） |
| `assistant` | 模型 | 原样带回 | 手动改写模型输出，导致下一轮对不上 |
| `tool` | **你的代码** | 只追加，必须紧跟对应 `assistant` | 漏塞、`id` 对不上、一条 `assistant` 只回了一半 |

## 2. ReAct 三段式

`Thought（想）→ Action（做）→ Observation（看）→ 再想`

- 原生 `tool_calls` 是生产首选；纯文本 ReAct 脆弱，只用于教学。
- 显式 Thought 按需加，别为简单任务付 token。
- 一条判断：**中间步骤能被验算就写代码，不能被验算才交给模型想**（同 C6-4 的 CoT 判据）。

## 3. 终止条件速查

| 信号 | 动作 |
|---|---|
| `finish_reason=stop` | 返回最终答案（先过业务完成判据） |
| `finish_reason=tool_calls` | 执行 + 继续 |
| `finish_reason=length` | 报错，不硬解析 |
| 步数上限 | 强制停 + 报未完成 + 附 trace |
| token / 时间超预算 | 同样收口，`reason` 记 `budget` / `timeout` |
| 连续失败 N 次 | 主动终止 + 降级 |
| 参数哈希重复 3 次 | 回传「你已重复」信号，让它换路子 |

## 4. 症状 → 病灶对照表

调试时先按现象查，比从原理倒推快得多：

| 症状 | 大概率病灶 | 回哪篇 |
|---|---|---|
| 模型不调工具，直接答 | 描述里没写「什么时候用」 | C10-2 |
| 调了工具但参数缺字段 | 参数描述为空 / schema 太松 | C10-2、C10-3 |
| `id` 对不上，报 400 | `tool` 消息没回全或顺序错 | 本篇 §1 |
| 第二轮开始胡编工具结果 | 工具结果没回填，模型自己补 | C11-2 |
| 同样的调用反复出现 | 没做重复检测，或错误没回传 | C9-4 §4 |
| 输出一半就断了 | `length` 被当正常结束 | C9-4 §5 |
| 每次跑结果都不一样 | `temperature` 没降到 0 | C1-2 |

## 5. 五个高频 bug

1. **把工具结果塞进 `user`**：语义上像「用户说了这句话」，模型会当成用户提供的背景，`tool_call_id` 也丢了，下一轮直接报错。
2. **一条 `assistant` 只回了一个 `tool`**：并行调用两个工具只回一个，请求直接被拒。
3. **`arguments` 先 `json.loads` 再累加**：流式下每片都是半截 JSON，必须先拼字符串再解析（见 C4-2）。
4. **用 `content` 判终止**：`content` 非空不代表任务完成，见 C9-4 §2.1 的假终止。
5. **循环里重建 messages**：每轮从零拼一遍，前缀变了，缓存全失效——正确做法是追加。

## 6. 自测（10 道）

> 答对 7 道以上，本课通过。

1. 一轮工具调用的消息数组要经历哪几步？哪条消息是「你的代码」塞进去的？
2. 并行返回两个工具调用时，回填结果靠什么保证不串？
3. 为什么生产里优先用原生 `tool_calls` 而不是纯文本 ReAct？
4. ReAct 三段式里，Observation 的作用是什么？为什么它决定循环质量？
5. `finish_reason=length` 时为什么不能把 `msg.content` 当最终答案？
6. 最大步数设成「很大」会有什么问题？到了上限该怎么做？
7. 为什么 Agent 循环要用 `temperature=0` 这一档采样？
8. 模型回了「已完成」但关键工具没调，这属于哪一类问题？靠什么兜底？
9. 流式返回的 `arguments` 为什么不能边收边 `json.loads`？
10. 把工具结果写进 `user` 消息会引发什么连锁问题？

### 答案要点

1. system/user → assistant(tool_calls) → 执行 → tool(result) → 再请求；`tool` 消息是代码塞的。
2. `tool_call_id` 与结果一一对应，数量一致。
3. 原生 tool_calls 稳定、各家支持一致；纯文本 ReAct 靠正则解析，格式漂移、解析出错是常态。
4. 它是模型「看世界」的唯一窗口，反馈真实环境结果；含糊/超长/报错不清会带偏下一步。
5. 输出被截断，content 是残缺的，返回会污染下游。
6. 白烧钱、浪费步数预算；到上限应明确报「未完成」并附已执行步骤，不要假装成功。
7. 追求可复现，采样走稳定档（见 C1-2），避免循环路径每次漂移。
8. 假终止（把计划当结果）。靠业务侧完成判据兜底：必须存在某次成功的工具调用才算完成。
9. 流式碎片是半截 JSON，逐片解析必然抛错；要先按 index 拼成完整字符串再解析（C4-2）。
10. 丢掉 `tool_call_id` 导致下一轮请求非法；模型还会把工具结果误读成用户提供的信息，产生新的幻觉。

C9 结课。下一门 C10 讲「工具设计」：粒度、命名、描述、参数校验——因为工具描述质量直接决定模型调用成功率。
