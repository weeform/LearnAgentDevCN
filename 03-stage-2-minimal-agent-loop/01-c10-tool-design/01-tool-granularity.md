# C10-1 · 工具粒度：一个工具该做多少事
> 阅读约 10 分钟。目标：掌握「拆到多细」的判断力——这是工具设计的第一个决策。

## 1. 粒度的两难

工具粒度，就是「一个工具封装多少能力」。两端各有代价：

| 倾向 | 表现 | 问题 |
|---|---|---|
| 太粗 | 一个 `do_everything` 工具包办所有 | 参数爆炸、模型难选、难复用、难测试 |
| 太细 | 每个字段一个工具 `get_name` / `get_age` | 模型要调 N 次才能完成一件事，轮次多、贵、易断 |

**目标是在两端之间，找到「一次调用恰好完成一个语义完整的动作」。**

## 2. 判断标准：一个动词 + 一个对象

好的粒度，通常能描述成「**一个动词 + 一个明确对象**」：

- ✅ `search_weather(city)` —— 查天气，语义完整。
- ✅ `save_note(content)` —— 存笔记，语义完整。
- ❌ `handle_everything(query)` —— 对象不明确。
- ❌ `get_temperature_unit()` —— 太细，是 `search_weather` 的一个字段。

**经验法则**：如果一个工具必须由另一个工具「紧接着补一刀」才能算完成，说明拆得太细了。

## 3. 三个具体信号

出现以下信号，考虑调整粒度：

1. **模型频繁「连环调用」**：为了一个目标连调 3–5 个工具，说明可合并。
2. **参数里塞「功能开关」**：`tool(mode="query"|"update"|"delete")` 这种「一个工具三种行为」，本质是三个工具强行塞一起——模型容易选错 mode。
3. **描述写不下边界**：工具 description 越写越长、要解释一堆「支持什么不支持什么」，通常意味着它承担了过多职责。

## 4. 粒度与成本的关系（三条暗线之一）

粒度直接决定**轮次**，而轮次直接决定**成本**（见 C7-1 的平方增长）：

- 太细 → 轮次多 → 历史消息涨得快 → 成本平方增长。
- 太粗 → 单次参数多、返回大 → 每轮 token 也涨。

所以粒度不是「怎么好看」，而是「怎么让总 token 最少」。

## 5. 一个反例重写

**改前（太粗）**：

```
process_order(action, order_id, ...一长串参数)
   action 可选 query / update / cancel / refund ...
```

**改后（拆成语义完整的动作）**：

```
get_order(order_id)          # 查订单
update_order(order_id, ...)  # 改订单
cancel_order(order_id)       # 取消
refund_order(order_id, ...)  # 退款
```

模型不再需要「猜该传哪个 action」，每个工具名本身就是意图。

## 6. 小结

- 粒度目标：一次调用恰好完成「一个动词 + 一个对象」。
- 太细→轮次多→成本平方涨；太粗→参数爆炸→难选、难复用。
- 三个信号：连环调用、功能开关参数、描述写不下边界。
