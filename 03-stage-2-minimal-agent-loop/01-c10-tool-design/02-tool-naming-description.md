# C10-2 · 命名与描述：写给模型看的说明书
> 阅读约 12 分钟。目标：写出让模型「一看就会用、不乱用」的工具命名和描述。

## 1. 一个被低估的事实

模型对工具的全部理解，来自**你写进 tools 数组的那段文字**（名字 + 描述 + 参数说明）。它看不到你的函数实现，也不「理解」你的业务。所以：

> 工具的 description 不是给人看的注释，而是**给模型的唯一说明书**。写砸了，模型就会乱调。

这是阶段 1 反复强调的「先读后答」在工具上的镜像：**模型只会按你给的说明书行事**。

## 2. 命名：动词开头、动宾结构、无歧义

| 好 | 差 | 原因 |
|---|---|---|
| `search_weather` | `get_data` | 无具体语义，模型不知道查什么 |
| `save_note` | `save` | 缺对象，歧义 |
| `list_orders` | `orders` | 缺动词，意图不明 |
| `cancel_order` | `do_cancel` | 「do」是废词 |

规则：
1. **动词开头**（search / get / save / list / cancel / create …）。
2. **动宾结构**，对象明确。
3. **避免近义歧义**：`get` 和 `search` 和 `query` 别混用，全家统一一种（`get` 是取已知对象，`search` 是按条件搜）。

## 3. 描述：写清「能干什么 + 什么时候用 + 边界」

一个高质量的 description 覆盖三件事：

```python
{
  "name": "search_weather",
  "description": "查询指定城市当前天气。用于用户询问天气时调用。"
                 "仅支持中国境内地级市，不支持国外城市和未来预报。",
  ...
}
```

- **能干什么**：一句话，动作 + 对象。
- **什么时候用**：什么场景该调它（和 `search_stock` 之类区分开）。
- **边界**：不支持什么，避免模型在错误场景硬调。

**反例**：`"description": "天气工具"` —— 什么都没说，模型只能猜。

## 4. 参数描述：每个字段都要写

模型靠参数描述决定**填什么值**。C1-4 已经强调过，这里再补两条：

1. **写「值的语义」，不写「字段名复读」**：

```
❌ "city": {"description": "城市"}          # 复读字段名
✅ "city": {"description": "城市名，如「北京」，不含省、国别"}
```

2. **能枚举就枚举，能举例就举例**（见 C4-3 的 enum 收敛）：

```
✅ "unit": {"enum": ["celsius", "fahrenheit"]}
✅ "date": {"description": "日期，ISO 8601 格式 YYYY-MM-DD"}
```

## 5. 一个完整的好例子

```python
{
  "name": "create_reminder",
  "description": "创建一个提醒。用于用户说「提醒我 / 到时候通知我」时调用。"
                 "仅支持未来时间，不支持过去的时刻。",
  "parameters": {
    "type": "object",
    "properties": {
      "content":  {"type": "string", "description": "提醒内容，一句话"},
      "due_time": {"type": "string",
                   "description": "提醒时间，ISO 8601 格式 YYYY-MM-DDTHH:MM:SS"}
    },
    "required": ["content", "due_time"]
  }
}
```

注意：名字、描述、参数、required，每一处都在给模型「降低理解成本」。

## 6. 小结

- description 是给模型的唯一说明书，不是给人看的注释。
- 命名：动词开头 + 动宾结构 + 全家统一词表。
- 描述：能干什么 + 什么时候用 + 边界；参数写值语义、能枚举就枚举。
