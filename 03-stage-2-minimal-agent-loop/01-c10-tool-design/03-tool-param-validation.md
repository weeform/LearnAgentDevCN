# C10-3 · 参数校验：schema 之外的第二道防线
> 阅读约 11 分钟。目标：在 JSON Schema 约束之上，建立代码层的参数校验。

## 1. 为什么 schema 不够

工具的 `parameters` 用 JSON Schema 描述，它能保证**参数类型对、必填在**（见 C4-3）。但它**管不了语义**：

- `age: 150` —— 类型对（number），但语义荒谬。
- `city: "不存在的地名"` —— 类型对（string），但值无效。
- `amount: -99999` —— 类型对，但越界。

这些「类型合法、语义非法」的值，模型照样可能填出来（尤其是它「脑补」参数时）。所以**代码层必须再校验一次**。

## 2. 校验三件套

在每个工具函数内部，做这三步：

```python
def search_weather(city: str):
    # 1. 类型/格式：str，非空，无控制字符
    if not isinstance(city, str) or not city.strip():
        return {"error": "city 必须是非空字符串"}
    # 2. 范围/白名单：值必须在合法集合内
    if city not in VALID_CITIES:
        return {"error": f"不支持的城市：{city}"}
    # 3. 业务规则：金额、日期、权限等
    ...
    return {"city": city, "temp": 18}
```

## 3. 校验失败的「正确姿势」

校验不通过，**别抛异常让循环崩掉，也别吞掉**——要返回一个**明确的错误**，让模型能据此修正（报错回传见 C11-2）：

```python
return {"error": "amount 必须在 1 到 10000 之间，收到 -5"}
```

这样模型下一轮能自己改参数，而不是整个任务中断。

### 3.1 错误消息写得好不好，决定模型能不能自己修

同一件事，三种写法，修复率差一个量级：

| 写法 | 例子 | 模型下一步 |
|---|---|---|
| ❌ 只说失败了 | `{"error": "参数错误"}` | 猜，大概率原样重试一次 |
| ⚠️ 只说是哪个字段 | `{"error": "amount 不合法"}` | 知道改哪个，但不知道怎么改 |
| ✅ 字段 + 期望 + 实收 | `{"error": "amount 必须在 1 到 10000 之间，收到 -5"}` | 直接修对 |

完整的信息其实就四项：**哪个字段、期望什么、收到什么、怎么改**。多写这十几个字，能省掉一整轮重试——而一整轮重试的成本是这个工具定义的好几倍。

再补一条：错误里**不要带堆栈**。堆栈对模型没用（它读不懂你的调用链），还白白多占几百 token，甚至泄露内部路径。

### 3.2 同一个参数错了两次，就别再让模型试了

校验失败回传是为了让模型修，但有个必须设的上限：**同一个工具、同一个字段，连续失败 2 次就停**。

原因很简单——第二次错通常说明模型已经从上下文里得出了错误结论（比如它认定「这个城市一定存在」），再给它第三次机会，它只会换个写法继续错。这时正确动作是终止并上报，而不是把错误再回传一遍。

这条和 C9-4 的重复检测是同一个机制：**用 (工具名, 归一化参数) 计数**，别指望模型自己意识到在打转。

## 4. 高危参数单独加码

对「有副作用」的参数，校验要格外严（和 C8-3 的权限层呼应）：

| 参数 | 校验 |
|---|---|
| 金额 | 上限、下限、精度（两位小数） |
| 收件人/收件地址 | 白名单、格式 |
| URL | 协议白名单（http/https）、域名黑名单 |
| 文件路径 | 防路径穿越（`../`）、限定根目录 |
| 表达式/代码 | **绝不放行任意执行**（见 C9-3 的 eval 坑） |

其中最后一条是红线：凡是「模型传进来的表达式 / 代码」，一律按不可信输入处理。

## 5. 校验放哪一层

一个常见分歧：校验放「工具函数内」还是「执行器统一入口」？

- **工具函数内**：贴近业务，能写业务规则（推荐，语义校验放这里）。
- **执行器入口**：做通用校验（参数是 dict、能 json 解析、必填字段存在），所有工具共享。

两者**都做**：入口做通用防线，函数内做业务防线。不要指望单一层包办。

### 5.1 三个最容易漏的通用校验

入口层这三条看着琐碎，但漏了都会出事：

1. **类型强转**：模型可能把 `3` 写成 `"3"`、把 `false` 写成 `"false"`。后者尤其坑——`bool("false")` 是 `True`。**字符串 `"false"` 必须显式转换成布尔**，不能直接 `if value:`。
2. **空字符串与纯空白**：`strip()` 之后为空要当缺失处理。否则 `city=" "` 会一路传到下游 API，报一个你看不懂的错。
3. **超长字符串**：单个参数超过几千字符，要么是模型把整段文档塞了进来（成本爆炸），要么是注入载荷（见 C8-2）。给字符串参数设上限，超了直接拒。

## 6. 小结

- schema 管「类型对」，代码管「语义对」，两者缺一不可。
- 校验失败返回明确 error，别抛异常、别吞掉；错误信息写全「哪个字段、期望什么、收到什么」。
- 同一字段连错 2 次就终止，别让它无限试。
- 高危参数（金额/URL/路径/表达式）单独加码，表达式执行是红线。
- 入口层三个通用校验最容易漏：类型强转（尤其 `"false"`）、空字符串、超长字符串。

3. 哪些参数属于「高危」，为什么表达式执行是红线？

<details>
<summary>参考思路</summary>

1. schema 只管类型对不对，管不了语义：金额传 -1、日期传 2099 年、路径传 `../../etc/passwd`、订单号传别人的。这些类型全合法。
2. 返回结构化 error（哪个字段、期望什么、收到什么），让模型可修正。抛异常会中断循环；静默兜底（默认成 0）最危险，错误数据一路流下去。
3. 金额、URL、文件路径、SQL/表达式。表达式执行等于把任意代码执行权交给模型输出，一行 `eval` 就能越过你所有防线。
