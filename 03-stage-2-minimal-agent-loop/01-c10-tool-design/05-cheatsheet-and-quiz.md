# C10-4 · 工具设计清单与自测
> 阅读约 10 分钟。这一篇把 C10 压成一份可打分的清单 + 自测。

## 1. 工具设计打分清单

拿你手上的每个工具，逐条打勾：

**粒度**
- [ ] 一次调用恰好完成「一个动词 + 一个对象」
- [ ] 没有「功能开关」型参数（`mode="query|update|delete"`）
- [ ] 不需要连环调用 3+ 个工具才能完成一个目标

**命名**
- [ ] 动词开头，动宾结构
- [ ] 无歧义，全家词表统一（get / search / query 不混用）

**描述**
- [ ] 写清「能干什么」
- [ ] 写清「什么时候用」
- [ ] 写清「边界（不支持什么）」

**参数**
- [ ] 每个参数都有 description（写值语义，非复读字段名）
- [ ] 能枚举的用 enum
- [ ] 类型正确、required 正确

**校验（代码层）**
- [ ] 类型/格式校验
- [ ] 范围/白名单校验
- [ ] 高危参数（金额/URL/路径/表达式）单独加码

## 2. 自测（6 道）

> 答对 4 道以上，本课通过。

1. 一个工具「太粗」和「太细」各有什么代价？
2. 出现哪三个信号说明粒度需要调整？
3. `get_data` 这个名字为什么不好？怎么改？
4. 工具的 description 要覆盖哪三件事？
5. 为什么 JSON Schema 管不了「参数语义」？举一个类型对但语义错的例子。
6. 参数校验失败时，应该「抛异常」「吞掉」还是「返回 error」？为什么？

### 答案要点

1. 太粗：参数爆炸、模型难选、难复用；太细：轮次多、成本平方涨、易断。
2. 连环调用、功能开关参数、描述写不下边界。
3. 无具体语义，模型不知道查什么；改成动词+对象，如 `get_weather` / `get_user_profile`。
4. 能干什么、什么时候用、边界（不支持什么）。
5. schema 只管类型和必填，管不了值是否合法；如 `age: 150`（类型对但语义荒谬）。
6. 返回明确的 error；让模型据此自我修正，既不让循环崩掉，也不误导模型以为成功。
