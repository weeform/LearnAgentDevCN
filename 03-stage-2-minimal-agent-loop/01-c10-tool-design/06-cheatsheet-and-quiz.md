# C10-6 · 工具设计清单与自测
> 阅读约 11 分钟。这一篇把 C10 压成一份可打分的清单（含操作型工具专项）+ 自测。

## 1. 工具设计打分清单

拿你手上的每个工具，逐条打勾：

**粒度**
- [ ] 一次调用恰好完成「一个动词 + 一个对象」
- [ ] 没有「功能开关」型参数（`mode="query|update|delete"`）
- [ ] 不需要连环调用 3+ 个工具才能完成一个目标

**命名**
- [ ] 动词开头，动宾结构
- [ ] 无歧义，全家词表统一（get / search / query 不混用）

**描述**
- [ ] 写清「能干什么」
- [ ] 写清「什么时候用」
- [ ] 写清「边界（不支持什么）」

**参数**
- [ ] 每个参数都有 description（写值语义，非复读字段名）
- [ ] 能枚举的用 enum
- [ ] 类型正确、required 正确

**校验（代码层）**
- [ ] 类型/格式校验
- [ ] 范围/白名单校验
- [ ] 高危参数（金额/URL/路径/表达式）单独加码

**操作型工具专项**（只对 computer use / 浏览器类工具，见 C10-4）

- [ ] 动作已原子化，没有 `login` 这种一次点十下的「大动作」
- [ ] 每个动作都返回观察（截图 + URL/标题/错误提示）
- [ ] 动作前先 `wait_for`，绝不盲点
- [ ] 有副作用的动作，重试前会先查状态
- [ ] 失败时最后一张截图进了 trace
- [ ] 运行身份是受限账号 + 独立 profile，不是主账号
- [ ] 有域名白名单
- [ ] 不可逆操作走人工确认（C23-3）

## 2. 一个工具的前后对比

清单是用来打分的，但打分前得先知道「满分长什么样」。同一个查询订单的工具，两种写法：

**改前**：

```json
{
  "name": "query",
  "description": "查询数据",
  "parameters": {
    "type": "object",
    "properties": {
      "type": {"type": "string"},
      "id": {"type": "string"}
    }
  }
}
```

三个问题叠在一起：名字叫 `query` 查什么不知道；描述没说什么场景该用；`type` 参数没有枚举，模型只能猜。

**改后**：

```json
{
  "name": "get_order",
  "description": "按订单号查询订单详情，返回状态、金额、物流与商品明细。用户问「这单到哪了」「订单多少钱」时使用。只能查本账号下的订单；要查别人或跨账号的订单，本工具不支持。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "订单号，形如 SO-2026-000123，从历史对话或列表中获取"},
      "include": {
        "type": "array",
        "items": {"type": "string", "enum": ["items", "logistics", "payment"]},
        "description": "额外要返回的区块，默认只返回状态与金额；用户问到物流或支付细节时再带上"
      }
    },
    "required": ["order_id"]
  }
}
```

差别不在措辞，在于**每一个会让模型犹豫的地方都被提前回答了**：什么时候用、参数长什么样、边界在哪、可选值有哪些。

## 3. 五个反模式（见到就改）

| 反模式 | 长什么样 | 为什么坏 |
|---|---|---|
| 万能工具 | `execute(query)`、`do_action(...)` | 相当于让模型写代码，等于放弃工具层的全部护栏 |
| 描述复读字段名 | `"city": "城市"` | 模型从中学不到任何东西；要写「值长什么样、从哪来」 |
| CRUD 四合一 | `manage_user(action, ...)` | 权限无法分级，审计看不出到底做了什么（见 C10-1 §5） |
| 返回整页 HTML/JSON | 直接把接口响应丢回去 | 一次几十 KB，后面每轮都为它付钱（见 C13-3） |
| 静默兜底 | 校验失败时返回默认值 | 错误数据一路流到结论，最难查（见 C10-3） |

## 4. 上线前 5 分钟自检

不用打分，只问四句话，答不上来就别上线：

1. **模型第一次看到这个工具名时，能不能猜出该在什么场景用？** 不能 → 改名字或改描述。
2. **它最可能填错的参数是哪个？填错了会怎样？** 说不出 → 校验没做够。
3. **这个工具失败时，模型拿到的是什么？** 是堆栈或空对象 → 改错误结构。
4. **这个工具被连调三次，会发生什么？** 会重复扣款/重复发货 → 缺幂等。

**多模态专项**（只对要「看」的工具，见 C10-5）

- [ ] 确认过「文本 / DOM 拿不到这条信息」，才用图
- [ ] 截图前固定了 viewport 与 DPR，坐标系写进了 prompt
- [ ] 动作后等状态稳定，而不是等固定毫秒
- [ ] 图片里的文字按「数据」处理，不当指令执行
- [ ] 视觉判断触发的写操作仍要过权限层

## 5. 自测（11 道）

> 答对 8 道以上，本课通过。

1. 一个工具「太粗」和「太细」各有什么代价？
2. 出现哪三个信号说明粒度需要调整？
3. `get_data` 这个名字为什么不好？怎么改？
4. 工具的 description 要覆盖哪三件事？
5. 为什么 JSON Schema 管不了「参数语义」？举一个类型对但语义错的例子。
6. 参数校验失败时，应该「抛异常」「吞掉」还是「返回 error」？为什么？
7. 一个「点提交按钮」的工具，模型重试了一次，结果提交了两笔。这属于哪类问题？怎么从设计上避免？
8. 工具数量到了 40 个，除了删工具还有哪两条路？
9. 为什么「读操作可以粗、写操作必须细」？
10. 模型把布尔值传成了字符串 `"false"`，直接 `if value:` 会怎样？正确做法是什么？
11. 带文字层的 PDF，为什么不该整页转图喂给视觉模型？

### 答案要点

1. 太粗：参数爆炸、模型难选、难复用；太细：轮次多、成本平方涨、易断。
2. 连环调用、功能开关参数、描述写不下边界。
3. 无具体语义，模型不知道查什么；改成动词+对象，如 `get_weather` / `get_user_profile`。
4. 能干什么、什么时候用、边界（不支持什么）。
5. schema 只管类型和必填，管不了值是否合法；如 `age: 150`（类型对但语义荒谬）。
6. 返回明确的 error；让模型据此自我修正，既不让循环崩掉，也不误导模型以为成功。
7. 违反幂等——操作型工具的点击会真实生效，重试就是重复执行。设计上改成「动作前先查状态」（提交前先查是否已有该单据），并用幂等键让服务端忽略重复请求；事后去重只是补救，不是方案。
8. 按领域分组（先调组入口再展开）与「工具检索」（按任务召回 top 5–8 个再注入），见 C10-1 §4。
9. 读没有副作用，一次拿全能省轮次；写有副作用，合并会让权限无法分级、审计说不清做了什么（C23-1）。
10. `bool("false")` 是 `True`，等于把「不要执行」读成「执行」。必须显式解析字符串布尔值，不能靠真值判断（C10-3 §5.1）。
11. 文字层能抽出准确文本，转图后模型可能看错小数点、表格错行，而成本是文本抽取的几十倍；先抽文本，抽不出来（真扫描件）才转图（C10-5 §4）。
