# C11-1 · 失效模式全景：Agent 会以哪些方式坏掉
> 阅读约 10 分钟。目标：建立 Agent 失效的完整地图，后面几篇逐个拆解应对。

## 1. 为什么 Agent 特别容易「坏」

单次 API 调用，坏的概率很低。但 Agent 是**几十次调用串成一条链**：

> 单步成功率 99%，30 步任务的整体成功率只剩约 74%（0.99³⁰）。

（这个算术在 C5 讲过，这里它第一次以「系统级问题」的面貌出现。）任何一环出问题，都可能让整条链跑偏。所以要先看清「会坏在哪」。

## 2. 失效模式地图

| 类别 | 表现 | 后果 |
|---|---|---|
| 工具报错 | 工具抛异常 / 返回错误 | 循环中断或模型「脑补」结果 |
| 幻觉调用 | 模型编造参数值 / 编造「工具已执行、结果如何」 | 结果凭空捏造，最隐蔽 |
| 死循环 | 模型在几步之间来回打转 | 烧钱、任务永远完不成 |
| 超时 / 无响应 | 网络、限流、长任务卡住 | 任务挂起 |
| 提前终止 | 该做的没做完就「回答」了 | 结果不完整 |
| 结果漂移 | 每次跑结果都不一样 | 不可复现 |

## 3. 按「可恢复性」分类

不是所有失效都该用同一种方式处理。先分两类：

- **可恢复（瞬态）**：网络抖动、限流 429、超时——重试可能就好（见 C5-2）。
- **不可恢复（确定）**：参数错（400）、工具不存在、权限不足——重试必再失败，要**改输入或降级**。

这个分类是 C5-1 的延续：**Agent 的每一环，都复用阶段 0 的稳定性判断**。

## 4. 一个关键区分：报错 vs 幻觉

- **报错**是「工具执行了，但失败了」——有明确的错误信号，可以回传（C11-2）。
- **幻觉调用**是「模型编造了它没真正拿到的东西」——最普遍的是**编造参数值**（给工具塞一个脑补的输入）和**编造「工具已执行、结果如何」**（根本没有真实执行，却言之凿凿）。原生 function calling 下「调用一个根本不存在的工具」很少见（工具名受约束解码限制），但「编参数、编结果」才是真正的坑。

幻觉调用的危险在于：它可能让模型**在错误的基础上继续自信地编**，直到输出一个看似合理、实则凭空捏造的结论。防御它，靠的是「让每一步都有真实反馈」——这正是 Observation 的意义（见 C9-2）。

## 5. 失效的根因，多数是「反馈缺失」

回头看这张地图，会发现一条共性：

> 模型一旦「看不到真实结果」，就会开始脑补。脑补，是一切失效的温床。

所以后面几篇的应对，几乎都围绕同一件事：**保证每一步都有真实、明确、及时的反馈**（工具结果、报错、超时信号），别让模型在黑暗中瞎走。

## 6. 最危险的一类：不报错的失效

上面那张地图里的失效，多数会留下痕迹（异常、状态码、空的 `tool_calls`）。真正难查的是**全程无异常、结果却是错的**那三种：

**静默错误**——工具调通了，返回 200，内容语义是错的。典型如查询接口按默认时间范围返回了上个月的数据、分页只取了第一页。Agent 没有任何信号说「这不对」，它拿着错数据继续推理，最后给一个逻辑自洽但事实错误的结论。

**污染扩散**——一次错误结论写进上下文后，后面每一步都在它之上推理。模型不会回头质疑自己十步前说的话，于是错误被反复引用、越滚越大（这也是 C15-4 要把脏上下文丢给子 Agent 的原因）。

**目标漂移**——任务跑到一半，模型把「用户想要的」换成了「它正在做的」。典型是让它汇总投诉，它跑去逐条回复投诉了，且做得很像样。

三种的共同点：**没有任何一步是「失败」的**。所以防御不能靠 try/except，只能靠**独立于模型的校验**：

| 失效 | 独立校验手段 |
|---|---|
| 静默错误 | 关键数值二次核对；对返回做基本合理性检查（行数、时间范围、空值比例） |
| 污染扩散 | 每 N 步做一次「复述任务目标 + 当前结论」的自检；关键结论要求附来源 |
| 目标漂移 | 结尾强制对照验收清单（见 C24-1 的写法），而不是让模型自己说「完成了」 |

一句话：**能被 try/except 抓住的都不算大问题**。真正让 Agent 上不了生产的是「它很自信，而且是错的」。

## 7. 症状 → 根因 → 对策

排查时从现象倒推比从原理正推快：

| 症状 | 根因 | 对策 | 详见 |
|---|---|---|---|
| 反复调同一个工具 | 工具没返回它想要的信息 / 错误没回传 | 检查返回值是否回答了问题；回传结构化错误 | C11-2 |
| 报错后不修，直接放弃 | 错误信息太模糊，模型无从下手 | 错误写清「字段 + 期望 + 实收」 | C10-3 |
| 中途「忘了」最初要求 | 上下文被压缩或稀释 | 关键约束固定在 system 或每轮复述 | C13-2 |
| 结论对但数字错 | 静默错误 + 无二次核对 | 关键数值独立重算 | C25-2 |
| 每次都跑出不同结果 | 采样不稳 / 工具本身有随机性 | 温度降到 0；把随机源固定住 | C1-2 |
| 花了很多步却啥也没做 | 目标漂移 / 规划失败 | 结尾强制对照验收清单 | C11-3 |

## 8. 小结

- 单步 99% × 30 步 ≈ 74%，链越长越脆。
- 失效地图：报错 / 幻觉调用 / 死循环 / 超时 / 提前终止 / 结果漂移。
- 先分「可恢复 vs 不可恢复」，再谈处理。
- 共性根因：反馈缺失 → 脑补 → 失效。
- 最难的不是报错，是**静默错误、污染扩散、目标漂移**这三类不报错的失效——只能靠独立于模型的校验拦。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 单步 99% 正确、30 步串联，整体成功率大约多少？这个数字对你的设计意味着什么？
2. 「报错」和「幻觉调用」为什么必须分开处理？
3. 为什么说失效的共性根因是「反馈缺失」？

<details>
<summary>参考思路</summary>

1. 约 74%（0.99³⁰）。意味着长链必须靠重试、校验、断点恢复来补偿，而不是指望每一步都不出错——链越长越要设计「错了能发现」。
2. 报错是显式的、有信号的，可以重试或修正；幻觉调用是「自信地调了个不存在的参数或工具」，没有信号，必须靠 schema 校验和结果检查抓出来。
3. 模型拿不到真实世界的反馈，只能脑补。所以恢复的第一原则不是「教它更聪明」，而是「让它看见发生了什么」——结构化回传、每步观察、明确状态。
