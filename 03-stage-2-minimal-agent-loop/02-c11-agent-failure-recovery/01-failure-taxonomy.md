# C11-1 · 失效模式全景：Agent 会以哪些方式坏掉
> 阅读约 10 分钟。目标：建立 Agent 失效的完整地图，后面几篇逐个拆解应对。

## 1. 为什么 Agent 特别容易「坏」

单次 API 调用，坏的概率很低。但 Agent 是**几十次调用串成一条链**：

> 单步成功率 99%，30 步任务的整体成功率只剩约 74%（0.99³⁰）。

（这个算术在 C5 讲过，这里它第一次以「系统级问题」的面貌出现。）任何一环出问题，都可能让整条链跑偏。所以要先看清「会坏在哪」。

## 2. 失效模式地图

| 类别 | 表现 | 后果 |
|---|---|---|
| 工具报错 | 工具抛异常 / 返回错误 | 循环中断或模型「脑补」结果 |
| 幻觉调用 | 模型编造参数值 / 编造「工具已执行、结果如何」 | 结果凭空捏造，最隐蔽 |
| 死循环 | 模型在几步之间来回打转 | 烧钱、任务永远完不成 |
| 超时 / 无响应 | 网络、限流、长任务卡住 | 任务挂起 |
| 提前终止 | 该做的没做完就「回答」了 | 结果不完整 |
| 结果漂移 | 每次跑结果都不一样 | 不可复现 |

## 3. 按「可恢复性」分类

不是所有失效都该用同一种方式处理。先分两类：

- **可恢复（瞬态）**：网络抖动、限流 429、超时——重试可能就好（见 C5-2）。
- **不可恢复（确定）**：参数错（400）、工具不存在、权限不足——重试必再失败，要**改输入或降级**。

这个分类是 C5-1 的延续：**Agent 的每一环，都复用阶段 0 的稳定性判断**。

## 4. 一个关键区分：报错 vs 幻觉

- **报错**是「工具执行了，但失败了」——有明确的错误信号，可以回传（C11-2）。
- **幻觉调用**是「模型编造了它没真正拿到的东西」——最普遍的是**编造参数值**（给工具塞一个脑补的输入）和**编造「工具已执行、结果如何」**（根本没有真实执行，却言之凿凿）。原生 function calling 下「调用一个根本不存在的工具」很少见（工具名受约束解码限制），但「编参数、编结果」才是真正的坑。

幻觉调用的危险在于：它可能让模型**在错误的基础上继续自信地编**，直到输出一个看似合理、实则凭空捏造的结论。防御它，靠的是「让每一步都有真实反馈」——这正是 Observation 的意义（见 C9-2）。

## 5. 失效的根因，多数是「反馈缺失」

回头看这张地图，会发现一条共性：

> 模型一旦「看不到真实结果」，就会开始脑补。脑补，是一切失效的温床。

所以后面几篇的应对，几乎都围绕同一件事：**保证每一步都有真实、明确、及时的反馈**（工具结果、报错、超时信号），别让模型在黑暗中瞎走。

## 6. 小结

- 单步 99% × 30 步 ≈ 74%，链越长越脆。
- 失效地图：报错 / 幻觉调用 / 死循环 / 超时 / 提前终止 / 结果漂移。
- 先分「可恢复 vs 不可恢复」，再谈处理。
- 共性根因：反馈缺失 → 脑补 → 失效。
