# C11-4 · 什么时候不该用 Agent
> 阅读约 10 分钟。目标：建立「该不该用 Agent」的判断力——这是最省钱的一项能力。

## 1. 先算一笔账

Agent 是**贵**的方案：多轮调用、平方增长的成本、更长的延迟、更难调试。它值得，**只有当任务的「不确定性」需要模型反复决策时**。

如果一个任务能用确定性代码解决，用 Agent 就是**花钱买罪受**。所以这一节的价值是：**把不该做的排除掉**，比学会怎么做更重要。

### 1.1 这笔账其实能算

「贵」不是形容词，可以落成三个数：

```
Agent 单任务成本 ≈ 轮数 × (system + 工具定义 + 历史累积) × 输入单价 + 输出 token × 输出单价
人工单任务成本 ≈ 处理分钟数 / 60 × 时薪
纠错成本 ≈ 出错率 × (返工成本 + 影响面)
```

一个具体例子（数字仅示意，请按自己的单价重算）：

| 项 | 数值 |
|---|---|
| 人工处理一单 | 6 分钟，时薪 60 元 → **6 元/单** |
| Agent 处理一单 | 12 轮，累计输入约 8 万 token、输出 6 千 → **约 1.2 元/单** |
| Agent 出错率 | 15%，其中一半需要人工重做 → 期望返工 0.075 单 × 6 元 ≈ **0.45 元** |
| **Agent 实际单成本** | **约 1.65 元/单** |

算到这里结论是「划算」——但请注意分子里那 0.45 元。**出错率一旦从 15% 涨到 40%，纠错成本就会吃掉全部节省**。所以「该不该用 Agent」的答案经常不是固定的，它随**出错率**变化。

这也解释了为什么 C11-2（错误回传）和 C20（评测）在这里如此关键：它们直接决定上面那个出错率。

## 2. 三类「别用 Agent」的场景

**① 确定性任务 → 用代码**

规则明确、输入输出固定，代码能 100% 做对：金额计算、格式转换、排序、查固定字段……用 Agent 反而引入「模型可能算错、可能飘」的风险。

> 判据：**你能写出明确的 if/else 吗？** 能，就别用 Agent。

**② 可枚举的流程 → 用固定工作流**

步骤是有限的、已知的，只是「按顺序执行」：下单流程、审批流、固定的数据管道……这类用**确定性编排**（代码 + 固定函数调用）即可，不需要「让模型自己决定下一步」。

> 判据：**下一步的选择是有限的、且你能全部列出来吗？** 能，就用工作流。

**③ 延迟敏感 / 高频场景 → 别用多步循环**

每一步都有模型调用延迟 + 网络往返。对「必须亚秒级响应」的场景（搜索补全、实时风控），多步 Agent 天然不合适。

> 判据：**响应必须很快吗？** 是，就压缩成单次调用。

## 3. 什么时候才值得用 Agent

反向看，Agent 的价值边界是**「不确定性」**：

- 需要**动态判断**下一步做什么（没有固定流程）；
- 需要**综合多步信息**、在过程中调整策略；
- 工具的选择和参数**依赖中间结果**。

一句话：

> 流程能写死就写死，写不死的部分才交给 Agent。

### 3.1 第四类边界：错误代价不对称

前面三类看的是「能不能写死」，还有一类看的是**错了会怎样**：

| 任务 | 错一次的代价 | 结论 |
|---|---|---|
| 生成周报初稿 | 人改两分钟 | Agent 合适 |
| 给客户报价 | 可能要道歉、赔付 | Agent 只出草稿，人发 |
| 转账 / 删库 / 对外发公告 | 不可逆 | 必须人在回路（C23-3） |

判据简单：**错误可逆且便宜 → 可以放手；错误不可逆或昂贵 → 只能建议不能执行**。这跟模型多强无关，再强的模型也有 P(错)，而不可逆操作只需要一次。

## 4. 一个实用的决策顺序

拿到一个任务，按这个顺序问：

1. 能用代码 / 规则确定性地解决吗？→ 能，**用代码**。
2. 能枚举成固定流程吗？→ 能，**用工作流**。
3. 必须亚秒级响应吗？→ 是，**压成单次调用**。
4. 前三步都不满足（确实需要动态决策）→ **才用 Agent**。

### 4.1 别忘了中间态：半自动

现实里最划算的常常不是「全自动」或「全人工」，而是**Agent 做建议、人做执行**：

- Agent 把「查了什么、结论是什么、建议怎么做」整理成一屏，人点确认或改一下。
- 好处：省掉 80% 的信息搜集与整理时间，同时把不可逆动作留在人手里。
- 代价：多一次人工点击，吞吐受限。

判断用哪一档，看两个数就够：**任务量**（每天几千单，人工跟不上 → 必须自动）和**错误代价**（错一次要赔钱 → 必须留人）。两个都高，就做「自动处理 + 抽样人工复核」；两个都低，别折腾 Agent，脚本更快。

## 5. 常见「伪 Agent」案例

| 任务 | 真相 | 正确做法 |
|---|---|---|
| 查天气后返回 | 一步工具调用 | 单次 function calling，别上循环 |
| 固定格式的报表生成 | 确定性流程 | 代码 + 模板 |
| 「智能客服」第一层分流 | 可枚举的分类 | 分类器 / 路由，别上多步 Agent |

这些案例的共同点：**把「单次调用」包装成了「Agent」**，白白付出了循环的代价。

## 6. 小结

- Agent 是贵的方案，只在「不确定性需要动态决策」时才值得；而且这笔账能算，结论随**出错率**变化。
- 三类别用：确定性任务（代码）、可枚举流程（工作流）、延迟敏感（单次调用）。
- 第四类看错误代价：**错误可逆且便宜才放手；不可逆或昂贵只能建议**。
- 决策顺序：能写死就写死，写不死的才交给 Agent。
- 别忘了中间态：**Agent 出建议、人执行**，往往比全自动更划算。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 三类「别用 Agent」的场景分别是什么？各自该用什么替代？
2. 「不确定性需要动态决策」为什么是 Agent 唯一站得住的前提？
3. 你手上有没有一个「伪 Agent」？怎么把它改回普通程序？

<details>
<summary>参考思路</summary>

1. 确定性任务 → 写代码；可枚举流程 → 工作流/状态机；延迟敏感 → 单次调用或预计算。三者都不需要模型做多步决策。
2. 因为 Agent 的每一步都要一次 LLM 调用，成本、延迟、不确定性都是数量级的代价。如果路径可以事先枚举，这笔钱纯属浪费。
3. 典型伪 Agent：固定 5 步的数据处理流程。改法是把步骤写成代码，只在「需要判断/生成」的那一两个节点调模型。
