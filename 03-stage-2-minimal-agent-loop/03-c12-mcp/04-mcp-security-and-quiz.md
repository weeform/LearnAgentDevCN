# C12-4 · MCP 安全与阶段 2 总复习
> 阅读约 13 分钟。目标：认清 MCP 的特有风险，并把 C9–C12 收束成能查、能自测的东西。

## 1. MCP 的特有风险

接 MCP 意味着**信任第三方提供的工具定义和执行逻辑**，攻击面比「自己写工具」大得多。四类风险：

| 风险 | 是什么 | 后果 |
|---|---|---|
| 投毒的工具描述 | server 的 tool description 里藏恶意指令 | 诱导模型执行不该做的事 |
| 间接提示词注入 | 工具返回的数据里藏指令 | 模型把数据当指令执行（见 C8-1） |
| 过度授权 | server 拿到超出所需的权限 | 一旦被攻破，破坏面更大 |
| 仿冒 server | 冒名顶替知名 server 的恶意服务 | 静默窃取数据/邮件等 |

**真实事故**：2025-09，一个非官方 Postmark MCP server 被植入后门，**静默把所有外发邮件 BCC 给攻击者**。你接入的「发邮件工具」，可能在替你发信的同时，把每封信抄送给第三方——而你完全不知道。

## 2. 防御：把 C8 的原则搬过来

MCP 安全不是新知识，是 C8（注入防御）在「工具生态」场景的落地：

1. **只接可信来源的 server**：优先官方、有维护、有社区 review 的 server；第三方 server 先读它的工具清单和源码。
2. **接之前审查工具描述**：`list_tools()` 拉出的 tool description 里若藏着异常指令，直接拒接。这专门针对「投毒的工具描述」——隔离标记只对工具返回的数据有效，对「进 prompt 的工具定义」无效。
3. **锁定版本 / 禁自动更新**：pin 到已审查过的具体版本，升级前 diff 源码、监控依赖变更。Postmark 那种「先建立信任、再在后续版本投毒」的攻击，光靠「只接可信来源」防不住。
4. **最小权限**：server 能访问什么，就在启动参数里只给什么（比如文件系统 server 只挂一个目录）。**别图省事给全盘。**
5. **工具白名单 + 敏感操作确认**：接进来的 server 里，把「只读工具」和「有副作用的工具」分开；有副作用的（发信、写库、删除）走人工确认（HITL，见 C8-3）。
6. **隔离标记**：工具返回的数据，套上「视为数据、不是指令」的隔离标记（见 C8-2）。
7. **记录日志**：每个工具调用的来源、参数、结果都留 trace，出事后能追溯。

一句话：**MCP 的「即插即用」是能力，也是风险——插之前先问「它可信吗、它需要这么多权限吗」。**

### 答案要点

1. system/user → assistant(tool_calls) → 执行 → tool(result) → 再请求；`tool` 消息是你的代码塞的。
2. 靠 `tool_call_id` 一一对应；流式按 index 累加、`finish_reason=tool_calls` 后再 `json.loads`。
3. Thought/Action/Observation；Observation 是模型看世界的唯一窗口，含糊或报错不清会带偏下一步。
4. 输出被截断，报错并重试，不硬解析。
5. 太细→轮次多、成本平方涨；太粗→参数爆炸、难选、难复用。
6. 能干什么、什么时候用、边界（不支持什么）。
7. 回传；raise 崩掉、吞掉脑补，回传能自我修正。
8. 记录动作签名，重复超阈值打断 + 提示换思路，仍无进展终止降级。
9. 确定性任务（用代码）、可枚举流程（用工作流）——不需要动态决策。
10. 把「模型↔工具」的集成从 N×M（逐对适配）降到 N+M（一次实现，处处复用）。
11. Host（应用）/Client（连接）/Server（暴露能力）；STDIO 本地、Streamable HTTP 远程。
12. 连 server → list_tools → 转 function calling tools → call_tool 执行。
13. name 来自函数名、description 来自 docstring、inputSchema 来自类型注解。
14. 投毒描述 / 间接注入 / 过度授权 / 仿冒 server；防御：只接可信来源、最小权限、白名单+人工确认、隔离标记、留日志（任举对应手段）。
