# C13-1 · 消息数组就是短期记忆
> 阅读约 13 分钟。目标：把「短期记忆」这个玄乎的词，落到一个具体的数据结构上——消息数组。

## 1. 先拆掉一个误解

「短期记忆」听起来像大脑在记东西，但 Agent 里它**不神秘，就是一个数组**：

```python
messages = [
    {"role": "system", "content": "..."},
    {"role": "user",   "content": "帮我查北京天气，算 18*3 并记下来"},
    {"role": "assistant", "content": None, "tool_calls": [...]},
    {"role": "tool",   "tool_call_id": "...", "content": "{\"temp\": 18}"},
    ...
]
```

API 是无状态的（见 C1-1）：模型每轮都从零开始，所以**你想让它「记得」什么，就得每轮把什么重新发一遍**。短期记忆 = 你愿意为每轮请求重复付费的那段上下文 = 消息数组。

一句话记住：

> 短期记忆不是「模型记住了」，而是「你把过去重新喂给它」。

## 2. 四种角色，四种处理方式

消息数组里每一条消息都有角色，它们的「记忆属性」完全不同：

| 角色 | 是什么 | 怎么处理 |
|---|---|---|
| `system` | 固定的规则与角色设定 | 尽量稳定，别动——动了就碎缓存（见 C2-5） |
| `user` | 用户输入 + 你要保留的指令 | 用户明确要求记住的必须原样保留 |
| `assistant` | 模型的回答与工具调用 | 已完成的可摘要，未完成的目标要保留 |
| `tool` | 工具返回 | 最容易被忽视的预算黑洞，单独 C13-3 讲 |

这个表是后面所有压缩策略的地基：**压缩不是「把最老的删掉」，而是「按角色分别决定每一条的去留」**。

## 3. 短期记忆的两个度量

判断「该不该动手压」，看两个数字：

1. **token 数**：当前消息数组一次请求要花多少 token（含 system、历史、工具返回）。
2. **轮数**：已经走了多少步。

两个数字要一起看。一个 30 步的任务，哪怕每步只加 500 token，第 30 步的输入也是 `system + 30×500`，而且前面 29 步已经为这些内容付过费了——总成本随步数**平方增长**（原理见 C7-1）。

### 3.1 一条容易被忽略的实测规律

一个真实的 Agent 会话里，**消息条数远多于「对话轮数」**。因为一次用户请求，模型可能连续调 4 次工具：

| 消息 | 角色 | 典型 token |
|---|---|---|
| 1 | user（用户提问） | 50 |
| 2 | assistant（tool_calls: search） | 120 |
| 3 | tool（检索结果原文） | 4,000 |
| 4 | assistant（tool_calls: get_weather） | 110 |
| 5 | tool（JSON 返回） | 600 |
| 6 | assistant（最终回答） | 300 |

**1 轮对话 = 6 条消息 = 约 5,200 token**。用户问了 3 个问题的会话，数组里已经有 18 条消息、1.5 万 token 以上。这就是为什么"才聊了几句怎么就贵了"——你数的轮次和数组的长度不是一个量级。

也正因为如此，**压缩的单位应该是「一轮完整的工具调用链」，不是「一条消息」**。单独压掉那条 4,000 token 的 tool 消息、却留着它前面的 assistant tool_calls，会造成下面第 4 节的问题。

## 4. 一个硬约束：tool_calls 必须成对

裁剪消息数组时，最容易踩的坑不是"删多了"，而是**删出了非法结构**。API 有一条硬规则：

> `assistant` 消息里带 `tool_calls`，则后面必须跟齐**数量相等、`tool_call_id` 一一对应**的 `tool` 消息。

如果你为了省 token 把那条 4,000 token 的 tool 消息删了，剩下的数组是：

```python
{"role": "assistant", "tool_calls": [{"id": "call_1", ...}]},   # 声明要调工具
                                                                # ← 对应的 tool 消息没了
```

直接发出去会被 API 拒绝（报错大意是 "tool call id 没有对应的 tool 响应"）。所以**裁剪的最小单位是一整组 `assistant(tool_calls) + tool(...)`，不能拆开**。

工程上建议在裁剪之后跑一次校验，比在报错里猜要省时间：

```python
def validate(messages):
    pending = set()
    for m in messages:
        if m["role"] == "assistant" and m.get("tool_calls"):
            pending |= {tc["id"] for tc in m["tool_calls"]}
        elif m["role"] == "tool":
            pending.discard(m["tool_call_id"])
    if pending:
        raise ValueError(f"孤儿 tool_call：{pending}")   # 有一半的消息被删了
```

这个检查只有十来行，但它能挡住裁剪逻辑里最常见的一类 bug。**建议放在每次组包之后、发请求之前**，而不是等 API 报错。

## 5. 什么时候必须动它

三个触发信号，满足任一就该动手：

1. **快爆窗口**：消息数组接近模型上下文上限（128K、200K），再走几步就截断。
2. **成本超预算**：每步的 prompt token 涨到不可接受，账单可见地涨。
3. **质量开始掉**：模型开始答非所问、顾此失彼（「lost in the middle」，中间信息易被忽略，见 C7-1 第 4 节）。

注意第三条最容易漏——**不是只有爆了才要压，注意力被稀释时就该压了**。

第三条有个具体表现值得记住：**模型开始重复已经做过的事**。比如明明查过天气了，又查一次；明明已经确认过地址，又问一遍。这通常不是"笨"，而是那条记录被埋在一万 token 的中段，它没看见。

## 6. 一个反直觉的事实

短期记忆的「质量」不取决于「存得多」，而取决于「存得准」：

> 塞 3 万 token 的历史，模型抓不住重点；留 3000 token 的关键信息，反而答得更准。

所以这一课的落脚点不是「怎么存更多」，而是「怎么删得聪明」。下一节就讲删/摘要/保留的分界。

## 7. 小结

- 短期记忆 = 消息数组，本质是「把过去重新喂给无状态的模型」。
- 四种角色处理方式不同，压缩要按角色分别决定，不是一刀切删最老的。
- 一轮对话 ≠ 一条消息：一次用户请求可能产生 5–6 条消息，压缩单位应是「完整调用链」。
- 硬约束：`tool_calls` 与 `tool` 消息必须成对，裁剪后要跑校验。
- 两个度量：token 数与轮数；三个触发信号：爆窗口、超预算、质量掉。
