# C13-2 · 压缩三法：摘要、删除、保留的分界
> 阅读约 12 分钟。目标：为每一条消息做出「摘要 / 删除 / 原样保留」的判断，而不是盲目砍最老的。

## 1. 三种操作，一句话分清

| 操作 | 含义 | 代价 | 收益 |
|---|---|---|---|
| **删除** | 彻底扔掉 | 信息永久丢失 | 省 token 最多 |
| **摘要** | 用更短的话替换 | 丢细节、可能失真 | 省 token，保住大意 |
| **保留原文** | 原封不动 | 不省 token | 零信息损失 |

三种操作里，**摘要最贵也最危险**（要额外调一次模型，还可能编造），删除最便宜但不可逆。多数人只想着删，其实「保留原文」和「摘要」经常是更好的默认。

## 2. 必须原样保留的（Keep）

以下内容一旦压缩或删除，任务直接跑偏，**必须逐字保留**：

1. **用户明确要求记住的**：用户说「记住我喜欢简洁回答」「以后都别用表格」——这是长期偏好，压缩时丢了等于违背用户。
2. **任务目标与未完成的承诺**：模型答应过「稍后给你汇总」，这个承诺没兑现前不能删。
3. **安全与合规约束**：system 里的「不要执行危险命令」「涉及钱要确认」这类。
4. **当前轮正在处理的关键数据**：正在用的参数、刚查到的关键结果。

判断标准一句话：

> 删掉它，任务还能不能正确完成？不能，就保留。

## 3. 可以摘要的（Summarize）

适合摘要的是「**过程已完成、但结论还有用**」的内容：

- 已完成的中间步骤的细节（例如「查了三次天气，最后取北京 18°C」→ 只需留结论）。
- 工具返回的详细结果（查库返回 5000 行 → 摘要成「共 5000 行，其中 3 行命中」）。
- 模型的思考过程（Thought 过程可以压，结论要留）。

摘要的要点：**用「结论」替换「过程」**。不是把原文压缩 30%，而是换成一个短结论。

## 4. 可以删除的（Drop）

以下内容可以直接删：

- 已完成且不影响后续的重复信息。
- 错误尝试的中间细节（试错过程本身，只要结论没丢）。
- 已经失效的临时数据（被更新的旧值）。

## 5. 最容易踩的坑：盲目砍最老的

「超了窗口就删最老几条」是最常见也最糟的策略——它把「时间」当成了「重要性」的代理，而两者经常无关：

> 第 1 轮用户说的「帮我做年度汇报」是全任务最重要的目标，按「删最老」会第一个被删掉。

正确做法是**按重要性保留，而不是按时间**：重要但老的内容，应该被摘要后保留，而不是被时间顺序淘汰。

## 6. 摘要的两个工程要点

1. **规则优先，模型兜底**。能用规则判断的（超长就截断、字段固定就只留字段），别调模型。摘要才需要模型，因为要「读懂再压缩」。
2. **摘要要可复现**。让摘要调用带固定 prompt 和 `temperature=0`（见 C1-2），否则同一个历史今天压成 A、明天压成 B，任务结果不可复现，违背三条暗线之二「可复现性」（三条暗线：成本意识 / 可复现性 / 上下文预算，见总纲第 7 节）。

## 7. 小结

- 三操作：删除最便宜但不可逆，摘要最贵也最危险，保留原文零损失。
- 分界原则：删掉还能不能正确完成？不能就保留；过程已完成、结论有用才摘要；重复失效的才删。
- 别按时间砍最老的，按重要性保留。
