# C13-2 · 压缩三法：摘要、删除、保留的分界
> 阅读约 13 分钟。目标：为每一条消息做出「摘要 / 删除 / 原样保留」的判断，而不是盲目砍最老的。

> **与 C7-3 的分工**：C7-3 讲压缩的**手法**（滚动摘要、分层摘要、结构化压缩），本篇讲**取舍**——哪些必须原样保留、哪些可以摘要、哪些可以删。手法是工具，取舍是判断，顺序别倒。

## 1. 三种操作，一句话分清

| 操作 | 含义 | 代价 | 收益 |
|---|---|---|---|
| **删除** | 彻底扔掉 | 信息永久丢失 | 省 token 最多 |
| **摘要** | 用更短的话替换 | 丢细节、可能失真 | 省 token，保住大意 |
| **保留原文** | 原封不动 | 不省 token | 零信息损失 |

三种操作里，**摘要最贵也最危险**（要额外调一次模型，还可能编造），删除最便宜但不可逆。多数人只想着删，其实「保留原文」和「摘要」经常是更好的默认。

## 2. 必须原样保留的（Keep）

以下内容一旦压缩或删除，任务直接跑偏，**必须逐字保留**：

1. **用户明确要求记住的**：用户说「记住我喜欢简洁回答」「以后都别用表格」——这是长期偏好，压缩时丢了等于违背用户。
2. **任务目标与未完成的承诺**：模型答应过「稍后给你汇总」，这个承诺没兑现前不能删。
3. **安全与合规约束**：system 里的「不要执行危险命令」「涉及钱要确认」这类。
4. **当前轮正在处理的关键数据**：正在用的参数、刚查到的关键结果。

判断标准一句话：

> 删掉它，任务还能不能正确完成？不能，就保留。

这个判断有个更可操作的形式：**假设一个新人接手这个任务，只给他压缩后的上下文，他能继续做下去吗？** 不能，说明你压掉了不该压的东西。这个视角比「这段重不重要」好判断，因为"重要"太主观，而"能不能继续"是具体的。

## 3. 可以摘要的（Summarize）

适合摘要的是「**过程已完成、但结论还有用**」的内容：

- 已完成的中间步骤的细节（例如「查了三次天气，最后取北京 18°C」→ 只需留结论）。
- 工具返回的详细结果（查库返回 5000 行 → 摘要成「共 5000 行，其中 3 行命中」）。
- 模型的思考过程（Thought 过程可以压，结论要留）。

摘要的要点：**用「结论」替换「过程」**。不是把原文压缩 30%，而是换成一个短结论。

### 3.1 「结论替换过程」具体长什么样

原文（约 380 token）：

```
我调用了 weather_api 查询北京天气，返回了 {"temp":18,"desc":"晴","humidity":40,...}。
然后我又查了上海，返回 {"temp":24,"desc":"多云",...}。用户问的是北京，
但提到了"顺便看看上海"，所以我又查了广州作对比……（后面是一串字段）
```

压成结论（约 30 token）：

```
天气：北京 18°C 晴；上海 24°C 多云；广州 27°C 阴（用于对比）。
```

注意压缩后的版本**保留了所有数值和城市**，删掉的是"我调用了什么、为什么查"这类过程叙述。**数字、ID、日期不能概括，只能照抄**——这是上一课（C7-3）讲过的原则，在会话压缩里同样适用。

判断一段内容该不该留的具体标准：**它是否改变了后续的行动**。查上海、广州如果不影响最终答案，那就是纯过程；如果用户后来问"那上海呢"，那它们就是关键事实，必须留。

## 4. 可以删除的（Drop）

以下内容可以直接删：

- 已完成且不影响后续的重复信息。
- 错误尝试的中间细节（试错过程本身，只要结论没丢）。
- 已经失效的临时数据（被更新的旧值）。

### 4.1 一个反例：错误记录不能整个删掉

「错误尝试可以删」这句话有个重要限定：**删的是细节，不是结论**。

C7-1 做过一个实验：把失败尝试的记录整体删掉，成功率反而明显下降——因为模型会**重复踩同一个坑**。它会再次调用那个已经超时的接口、再次用那个不支持的参数格式。

正确的处理是把它压成一行「负向约束」：

```
✗ 删掉：【调用 search_api(timeout=30) → 超时 → 重试 → 超时 → 改用 search_api_v2 成功】
✓ 压成：search_api 已确认不可用（超时），改用 search_api_v2。
```

差别在于：前者是故事，后者是状态。**模型不需要知道你怎么试错的，只需要知道什么路已经堵死了。** 这也解释了为什么"错误记录"既不能全删也不能全留——它是这个课里最典型的「该摘要、不该二选一」的例子。

## 5. 最容易踩的坑：盲目砍最老的

「超了窗口就删最老几条」是最常见也最糟的策略——它把「时间」当成了「重要性」的代理，而两者经常无关：

> 第 1 轮用户说的「帮我做年度汇报」是全任务最重要的目标，按「删最老」会第一个被删掉。

正确做法是**按重要性保留，而不是按时间**：重要但老的内容，应该被摘要后保留，而不是被时间顺序淘汰。

一个具体的替换规则：

| 内容类型 | 保留策略 |
|---|---|
| 第 1 轮的任务目标 | 抽出来写进 system 或"任务卡"，永不参与裁剪 |
| 用户偏好与约束 | 抽出到独立的 `preferences` 字段 |
| 中间工具返回 | 按时间淘汰 + 压成结论 |
| 对话叙述 | 滚动摘要 |

注意第一行：**把任务目标从消息数组里"提"出来**，是比任何压缩算法都有效的做法。它在数组里就会被裁，它在外面的变量里就永远不会被裁。这也是 C15 讲"外部状态"的起点。

## 6. 摘要的两个工程要点

1. **规则优先，模型兜底**。能用规则判断的（超长就截断、字段固定就只留字段），别调模型。摘要才需要模型，因为要「读懂再压缩」。
2. **摘要要可复现**。让摘要调用带固定 prompt 和 `temperature=0`（见 C1-2），否则同一个历史今天压成 A、明天压成 B，任务结果不可复现，违背三条暗线之二「可复现性」（三条暗线：成本意识 / 可复现性 / 上下文预算，见总纲第 7 节）。

再补一条：**摘要结果要能验证**。最便宜的验证是「关键实体是否还在」——把压缩前的数字、ID、日期抽出来做集合比对，缺了就拒绝这次压缩、退回原文（做法同 C7-4 的逐字比对）。这一步是纯字符串操作，零模型成本，却能挡住大部分静默失真。

## 7. 小结

- 三操作：删除最便宜但不可逆，摘要最贵也最危险，保留原文零损失。
- 分界原则：删掉还能不能正确完成？不能就保留；过程已完成、结论有用才摘要；重复失效的才删。
- 「结论替换过程」具体做法：留数值与结论，删"我调了什么、为什么调"。
- 错误记录要压成负向约束，不能整体删除（否则会重复踩坑）。
- 把任务目标提到数组之外，比任何裁剪算法都有效。
- 别按时间砍最老的，按重要性保留。
