# C13-3 · 工具返回的预算黑洞
> 阅读约 10 分钟。目标：处理「工具一次返回几万 token」这个最隐蔽的成本与质量杀手。

## 1. 为什么它是黑洞

历史消息随轮数线性涨，**工具返回可能一步就爆掉**：

- 查数据库返回 5000 行原始 JSON；
- 抓网页返回整页 HTML；
- 读日志返回 200KB 文本。

模型往往只需要其中两三个字段，但**这些全都会塞进消息数组，并且每一轮都要重新付费**（无状态，见 C13-1）。一次 50KB 的工具返回，在后续每一步都重复计费——这是 Agent 账单里最不起眼、却最凶的一笔。

## 2. 四种处理手法

| 手法 | 怎么做 | 适用 |
|---|---|---|
| **截断** | 只保留前 N 字符/前 N 行 | 结果大但「关键信息在前面」 |
| **字段抽取** | 只留需要的字段 | 结构化返回（JSON），字段已知 |
| **落盘 + 引用** | 结果存文件/库，上下文只放句柄 | 大结果、可能二次使用 |
| **分页** | 每次只取一页，模型主动翻页 | 结果巨大且需要浏览 |

四种手法按「信息损失递增、token 节省递增」排序，选择取决于**模型到底要用多少**。

## 3. 最推荐：落盘 + 引用

核心思路是**把「数据」和「数据的引用」分离**：

```python
def search_db(query: str):
    rows = db.query(query)              # 可能几万行
    if len(rows) > 200:                  # 超过阈值就不塞全量
        file_id = save_to_disk(rows)     # 结果落盘
        return {
            "total": len(rows),
            "head": rows[:5],            # 只给前几行让模型有感觉
            "file_id": file_id,          # 引用句柄
            "hint": "数据已落盘，需要看具体行请用 read_file(file_id, offset, limit) 分页读取"
        }
    return {"total": len(rows), "rows": rows}
```

这样上下文里只放 `total` + 前几行 + 句柄，模型需要时再通过 `read_file` 按需取。**这是「按需加载」在工具返回上的应用**（完整版见 C15-3）。

## 4. 两个容易做错的地方

1. **别在 Agent 循环里动态增删工具**。要不要给 `read_file` 这个工具，应该按任务类型**静态划分**，而不是等看到大结果再临时加——那会打碎前缀缓存（见 C7-1 第 3 节）。

2. **摘要和落盘不是二选一，经常是连用**。落盘保留全量（不丢信息），再摘要一句「本次命中 3 条，分别关于 X/Y/Z」放进上下文，让模型先判断要不要读详情。

## 5. 阈值怎么定

「超过多少就该落盘」没有魔法数字，一个可操作的起点：

- 结构化 JSON：超过 200 行（约几千 token）就落盘。
- 自由文本：超过 2000 字符就考虑摘要或落盘。

真正依据是**你的上下文预算**（见 C7-1）：先量出「每轮工具返回平均占多少」，再决定阈值，别拍脑袋。

## 6. 小结

- 工具返回是「一步就爆」的黑洞，且每轮重复计费。
- 四种手法：截断 / 字段抽取 / 落盘+引用 / 分页；落盘+引用最推荐。
- 别动态增删工具（碎缓存）；摘要与落盘常连用；阈值依据上下文预算来定。
