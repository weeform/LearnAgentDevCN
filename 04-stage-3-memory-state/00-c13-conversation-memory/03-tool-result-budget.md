# C13-3 · 工具返回的预算黑洞
> 阅读约 13 分钟。目标：处理「工具一次返回几万 token」这个最隐蔽的成本与质量杀手。

> **与 C7-4 的分工**：C7-4 把「工具返回要落盘」写进了裁剪策略模板；本篇展开为什么要落盘、四种手法的成本对比、阈值怎么定。

## 1. 为什么它是黑洞

历史消息随轮数线性涨，**工具返回可能一步就爆掉**：

- 查数据库返回 5000 行原始 JSON；
- 抓网页返回整页 HTML；
- 读日志返回 200KB 文本。

模型往往只需要其中两三个字段，但**这些全都会塞进消息数组，并且每一轮都要重新付费**（无状态，见 C13-1）。一次 50KB 的工具返回，在后续每一步都重复计费——这是 Agent 账单里最不起眼、却最凶的一笔。

算一下就明白有多凶：一个 50KB 的返回约 1.5 万 token，后面还剩 15 步，就是 22.5 万 token 的重复开销。而模型当初可能只用到了其中一个 `status` 字段。

## 2. 四种处理手法

| 手法 | 怎么做 | 适用 |
|---|---|---|
| **截断** | 只保留前 N 字符/前 N 行 | 结果大但「关键信息在前面」 |
| **字段抽取** | 只留需要的字段 | 结构化返回（JSON），字段已知 |
| **落盘 + 引用** | 结果存文件/库，上下文只放句柄 | 大结果、可能二次使用 |
| **分页** | 每次只取一页，模型主动翻页 | 结果巨大且需要浏览 |

四种手法按「信息损失递增、token 节省递增」排序，选择取决于**模型到底要用多少**。

### 2.1 截断为什么经常是错的

截断看着简单，但它有个致命假设：**关键信息在前面**。而真实数据里经常不是：

- 日志按时间升序，**错误在最后**；
- 数据库按主键排序，**要找的那条在中间**；
- 网页正文前面全是导航与广告。

截断最坏的结果不是"漏了信息"，而是**模型不知道自己漏了**——它看着前面 200 行干净的记录，很自信地得出"数据一切正常"。所以截断必须配一句显式告知：

```python
return {"shown": 200, "total": 5000,
        "note": "仅展示前 200 行，其余未展示。若需完整数据请用 read_file(file_id, offset, limit) 分页读取。"}
```

`note` 这一句的价值远超它的 token 成本：它把"我以为我看全了"变成"我知道我没看全"，模型的行为会完全不同——通常会主动去翻页，而不是下结论。

## 3. 最推荐：落盘 + 引用

核心思路是**把「数据」和「数据的引用」分离**：

```python
def search_db(query: str):
    rows = db.query(query)              # 可能几万行
    if len(rows) > 200:                  # 超过阈值就不塞全量
        file_id = save_to_disk(rows)     # 结果落盘
        return {
            "total": len(rows),
            "head": rows[:5],            # 只给前几行让模型有感觉
            "file_id": file_id,          # 引用句柄
            "hint": "数据已落盘，需要看具体行请用 read_file(file_id, offset, limit) 分页读取"
        }
    return {"total": len(rows), "rows": rows}
```

这样上下文里只放 `total` + 前几行 + 句柄，模型需要时再通过 `read_file` 按需取。**这是「按需加载」在工具返回上的应用**（完整版见 C15-3）。

三个字段各有分工，缺一个都会出问题：

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| `total` | 告诉模型数据规模 | 模型以为只有 5 条，结论失准 |
| `head` | 给模型"数据的形状" | 模型不知道该取哪些字段，乱翻页 |
| `hint` | 告诉模型下一步怎么做 | 模型不知道有分页工具，直接放弃或编造 |

`head` 取 3–5 行就够，它的作用是**让模型知道 schema**，不是让它看数据。取太多等于把黑洞搬回来了一半。

### 3.1 一个真实形态的教训：head 不能代表全部

一个销售数据 Agent，工具返回表头 + 前 5 行。前 5 行恰好是某个大客户的订单，金额都在 10 万以上。模型据此回答"平均订单金额约 12 万"，实际全表均值是 3,800。

问题不在截断，而在**没告诉模型"这只是样例"**。修法有两种，成本都很低：

1. 在 `head` 旁边给出**聚合值**：`{"total": 5000, "sum": 19_000_000, "avg": 3800, "sample": [...]}`——模型要算统计量时直接用聚合值，不需要自己从样例推。
2. 在 `hint` 里明确写「`head` 仅为样例，不代表分布，统计请用 `total`/`avg` 或读取全量」。

这里的原则值得记住：**凡是你替模型做了一次"取样"，就必须同时给它"这个取样不代表全体"的元信息**。否则模型会默认它看到的就是全部——这是它最自然的假设，也是最容易出错的地方。

## 4. 两个容易做错的地方

1. **别在 Agent 循环里动态增删工具**。要不要给 `read_file` 这个工具，应该按任务类型**静态划分**，而不是等看到大结果再临时加——那会打碎前缀缓存（见 C7-1 第 3 节）。

2. **摘要和落盘不是二选一，经常是连用**。落盘保留全量（不丢信息），再摘要一句「本次命中 3 条，分别关于 X/Y/Z」放进上下文，让模型先判断要不要读详情。

第 2 点的价值在于**省掉一次不必要的翻页**。如果模型看到摘要就知道"这 3 条都不是我要的"，它就完全不必调 `read_file`——省下的不只是一次工具调用的 token，还有一整轮往返的延迟。

## 5. 阈值怎么定

「超过多少就该落盘」没有魔法数字，一个可操作的起点：

- 结构化 JSON：超过 200 行（约几千 token）就落盘。
- 自由文本：超过 2000 字符就考虑摘要或落盘。

真正依据是**你的上下文预算**（见 C7-1）：先量出「每轮工具返回平均占多少」，再决定阈值，别拍脑袋。

还有一个更本质的判据：**看这个返回会被引用几次**。

| 引用次数 | 策略 |
|---|---|
| 0–1 次（用完即弃） | 激进：只留摘要 + 关键字段 |
| 2–3 次 | 落盘 + 摘要 + 句柄 |
| 多次反复引用（如主数据表） | 干脆整段保留，压缩反而添乱 |

第三种情况常被忽略：有些数据（比如一份被反复对照的合同条款）**就该完整留在上下文里**。为它做压缩，换来的是模型每次都去翻页、每次都多一轮往返——token 省了，延迟和失败率涨了。

## 6. 小结

- 工具返回是「一步就爆」的黑洞，且每轮重复计费。
- 四种手法：截断 / 字段抽取 / 落盘+引用 / 分页；落盘+引用最推荐。
- 截断必须显式告知"还有多少没展示"，否则模型会以为自己看全了。
- 落盘三件套：`total`、`head`（样例）、`hint`（下一步）；给了样例就要声明它不代表全体。
- 别动态增删工具（碎缓存）；摘要与落盘常连用；阈值依据上下文预算和引用次数来定。
