# C13-4 · 压缩的代价怎么量
> 阅读约 12 分钟。目标：用数字证明你的压缩策略「省钱且不掉链子」，而不是凭感觉。

## 1. 压缩不是免费的

摘要会丢细节、删消息会丢信息，两者都可能让模型**瞎编或答错**。所以压缩的及格线不是「省了多少 token」，而是：

> **成本降了，同时成功率不掉。**

只有省 token、却把任务做坏了，那是失败的压缩。

这句话背后有个容易被忽略的推论：**压缩的收益是有上限的，而损失没有**。一个任务多花 3 块钱是可以接受的，一个任务答错导致客户投诉不是。所以当成本和成功率冲突时，永远站在成功率那边。

## 2. 两个必须同时看的指标

| 指标 | 怎么算 | 回答什么 |
|---|---|---|
| **成本降幅** | 压缩前总 token − 压缩后总 token | 省了多少钱 |
| **成功率变化** | 同一批任务，压缩前后各跑一遍，对比答对率 | 丢了没丢效果 |

只看成本 → 容易过度压缩；只看成功率 → 忽略了你为什么要压缩。**必须成对看。**

但「总 token」这个指标本身有个陷阱：**任务的 token 分布极不均匀**。20 个任务里如果有 2 个特别重（比如要读整份财报），它们可能占了 70% 的 token。这时"总降幅 40%"可能完全来自这 2 个任务，其余 18 个一点没省。

所以除了总量，还要看**中位数**：单任务 token 的中位数降了多少。中位数降幅才是"普遍变便宜了"，总量降幅可能只是"贵的那几个变便宜了"。

## 3. 怎么测：固定评测集，跑两遍

别拿单个任务「感觉变好了」，要建一个**固定的小评测集**（10–20 个代表性任务），同一套任务跑两遍：

1. **基线**：不压缩，记录成功率和总 token。
2. **压缩版**：上你的压缩策略，再跑一遍，记录成功率和总 token。

对比两张表。这是最简单、也最可信的量化方法，和阶段 5 的回归评测是同一个思路（提前用它一点不亏）。

### 3.1 评测集怎么攒（20 条就够）

不用一开始就做正规数据集，从真实流量里挑就行：

| 类别 | 条数 | 从哪来 |
|---|---|---|
| 常规任务 | 8 | 最近的正常请求 |
| 长任务（20 步以上） | 5 | 压缩效果最明显的场景 |
| 边界任务（缺字段、需拒答） | 4 | 曾经出错过的那几条 |
| 依赖早期信息的任务 | 3 | 专门检验"删最老"有没有出事 |

**第四类最关键**：它是专门用来抓"压缩把任务目标删了"这个 bug 的。没有这一类，你的评测会显示"压缩毫无副作用"，然后线上翻车。

### 3.2 「成功率」怎么定义

这是最容易糊弄自己的地方。三种定义，从松到严：

| 定义 | 判法 | 适合 |
|---|---|---|
| 跑通率 | 有没有报错、有没有超时 | 基线，但没有区分度 |
| 格式合规 | 输出能不能被解析、字段齐不齐 | 工程验收 |
| 事实正确 | 关键字段/结论是否与标准答案一致 | **真正的效果指标** |

前两种能自动判，第三种需要人工抽检或写断言（比如"金额必须等于 1280"）。**至少要有一个第三种**，否则你的"成功率 95%"可能只是在说"它没崩溃"。

一个折中的做法：给每个任务配 1–2 条**可自动断言的关键事实**（金额、日期、订单号、是否拒答），其余部分人工抽检 20%。这样既不贵，又能抓住主要退化。

### 3.3 结果长什么样

跑完通常会得到一张这样的表（数字为示意，看趋势）：

| 方案 | 总 token | 中位数 token | 断言通过率 | 结论 |
|---|---|---|---|---|
| 基线（不压缩） | 100% | 100% | 92% | — |
| 只压工具返回 | 58% | 61% | 92% | **划算，直接上** |
| 加滚动摘要 | 34% | 40% | 88% | 有一点损失，可接受 |
| 再加"删最老 30%" | 22% | 28% | 74% | **失败，回退** |

这张表最有价值的信息不在第一列，而在最后一行——**继续压到 22% 时，通过率崩了**。这就是"压缩的悬崖"：在某个点之前几乎无损，越过后急剧恶化。找到自己的悬崖位置，比追求极限压缩重要得多。

上面的数据还能推出一件事：**前三行的收益递减**。「只压工具返回」用一步拿到 42% 的降幅且零损失；之后的滚动摘要只多省 24%，代价是 4 个点的通过率。所以最优解通常是"做前一两步就停"，而不是"压到不能再压"。

## 4. 三种常见的失败模式

1. **过度摘要导致瞎编**：把关键数据也压掉了，模型补不上就开始编。表现是「答案看着像，数字对不上」。
2. **删错约束导致目标漂移**：把早期的重要目标/约束当「旧消息」删了，模型开始自由发挥。
3. **摘要本身不稳定**：摘要调用没固定 `temperature`，同一历史每次压出来不一样，结果不可复现（见 C13-2 第 6 节）。

还有第四种，更隐蔽：**模型不会用你给的取回路径**。

你老老实实做了"落盘 + 引用 + hint"，但模型从来不去调 `read_file`，直接基于 `head` 那 5 行编了个答案。这时候你的压缩在数据上"没有丢信息"（全量还在盘上），在效果上却完全失效了。判据很简单：**看压缩后 `read_file` 的调用次数**。如果长期是 0，说明 hint 没起作用——要么措辞不够明确，要么这个工具根本没进 tools 列表。

## 5. 发现成功率掉了怎么办

按这个顺序排查，别急着调参数：

1. **是不是删掉了「必须保留」的内容**？回看 C13-2 第 2 节的四类，尤其「用户要求记住的」和「未完成的承诺」。
2. **摘要是不是把结论也压没了**？摘要应留结论、压过程；把结论压掉等于白压。
3. **是不是工具返回压太狠**？落盘+引用保留了全量，但如果模型没学会用 `read_file` 去取，等于丢了信息——检查 system prompt 里有没有教它「需要详情就按 hint 读」。

排查时有个技巧：**把失败的那些任务单独跑一次"不压缩"版本**。如果基线也失败，那问题不在压缩，别浪费时间。这个对照只要几分钟，能省掉一整天的瞎调。

## 6. 一条及格线

一个可操作的验收标准：

> 压缩后，**token 降幅 ≥ 40%，且成功率下降 ≤ 5%**，算合格；成功率掉超过 5%，回退粒度（少摘要、多保留）重测。

数字是参考，关键是养成「压缩必量化」的习惯——这正是三条暗线之二「可复现性」在记忆层的落地。

补一句关于"5%"的用法：**它不是绝对值，是相对你当前成功率的容忍度**。基线 92%、压后 87% 是可接受的；基线 70%、压后 65% 就值得警惕——因为低基线说明任务本来就难，压缩带来的额外不确定性会把长尾任务推过临界点。

## 7. 小结

- 压缩及格线：成本降、成功率不掉，两个指标成对看。
- 用固定评测集跑「基线 vs 压缩」两遍，别凭感觉；评测集要有"依赖早期信息"这一类。
- 成功率要有至少一个"事实正确"级别的断言，否则只是在测"没崩溃"。
- 找自己的"压缩悬崖"：多数情况下做前一两步就够，压到极限必然掉效果。
- 失败就查四件事：删没删必须保留的、摘要压没压掉结论、工具返回压太狠没给取回路径、模型有没有真的去取回。
