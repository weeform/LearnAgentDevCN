# C14-1 · 什么时候根本不需要 RAG
> 阅读约 12 分钟。目标：在上 RAG 之前，先回答「我到底需不需要 RAG」——这个被大多数人跳过、却最值钱的问题。

## 1. 前提变了，问题要重问

RAG 的经典动机是「上下文窗口太小，装不下我的资料」。但 2026 年上下文窗口已经到 1M+，很多人第一反应是：**那还要 RAG 干嘛，全塞进去不就行了？**

答案是：**长上下文不是 RAG 的替代品**。三条硬约束先摆出来（数值为量级参考，以具体模型和当时的评测为准）：

1. **质量会随长度衰减**：多个长上下文评测显示，上下文越长，模型对特定信息的定位越差，中间位置尤甚（「lost in the middle」，即关键信息在中间时最容易被漏）。塞得越多，模型越抓不住重点。
2. **成本会爆**：长上下文每次请求都按全量 token 计费，而 RAG 只按检索到的少量 chunk 计费——生产量级下，长上下文单次查询成本可高出 1–2 个数量级（工程估算，取决于上下文长度与 chunk 规模）。
3. **延迟难忍**：超长上下文的 prefill 时间以数十秒计（取决于硬件与模型规模），交互场景很难用。

结论一句话：

> 长上下文窗口解决的是「能不能装下」，不是「能不能用好」。

## 2. 什么时候该用长上下文（而不是 RAG）

长上下文真正胜出的场景，是**对「有界文档集」做整体推理**：

- 合同比对：要通读两份合同的每一个条款找差异，不能靠检索挑几段。
- 代码库全局分析：要理解跨文件的调用关系，片段检索会割裂上下文。
- 文献综述：要在几十篇论文间找关联、做综合判断。

共同特征：**文档集有明确边界，且任务需要「整体」，不是「定位」**。

## 3. 什么时候该用 RAG

RAG 胜在「从海量、无界、会增长的内容里快速定位相关片段」：

- 知识库很大且持续增长（客服文档、公司 wiki、FAQ）。
- 每次查询只需要一小部分内容，不需要全局视角。
- 对成本和延迟敏感，要控制每请求的 token。

共同特征：**内容海量且不断变，任务只需「定位」，不需要「通读」**。

## 4. 2026 的最佳实践：混合式

现实里多数场景是「两者都要」，主流做法是**混合式**：

> **RAG 当注意力调度器，长上下文当合成层。**

具体：RAG 先检索 top 20–40 个 chunks（注意：不再是老做法里的 5–10 个，因为要给长上下文模型足够的「视野」），把这些 chunk 交给长上下文模型做综合与回答。

- RAG 负责「把相关的东西捞出来」（省成本、控延迟）。
- 长上下文负责「把捞出来的东西读懂、综合」（保质量）。

## 5. 一张决策表

| 你的情况 | 选 |
|---|---|
| 文档集有界、任务需全局推理（合同、代码、综述） | 长上下文 |
| 内容海量、只定位片段、对成本延迟敏感 | RAG |
| 内容多、又要综合（多数企业场景） | 混合式（RAG 检索 + 长上下文合成） |
| 内容很小、每次都能全塞 | 直接塞，别上 RAG |

最后一行最容易忽略：**如果你的资料每次都能完整放进窗口，且不超预算，就直接塞——为一个 3 页文档搭一套 RAG 是过度设计**。

## 6. 小结

- 长上下文解决「装得下」，不解决「用得好」：质量、成本、延迟三方面都不如「精准检索」。
- 长上下文赢在有界文档的整体推理；RAG 赢在海量内容的快速定位。
- 2026 主流是混合式：RAG 检索 top 20–40 chunks，交给长上下文合成。
