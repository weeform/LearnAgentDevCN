# C14-1 · 什么时候根本不需要 RAG
> 阅读约 14 分钟。目标：在上 RAG 之前，先回答「我到底需不需要 RAG」——这个被大多数人跳过、却最值钱的问题。

## 1. 前提变了，问题要重问

RAG 的经典动机是「上下文窗口太小，装不下我的资料」。但 2026 年上下文窗口已经到 1M+，很多人第一反应是：**那还要 RAG 干嘛，全塞进去不就行了？**

答案是：**长上下文不是 RAG 的替代品**。三条硬约束先摆出来（数值为量级参考，以具体模型和当时的评测为准）：

1. **质量会随长度衰减**：多个长上下文评测显示，上下文越长，模型对特定信息的定位越差，中间位置尤甚（「lost in the middle」，即关键信息在中间时最容易被漏）。塞得越多，模型越抓不住重点。
2. **成本会爆**：长上下文每次请求都按全量 token 计费，而 RAG 只按检索到的少量 chunk 计费——生产量级下，长上下文单次查询成本可高出 1–2 个数量级（工程估算，取决于上下文长度与 chunk 规模）。
3. **延迟难忍**：超长上下文的 prefill 时间以数十秒计（取决于硬件与模型规模），交互场景很难用。

结论一句话：

> 长上下文窗口解决的是「能不能装下」，不是「能不能用好」。

### 1.1 把成本差算成具体数字

抽象说「差 1–2 个数量级」没有痛感，代入一组常见数字（单价按输入 $3/M token 示意，实际按账单替换）：

| 方案 | 每次请求的输入 | 单次成本 | 日 1 万次 |
|---|---|---|---|
| 全量塞 200K tokens | 200,000 | $0.60 | $6,000 |
| RAG 检索 30 chunk（约 12K） | 12,000 | $0.036 | $360 |

差 16 倍。而且这个差距**不会随模型降价消失**，因为它来自输入量的比例差，不是单价差。

更值得注意的是：**多出来的 188K token 里，绝大多数与当前问题无关**。你付了 16 倍的钱，买的却是更多的噪声——这也解释了为什么长上下文方案的答案质量往往还不如精准检索。

## 2. 什么时候该用长上下文（而不是 RAG）

长上下文真正胜出的场景，是**对「有界文档集」做整体推理**：

- 合同比对：要通读两份合同的每一个条款找差异，不能靠检索挑几段。
- 代码库全局分析：要理解跨文件的调用关系，片段检索会割裂上下文。
- 文献综述：要在几十篇论文间找关联、做综合判断。

共同特征：**文档集有明确边界，且任务需要「整体」，不是「定位」**。

再补一个判据：**问题里有没有"跨文档"的关系**。如果用户问的是「A 文档第 3 条和 B 文档第 7 条冲突吗」，那是跨文档推理——检索很可能只捞回其中一份，答案就残缺了。这类任务，长上下文（或至少要保证两份都进上下文）不是可选项。

## 3. 什么时候该用 RAG

RAG 胜在「从海量、无界、会增长的内容里快速定位相关片段」：

- 知识库很大且持续增长（客服文档、公司 wiki、FAQ）。
- 每次查询只需要一小部分内容，不需要全局视角。
- 对成本和延迟敏感，要控制每请求的 token。

共同特征：**内容海量且不断变，任务只需「定位」，不需要「通读」**。

## 4. 2026 的最佳实践：混合式

现实里多数场景是「两者都要」，主流做法是**混合式**：

> **RAG 当注意力调度器，长上下文当合成层。**

具体：RAG 先检索 top 20–40 个 chunks（注意：不再是老做法里的 5–10 个，因为要给长上下文模型足够的「视野」），把这些 chunk 交给长上下文模型做综合与回答。

- RAG 负责「把相关的东西捞出来」（省成本、控延迟）。
- 长上下文负责「把捞出来的东西读懂、综合」（保质量）。

这里有个容易忽略的工程含义：**top-k 从 5 提到 30，召回率会涨，但 token 也会涨 6 倍**。所以混合式真正的调优点不是"要不要多捞"，而是"多捞之后怎么排"——这就是 C14-4 讲重排的原因：先粗召回 30–40 个，重排后只把前 8–10 个交给模型，兼顾召回与成本。

## 5. 一张决策表

| 你的情况 | 选 |
|---|---|
| 文档集有界、任务需全局推理（合同、代码、综述） | 长上下文 |
| 内容海量、只定位片段、对成本延迟敏感 | RAG |
| 内容多、又要综合（多数企业场景） | 混合式（RAG 检索 + 长上下文合成） |
| 内容很小、每次都能全塞 | 直接塞，别上 RAG |

最后一行最容易忽略：**如果你的资料每次都能完整放进窗口，且不超预算，就直接塞——为一个 3 页文档搭一套 RAG 是过度设计**。

### 5.1 上 RAG 之前，先走这四级阶梯

RAG 不是第一个选项，是第四、五个。真正该按这个顺序试：

| 级别 | 方案 | 什么时候够用 | 成本 |
|---|---|---|---|
| 1 | **直接塞** | 资料 < 20K token，且不常变 | 最低 |
| 2 | **结构化查询** | 数据有明确字段（订单、用户、指标） | 低，且**准确率最高** |
| 3 | **关键词/全文检索** | 用户用语与文档用语一致（如查"退款政策"） | 低 |
| 4 | **向量检索（RAG）** | 语义模糊、同义表达多、跨文档归纳 | 中 |
| 5 | **混合检索 + 重排** | 上一级召回不够，且有评测手段 | 高（真金白银那一步） |

这张表的用处在第 2 行：**很多被叫做"知识库问答"的需求，本质是查数据库**。用户问「我上个月的订单到哪了」，正确答案不是从文档里检索出来的，是 `SELECT` 出来的。用向量检索去答这类问题，准确率会低得莫名其妙——因为你要的信息根本不在"文档语义"里，它在一个结构化的表里。

一个具体的失败案例：某团队把订单 FAQ 和订单状态混在一个向量库里。用户问「订单 A-1024 的退款到账了吗」，检索召回了《退款政策说明》，模型照着政策回答"一般 3–7 个工作日到账"——听起来对，实际用户的订单**昨天就退完了**。这不是检索质量的问题，是**选错了数据源**。

**判断方法**：问自己「这个答案存不存在于某个字段里？」如果存在，就先查字段，别检索文本。

## 6. 小结

- 长上下文解决「装得下」，不解决「用得好」：质量、成本、延迟三方面都不如「精准检索」。
- 长上下文赢在有界文档的整体推理（尤其跨文档关系）；RAG 赢在海量内容的快速定位。
- 2026 主流是混合式：RAG 检索 top 20–40 chunks（可先粗召回再重排），交给长上下文合成。
- 上 RAG 前先走四级阶梯：直接塞 → 结构化查询 → 全文检索 → 向量检索；很多"知识库"需求其实是 SQL。

## 思考题

1. 长上下文「装得下」为什么≠「用得好」？从质量、成本、延迟三个维度说。
2. 上 RAG 之前的四级阶梯是什么？为什么很多「知识库需求」其实是 SQL？
3. 「混合式」为什么成了当前的主流答案？它各取了什么长处？

<details>
<summary>参考思路</summary>

1. 质量：无关内容稀释注意力，模型容易漏掉关键段；成本：每次全量重发；延迟：prefill 越长首字越慢。精准检索三方面都更优。
2. 直接塞 → 结构化查询 → 全文检索 → 向量检索。结构化数据（订单、库存、指标）用 SQL 精确且便宜，用向量检索是拿模糊工具解决精确问题。
3. RAG 负责从海量内容里定位候选（可再重排），长上下文负责在候选里做整体推理与合成。一个管「找得到」，一个管「想得清」。
