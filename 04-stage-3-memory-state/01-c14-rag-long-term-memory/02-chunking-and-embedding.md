# C14-2 · 切分与 Embedding
> 阅读约 14 分钟。目标：把知识切成「可检索的块」，并选对 Embedding 模型——RAG 链路的前两环。

## 1. 切分为什么决定一切

检索的最小单位是「块」（chunk）。块切得不好，后面检索、重排再努力都白搭：

- **块太大**：一个块里混了多个主题，检索到的「相关块」里其实大部分不相关，还浪费 token。
- **块太小**：一个完整的意思被切成几片，检索只能命中半句话，上下文割裂。

一句话：**块的边界，最好和「一个完整意思」的边界重合。**

这个说法有个容易忽略的推论：**"完整意思"的粒度取决于问题，而不是取决于文本**。同一份《员工手册》，如果用户问"年假有几天"，一个条款就够了；如果问"请假流程是什么"，需要跨三个条款。**你没法同时最优，只能按主要问题类型选粒度**——这也解释了为什么元数据（下面第 4 节）比切分参数更重要：它让你能在检索后按需扩大范围。

## 2. 三种切分策略

| 策略 | 做法 | 适用 |
|---|---|---|
| **按段落** | 按自然段 / 换行切 | 通用文本，最简单 |
| **按语义** | 按主题边界切（用标题、语义相似度断点） | 结构化文档（手册、规范） |
| **按结构** | 按标题层级 / 章节 / 代码函数切 | 代码库、带目录的文档 |

工程上常用「**结构 + 段落**」的组合：先按标题/章节切大块，再在大块内按段落切到合适大小。纯按固定字符数硬切是最省事、也最差的做法——它会把一句话从中间劈开。

### 2.1 硬切的三种典型破坏

固定 500 字符切分看起来"均匀漂亮"，但会制造三类无法修复的坏块：

**破坏一：把表格切成两半。**

```
块 37 结尾：
| 产品 | 价格 |

块 38 开头：
|---|---|
| A | 100 |
```

块 37 里有个孤立表头，块 38 里有个没有表头的数据行。**两块都不可用**，而且检索时很可能只命中其中一块。表格必须整体成块，哪怕它超长。

**破坏二：把"条件 + 结论"分开。**

```
块 12：若员工连续工作满 10 年，可享受额外 5 天年假。
块 13：以上规定不适用于试用期员工。
```

看块 12 的人（和模型）会得出"满 10 年就能多 5 天"的结论，而真正适用的例外在下一块里。**这是 RAG 里最常见的"答对了半句"型错误**——答案不算错，就是不完整。

**破坏三：把列表的"总述"和"条目"分开。**「以下三类情况需要审批：」在一个块里，三个条目在下一个块里。

三种破坏的共同点：**它们都不影响"检索命中"，只影响"命中后能不能读懂"**。所以你的召回率指标会很漂亮，答案质量却很糟——这就是为什么 C14-5 要坚持测端到端答案，而不只测召回。

## 3. 块大小的经验区间

没有魔法数字，一个可操作的起点：

- 通用文本：**300–800 token** 一块。
- 代码：**一个函数 / 一个类** 一块，别按行数硬切。
- 需要更多上下文的任务：先切小块存索引，检索时再「取相邻块」补全（见下）。

关键技巧：**检索时取「命中块 + 前后相邻块」**，用小块保证精准，用相邻块补足上下文——这样既避免了块太大，又不怕块太小。

「取相邻块」需要你的存储支持**有序邻居查询**：每个块要带 `doc_id` + `chunk_index`，取邻居就是查 `chunk_index ± 1`。这个设计在初期加，两行代码；等到上线后想补，就要重跑全量索引。

## 4. 元数据：比切分参数更重要

一个只存 `{id, text, vector}` 的库，做不出好的 RAG。因为**检索之后你需要做很多决策，而决策依赖元数据**。

至少要存的字段：

| 字段 | 用途 |
|---|---|
| `doc_id` / `chunk_index` | 取相邻块、去重、排序 |
| `source` / `url` | 引用出处（用户要能点开原文） |
| `title` / `section` | 给模型"这段来自哪一章"的上下文 |
| `updated_at` | 时效判断：旧文档降权 |
| `acl` / `tenant` | 权限过滤：**必须在检索前过滤，不能检索后再删** |

最后一行是安全要求，不是优化项。如果你先检索 20 个块、再剔除用户无权看的，那么：
1. 有效候选变少，答案质量下降；
2. 更糟的是，被剔除的过程可能已经在日志、缓存或模型输出里留下了痕迹。

**正确做法是把权限条件带进向量检索的过滤参数**（主流向量库都支持 metadata filter），让它从头就不参与候选。

## 5. Embedding 模型怎么选

Embedding 把文本变成向量，向量越近语义越近。选型看四个维度：

| 维度 | 要问什么 |
|---|---|
| 语言 | 是否支持中文？很多英文模型对中文效果打折 |
| 维度 | 维数影响存储与检索成本；检索效果主要看模型本身，需在检索基准上评测 |
| 长度 | 单条文本最大支持多少 token，超了会被截断 |
| 价格/部署 | 云 API 按量计费，还是本地开源模型免费跑 |

一个常见误区：**别拿「生成模型」当「Embedding 模型」用**。Embedding 需要专门的检索优化模型（生成模型也能出向量，但检索效果差且贵）。选模型前先看它在「检索基准」上的表现，而不是看它「名气大」。

还有个现实约束：**换 Embedding 模型 = 重建全量索引**。这件事在原型期无感，在百万级文档时是一次真正的迁移工程。所以选型时多花一天做对比评测，比上线后换模型便宜得多。

## 6. Embedding 的三个坑

1. **忽略最大长度**：Embedding 模型通常有输入上限（如 512、8192 token），超长文本会被静默截断——你存的和你想存的不是一回事。所以切分要配合模型的长度上限来定。
2. **不归一化**：若用「点积」代替余弦相似度，向量必须先归一化成单位长度（否则点积 ≠ 余弦）。不少库默认帮你做了，但自己手写点积相似度时容易漏。
3. **「同一个意思」在不同语言/领域的向量可能不相近**：检索质量最终靠评测验证（见 C14-5），别默认「模型选了就对」。

第 1 条值得再强调一次它的隐蔽性：**截断是静默的**。你入库时不会报错，检索时也不会报错，只是那篇 3000 字文档的后半部分永远检索不到。表现是"有些问题怎么都答不对"，排查成本极高。**入库时打印一次实际 token 数并与模型上限比对**，两行日志能省掉几天的排查。

## 7. 小结

- 块边界要贴合「完整意思」，结构+段落组合切分，别硬按字符数切；硬切会拆散表格、条件与结论、总述与条目。
- 块大小 300–800 token 起手；检索时取「命中块+相邻块」补上下文（需要 `doc_id`+`chunk_index`）。
- 元数据不是可选项：引用、时效、权限过滤都靠它；**权限必须在检索前过滤**。
- Embedding 看语言/维度/长度/价格四维；别拿生成模型当 Embedding，注意长度上限（静默截断）与归一化；换模型 = 重建索引。
