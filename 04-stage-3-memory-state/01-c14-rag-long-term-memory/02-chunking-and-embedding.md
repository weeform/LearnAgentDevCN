# C14-2 · 切分与 Embedding
> 阅读约 12 分钟。目标：把知识切成「可检索的块」，并选对 Embedding 模型——RAG 链路的前两环。

## 1. 切分为什么决定一切

检索的最小单位是「块」（chunk）。块切得不好，后面检索、重排再努力都白搭：

- **块太大**：一个块里混了多个主题，检索到的「相关块」里其实大部分不相关，还浪费 token。
- **块太小**：一个完整的意思被切成几片，检索只能命中半句话，上下文割裂。

一句话：**块的边界，最好和「一个完整意思」的边界重合。**

## 2. 三种切分策略

| 策略 | 做法 | 适用 |
|---|---|---|
| **按段落** | 按自然段 / 换行切 | 通用文本，最简单 |
| **按语义** | 按主题边界切（用标题、语义相似度断点） | 结构化文档（手册、规范） |
| **按结构** | 按标题层级 / 章节 / 代码函数切 | 代码库、带目录的文档 |

工程上常用「**结构 + 段落**」的组合：先按标题/章节切大块，再在大块内按段落切到合适大小。纯按固定字符数硬切是最省事、也最差的做法——它会把一句话从中间劈开。

## 3. 块大小的经验区间

没有魔法数字，一个可操作的起点：

- 通用文本：**300–800 token** 一块。
- 代码：**一个函数 / 一个类** 一块，别按行数硬切。
- 需要更多上下文的任务：先切小块存索引，检索时再「取相邻块」补全（见下）。

关键技巧：**检索时取「命中块 + 前后相邻块」**，用小块保证精准，用相邻块补足上下文——这样既避免了块太大，又不怕块太小。

## 4. Embedding 模型怎么选

Embedding 把文本变成向量，向量越近语义越近。选型看四个维度：

| 维度 | 要问什么 |
|---|---|
| 语言 | 是否支持中文？很多英文模型对中文效果打折 |
| 维度 | 维数影响存储与检索成本；检索效果主要看模型本身，需在检索基准上评测 |
| 长度 | 单条文本最大支持多少 token，超了会被截断 |
| 价格/部署 | 云 API 按量计费，还是本地开源模型免费跑 |

一个常见误区：**别拿「生成模型」当「Embedding 模型」用**。Embedding 需要专门的检索优化模型（生成模型也能出向量，但检索效果差且贵）。选模型前先看它在「检索基准」上的表现，而不是看它「名气大」。

## 5. Embedding 的三个坑

1. **忽略最大长度**：Embedding 模型通常有输入上限（如 512、8192 token），超长文本会被静默截断——你存的和你想存的不是一回事。所以切分要配合模型的长度上限来定。
2. **不归一化**：若用「点积」代替余弦相似度，向量必须先归一化成单位长度（否则点积 ≠ 余弦）。不少库默认帮你做了，但自己手写点积相似度时容易漏。
3. **「同一个意思」在不同语言/领域的向量可能不相近**：检索质量最终靠评测验证（见 C14-5），别默认「模型选了就对」。

## 6. 小结

- 块边界要贴合「完整意思」，结构+段落组合切分，别硬按字符数切。
- 块大小 300–800 token 起手；检索时取「命中块+相邻块」补上下文。
- Embedding 看语言/维度/长度/价格四维；别拿生成模型当 Embedding，注意长度上限与归一化。
