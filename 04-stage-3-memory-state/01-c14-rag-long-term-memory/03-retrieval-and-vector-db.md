# C14-3 · 检索与向量库选型
> 阅读约 12 分钟。目标：搭对检索那一环——为什么混合检索几乎总更好，以及向量库选本地还是云。

## 1. 检索的两种基本方式

| 方式 | 原理 | 强项 | 弱项 |
|---|---|---|---|
| **关键词检索**（BM25） | 按词频精确匹配 | 人名、编号、代码、专有名词 | 不懂同义词、不懂语义 |
| **向量检索** | 按语义相似度 | 同义改写、模糊语义 | 精确匹配反而不行 |

一个经典翻车：用户查「**身份证号 110101**」，向量检索可能返回一堆「证件、身份」相关的段落却漏掉真正含这串数字的那段；而关键词检索一抓一个准。反过来，用户查「**怎么给手机充电更快**」，关键词检索会漏掉所有写「**快充技巧**」却没有「充电」「更快」这两个词的段落。

**两者是互补的，不是替代的。**

## 2. 混合检索：向量 + 关键词

做法：两条检索各跑一遍，把结果**合并去重**后再重排。这几乎总是比单用任一更好——尤其当你的知识库同时有「自然语言描述」和「精确值」（编号、型号、代码、日期）时。

一个可操作的起点：

1. 向量检索取 top 50，关键词检索取 top 50。
2. **融合排名**（如 RRF，Reciprocal Rank Fusion：对每条结果按它在两种检索里的排名倒数求和，再统一排序），而不是简单去重——「两种检索都排得靠前」的结果会自然浮上来。
3. 交给重排（rerank，见 C14-4）取最终 top k。

混合检索的额外成本是「多跑一次关键词索引」，但它便宜、可复现、且补上向量检索最怕的精确匹配缺口，**默认就上**。

## 3. top-k 怎么定

- 只做问答、要精准：top-k 取 5–10。
- 要交给长上下文模型做合成（C14-1 的混合式）：top-k 取 **20–40**。
- 有 rerank 时：初检索可以多取（50–100），让 rerank 再筛，别在一开始就砍太狠。

## 4. 向量库选型：本地 vs 云

| 维度 | 本地库（Chroma / FAISS / Milvus 单机 等） | 云服务（厂商托管的向量库） |
|---|---|---|
| 启动成本 | 低，pip 装上就能跑 | 要开通、配置 |
| 规模上限 | 内存/磁盘决定，单机有限 | 弹性，海量向量 |
| 运维 | 自己管 | 托管，省心 |
| 延迟 | 本地极低 | 走网络，略高 |
| 适合 | 原型、个人项目、中小知识库 | 生产、大规模、多用户 |

判断标准很朴素：**数据量多大、要不要多人共享、你愿不愿意运维**。学习阶段和中小项目，本地库足够；等知识库到百万级向量、要多副本高可用，再上云服务。

## 5. 检索质量的唯一裁判是评测

无论选什么库、什么策略，**最终都要用评测集说话**（见 C14-5）：

> 建 50–100 条「问题 → 正确答案所在 chunk」的评测集，量两件事：**召回率**（正确答案有没有被捞进 top-k）和 **MRR**（正确答案排第几）。

没有这组数字，你的「选型」只是玄学。这也是阶段 5 评测（C20）的提前演练。

## 6. 小结

- 向量抓语义、关键词抓精确，混合检索默认就上。
- top-k：精准问答 5–10，交长上下文合成 20–40，有 rerank 可初检索放宽到 50–100。
- 本地库 vs 云服务看规模、共享需求、运维意愿；学习阶段本地足够。
- 检索质量用召回率 + MRR 评测集说话，别凭感觉。
