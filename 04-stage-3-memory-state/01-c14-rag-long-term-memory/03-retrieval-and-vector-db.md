# C14-3 · 检索与向量库选型
> 阅读约 14 分钟。目标：搭对检索那一环——为什么混合检索几乎总更好，以及向量库选本地还是云。

## 1. 检索的两种基本方式

| 方式 | 原理 | 强项 | 弱项 |
|---|---|---|---|
| **关键词检索**（BM25） | 按词频精确匹配 | 人名、编号、代码、专有名词 | 不懂同义词、不懂语义 |
| **向量检索** | 按语义相似度 | 同义改写、模糊语义 | 精确匹配反而不行 |

一个经典翻车：用户查「**身份证号 110101**」，向量检索可能返回一堆「证件、身份」相关的段落却漏掉真正含这串数字的那段；而关键词检索一抓一个准。反过来，用户查「**怎么给手机充电更快**」，关键词检索会漏掉所有写「**快充技巧**」却没有「充电」「更快」这两个词的段落。

**两者是互补的，不是替代的。**

这个互补性有个更本质的解释：**它们错的方式不一样**。关键词检索的漏，是"说法不同"；向量检索的漏，是"精确值被语义稀释"。两种错误几乎不重叠，所以合并它们的召回率会明显高于任一单独使用——这正是混合检索几乎总更好的原因，不是玄学。

## 2. 混合检索：向量 + 关键词

做法：两条检索各跑一遍，把结果**合并去重**后再重排。这几乎总是比单用任一更好——尤其当你的知识库同时有「自然语言描述」和「精确值」（编号、型号、代码、日期）时。

一个可操作的起点：

1. 向量检索取 top 50，关键词检索取 top 50。
2. **融合排名**（如 RRF，Reciprocal Rank Fusion：对每条结果按它在两种检索里的排名倒数求和，再统一排序），而不是简单去重——「两种检索都排得靠前」的结果会自然浮上来。
3. 交给重排（rerank，见 C14-4）取最终 top k。

RRF 的公式很朴素，就是排名倒数的加权和：

```
score(d) = Σ  1 / (k + rank_i(d))
          i∈检索源
```

`k` 通常取 60（来自原论文的经验值），作用是**压平头部差距**：不取 `k` 时，第 1 名得 1.0、第 2 名得 0.5，差距太大；取 `k=60` 后是 1/61 与 1/62，几乎持平。这样"在两个列表里都排前 10"会比"在一个列表里排第 1、另一个里没有"得分更高——而这正是我们要的效果。

代码不到十行：

```python
def rrf(rank_lists: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores = {}
    for ranks in rank_lists:
        for pos, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + pos)
    return sorted(scores.items(), key=lambda x: -x[1])
```

两个实现细节容易错：**排名从 1 开始**（从 0 开始会让第 1 名得 1/60 而不是 1/61，影响很小但不规范）；**去重发生在 RRF 之后**，如果先去重再算分，同一个 doc 在两路里的重复投票就被抹掉了。

混合检索的额外成本是「多跑一次关键词索引」，但它便宜、可复现、且补上向量检索最怕的精确匹配缺口，**默认就上**。

## 3. top-k 怎么定

- 只做问答、要精准：top-k 取 5–10。
- 要交给长上下文模型做合成（C14-1 的混合式）：top-k 取 **20–40**。
- 有 rerank 时：初检索可以多取（50–100），让 rerank 再筛，别在一开始就砍太狠。

### 3.1 top-k 取太小的代价是"静默失败"

top-k 太小（比如 3）最危险的地方不是答得差，而是**你无法从答案里看出检索漏了**。模型拿到 3 个不相关的块，通常不会说"我没找到"，而是**用这 3 块的边角信息拼一个看起来合理的答案**。

这类失败的排查成本极高，因为表现和"模型能力不足"一模一样。所以有个反直觉的建议：**调试期把 top-k 开大**（20–30），先确认"正确答案在不在候选里"。答案在，才说明是排序问题；答案不在，才说明是检索或切分问题。两种问题的修法完全不同。

一个便宜的诊断脚本：

```python
# 对每条评测问题，检查正确答案所在 chunk 是否出现在 top-N 里
for q in eval_set:
    hits = retriever.search(q.text, top_k=50)
    rank = next((i for i, h in enumerate(hits, 1) if h.id == q.gold_chunk_id), None)
    print(q.id, "rank=", rank)     # rank=None 说明 50 个里都没有：检索/切分问题
```

如果大部分问题 `rank=None`，别调 top-k，去查切分和 Embedding；如果 `rank` 集中在 10–30，那是排序问题，上重排（C14-4）。**这个区分能省掉大量盲目试错。**

## 4. 向量库选型：本地 vs 云

| 维度 | 本地库（Chroma / FAISS / Milvus 单机 等） | 云服务（厂商托管的向量库） |
|---|---|---|
| 启动成本 | 低，pip 装上就能跑 | 要开通、配置 |
| 规模上限 | 内存/磁盘决定，单机有限 | 弹性，海量向量 |
| 运维 | 自己管 | 托管，省心 |
| 延迟 | 本地极低 | 走网络，略高 |
| 适合 | 原型、个人项目、中小知识库 | 生产、大规模、多用户 |

判断标准很朴素：**数据量多大、要不要多人共享、你愿不愿意运维**。学习阶段和中小项目，本地库足够；等知识库到百万级向量、要多副本高可用，再上云服务。

有个不常被提到的选型因素：**你需不需要"混合检索"和"元数据过滤"**。有些轻量本地库只支持纯向量相似度，做不了 BM25 也不支持带条件的过滤——那上面第 2 节和第 4 节讲的方案就落不了地。选库前先确认这两个能力，别等写完代码才发现。

## 5. 检索质量的唯一裁判是评测

无论选什么库、什么策略，**最终都要用评测集说话**（见 C14-5）：

> 建 50–100 条「问题 → 正确答案所在 chunk」的评测集，量两件事：**召回率**（正确答案有没有被捞进 top-k）和 **MRR**（正确答案排第几）。

没有这组数字，你的「选型」只是玄学。这也是阶段 5 评测（C20）的提前演练。

两个指标分别管什么，值得分清：

| 指标 | 算法 | 反映什么 | 掉了说明 |
|---|---|---|---|
| Recall@k | 正确答案命中 top-k 的比例 | **能不能捞到** | 切分/Embedding/检索方式有问题 |
| MRR | `mean(1 / 正确答案的排名)` | **捞得准不准** | 排序有问题，该上重排 |
| Precision@k | top-k 里相关块的比例 | 噪声多少 | 块太大、或多路融合太宽松 |

三者的读法：**Recall 低是根本问题**（后面怎么排都没用），**MRR 低是排序问题**（重排能救），**Precision 低是噪声问题**（浪费 token，也干扰模型判断）。

实践中常见的顺序是：先保 Recall（多路召回、放大 k），再提 MRR（重排），最后控 Precision（截断）。反过来做——先追精度——会导致你的候选集本来就缺正确答案，无论怎么调都上不去。

## 6. 小结

- 向量抓语义、关键词抓精确，两者错法不重叠，混合检索默认就上。
- 融合用 RRF（`1/(k+rank)` 求和）而非简单去重；调试期把 top-k 放大，先判断是"没捞到"还是"没排好"。
- top-k：精准问答 5–10，交长上下文合成 20–40，有 rerank 可初检索放宽到 50–100。
- 本地库 vs 云服务看规模、共享需求、运维意愿；**先确认库支持混合检索与元数据过滤**。
- 检索质量用 Recall / MRR / Precision 说话：先保 Recall，再提 MRR，最后控 Precision。

2. 融合为什么用 RRF 而不是简单去重合并？
3. 调试检索时为什么先把 top-k 放大？它帮你区分哪两种失败？

1. 向量抓语义（同义改写能召回，但精确编号、专有名词容易错），关键词抓字面（精确匹配强，但换个说法就丢）。错法不重叠，叠加才覆盖全。
