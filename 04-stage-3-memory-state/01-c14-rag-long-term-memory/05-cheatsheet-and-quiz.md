# C14-5 · 速查表与自测
> 阅读约 10 分钟。目标：把 C14 全链路固化成一页，并用自测检验。

## 速查表

### 长上下文 vs RAG 决策

| 情况 | 选 |
|---|---|
| 有界文档、需整体推理 | 长上下文 |
| 海量内容、只定位片段 | RAG |
| 内容多又要综合 | 混合式（RAG 检索 + 长上下文合成） |
| 内容小、每次能全塞 | 直接塞，别上 RAG |

### RAG 链路五环

| 环节 | 要点 |
|---|---|
| 切分 | 结构+段落，块 300–800 token，边界贴合完整意思 |
| Embedding | 看语言/维度/长度/价格；别拿生成模型当 Embedding |
| 检索 | 混合（向量+关键词），精准取 5–10、合成取 20–40 |
| 重排 | 交叉编码器只重排 top 50–100，取最终 top 5–20 |
| 维护 | 去重、过期、矛盾（新覆盖旧+标注来源时间）、污染 |

### 记忆维护四件套

去重（相似度阈值合并）、过期（时间戳清理）、矛盾（新覆盖旧 + 显式冲突）、污染（准入校验 + 可信度标注）。

## 自测题

1. 一个 3 页的产品说明文档，每次都能完整放进窗口。要不要上 RAG？为什么？
2. 用户知识库里既有「自然语言的产品介绍」，又有「精确的型号编号」。纯向量检索会出什么问题？怎么解决？
3. 你的检索召回率很高（正确答案总在 top-50 里），但模型还是经常答错。最可能是什么环节出问题？
4. 用户换了新的退货政策，但旧政策还在知识库里被检索到。这属于哪类记忆问题？怎么处理？
5. 「切分」为什么不能按固定字符数硬切？

## 参考答案要点

1. 不上。每次能全塞且不超预算，直接塞即可，搭 RAG 是过度设计（见 C14-1 决策表）。
2. 向量检索不懂精确匹配，可能漏掉含型号的那段。用混合检索（向量 + BM25 关键词）合并去重。
3. 很可能是「排序」问题而非「召回」问题——召回够但排错位置。加 rerank（交叉编码器重排），把最相关的排前面。
4. 属于「过期」记忆。做法：每条记忆带时间戳，新政策写入时覆盖/标记旧政策失效，定期清理。
5. 固定字符数会把一句话从中间劈开，破坏语义完整性；块边界应贴合「完整意思」（按段落/结构切）。
