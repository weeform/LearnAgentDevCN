# C15-1 · 状态外置：任务状态机
> 阅读约 13 分钟。目标：把「任务进度」从隐含在消息里，改成显式的、可恢复的状态机。

## 1. 问题：进度藏在消息里，一挂就丢

阶段 2 的 Agent，进度是**隐含在消息数组里**的：走到第几步、查过什么、结果是什么，全靠消息里那堆文本承载。后果：

- 进程一挂，消息数组没了，**进度归零**。
- 想「人工看一眼进度」？只能读一大堆消息文本。
- 想「从第 15 步重来」？做不到，只能从头跑。

一句话：

> 把「状态」和「承载状态的消息」混在一起，状态就成了消息的附属品——消息没了，状态也没了。

还有两个不那么明显但同样致命的后果：

- **无法去重**：模型不知道自己已经查过哪些数据，容易重复调用同一个接口。你在消息里"有记录"，但它埋在一万 token 的中段，模型没看见（回忆 C13-1 第 5 节的"重复劳动"）。
- **无法并发**：两个进程想同时处理同一个任务时，没有任何地方可以"抢锁"——因为它们共享的只有一份易失的消息。

## 2. 解决：显式状态机

把进度写成一个**独立存储的状态对象**（文件或数据库），消息数组照常跑，但每一步都把关键状态落进去：

```json
{
  "task_id": "t_20261020_001",
  "goal": "分析 Q3 销售数据并出报告",
  "status": "running",          // pending / running / paused / done / failed
  "current_step": "analyze",    // 下一步要做的事（cn、us 数据已取完）
  "steps_done": ["fetch_cn_data", "fetch_us_data"],
  "artifacts": {                 // 中间产物，落盘后的引用
    "cn_data": "file://artifacts/cn.csv",
    "us_data": "file://artifacts/us.csv"
  },
  "updated_at": "2026-10-20T00:05:36Z"
}
```

关键字段：

- `status`：任务处于哪个阶段（状态机的「状态」）。
- `current_step`：当前所处步骤 / 下一步要做的事（用于断点续跑时定位「从哪继续」）。
- `artifacts`：中间产物落盘后的引用（不是产物本身，见 C13-3 的落盘+引用）。

### 2.1 该放什么、不该放什么

状态对象最容易变成「第二个消息数组」——什么都往里塞，最后又大又乱。判据是：**只放"恢复时需要的事实"，不放"过程叙述"**。

| 放 | 不放 |
|---|---|
| 已完成哪些步骤（步骤名） | 每步的完整推理过程 |
| 中间产物的引用（ID / 路径） | 产物正文 |
| 关键决策与理由（一行一条） | 讨论与犹豫过程 |
| 失败原因（供重试判断） | 报错堆栈全文（落盘，存引用） |
| 下一步做什么 | 模型的思考链 |

判据的另一种表述：**状态对象要能被人类在 10 秒内读完**。读不完，说明你放多了——它就不是"状态"了，而是"日志"。

## 3. 为什么放外部，而不是放上下文

| 放上下文 | 放外部状态 |
|---|---|
| 进程挂就丢 | 独立存储，进程挂了还在 |
| 占用 token，每轮重复付费 | 不占上下文 |
| 无法审计、无法人工干预 | 可读、可改、可审计 |
| 只能「从头跑」 | 可暂停、可恢复、可回退 |

这也是三类记忆的第三条边界（见阶段 README）：**「压根不该放上下文的东西」——任务进度、中间产物——放外部状态**。

## 4. 状态机 vs 消息的职责分工

- **消息数组**：给模型看「当前该做什么」的工作记忆。
- **状态机**：给系统看「任务进行到哪、还能不能恢复」的事实记录。

两者要同步，但**不能互相替代**：状态机是真相源（source of truth），消息是从它派生的「视图」。

这个"真相源"的说法有很实际的含义：**当两者不一致时，以状态机为准**。比如状态机说 `fetch_cn_data` 已完成、但消息数组里没有对应记录（可能被压缩掉了），正确做法是相信状态机、必要时按 `artifacts` 重新取回数据，而不是重新跑一遍。

## 5. 最小可用状态机

先别上状态机框架，从「一个 JSON 文件 + 几个状态字段」开始：

```
pending（待开始）→ running（进行中）→ done（完成）
                          └→ paused（暂停，可恢复）→ running
                          └→ failed（失败，可重试）→ running
```

状态不用多，够用就行。**能表达「现在在哪、下一步去哪、能不能恢复」就够**。

### 5.1 加一层转移校验（十行代码，省掉大量脏状态）

状态机最常见的 bug 不是"状态设计得不好"，而是**出现了不该出现的状态**：任务已经 `done` 了又被改成 `running`，或者 `pending` 直接跳到 `done`（漏了中间步骤但没人发现）。

防法是在写入前校验转移合法性：

```python
ALLOWED = {
    "pending": {"running"},
    "running": {"paused", "done", "failed"},
    "paused":  {"running", "failed"},
    "failed":  {"running"},          # 重试
    "done":    set(),                # 终态，不可再变
}

def transition(state, new_status):
    if new_status not in ALLOWED[state["status"]]:
        raise ValueError(f"非法转移 {state['status']} → {new_status}")
    state["status"] = new_status
    state["updated_at"] = now()
    save(state)
```

这段代码的价值在于**把"不可能发生的事"变成"立刻报错"**。没有它，一个 `done` 的任务被重复恢复，会产生两份报告、两次通知——而这类问题在日志里看不出来，因为每次状态变更本身都是合法的（只是顺序错了）。

### 5.2 别忘了「人工暂停」这个真实需求

`paused` 不是为了好看。真实业务里经常需要：

- 任务跑到一半，需要人确认一个关键判断（这与 C23-3 的 HITL 是一回事）；
- 成本超预算，主动挂起，等人决定是否继续；
- 外部依赖不可用（第三方接口挂了），挂起等恢复。

这三种情况都不该走 `failed`——`failed` 意味着"出错了"，会触发告警和重试逻辑；而 `paused` 意味着"正常停下，等人"。**把这两种语义混在一起，会导致告警风暴或者静默卡死。**

## 6. 小结

- 进度别隐含在消息里，要写成独立存储的显式状态机。
- 状态字段：`status` / `current_step` / `artifacts`（中间产物落盘引用）；只放"恢复需要的事实"，能被人 10 秒读完。
- 状态机是真相源，消息是派生的视图；两者冲突时以状态机为准。
- 加一层转移校验：非法转移立刻报错，比事后查脏状态便宜得多。
- `paused` 与 `failed` 语义要分开：一个是等人，一个是出错。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 进度为什么不能藏在消息数组里？挂了之后会怎样？
2. 状态字段为什么只放「恢复需要的事实」？放多了有什么坏处？
3. 状态机和消息冲突时，为什么以状态机为准？

<details>
<summary>参考思路</summary>

1. 消息是易失的、会被压缩、会被裁剪，而且无法判断「做到第几步」。一挂就得从头再跑一遍，还可能重复执行副作用。
2. 状态是要被人 10 秒读完、被程序直接判断的。塞进大段日志和中间结果，它就不再是状态，而是一个更烂的上下文。
3. 状态机是你显式维护的真相源，消息只是某一时刻的派生视图。以视图为准等于让「可能被压缩过的历史」决定事实——必然出错。
