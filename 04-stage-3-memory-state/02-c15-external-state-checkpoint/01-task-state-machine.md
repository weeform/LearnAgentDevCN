# C15-1 · 状态外置：任务状态机
> 阅读约 10 分钟。目标：把「任务进度」从隐含在消息里，改成显式的、可恢复的状态机。

## 1. 问题：进度藏在消息里，一挂就丢

阶段 2 的 Agent，进度是**隐含在消息数组里**的：走到第几步、查过什么、结果是什么，全靠消息里那堆文本承载。后果：

- 进程一挂，消息数组没了，**进度归零**。
- 想「人工看一眼进度」？只能读一大堆消息文本。
- 想「从第 15 步重来」？做不到，只能从头跑。

一句话：

> 把「状态」和「承载状态的消息」混在一起，状态就成了消息的附属品——消息没了，状态也没了。

## 2. 解决：显式状态机

把进度写成一个**独立存储的状态对象**（文件或数据库），消息数组照常跑，但每一步都把关键状态落进去：

```json
{
  "task_id": "t_20261020_001",
  "goal": "分析 Q3 销售数据并出报告",
  "status": "running",          // pending / running / paused / done / failed
  "current_step": "analyze",    // 下一步要做的事（cn、us 数据已取完）
  "steps_done": ["fetch_cn_data", "fetch_us_data"],
  "artifacts": {                 // 中间产物，落盘后的引用
    "cn_data": "file://artifacts/cn.csv",
    "us_data": "file://artifacts/us.csv"
  },
  "updated_at": "2026-10-20T00:05:36Z"
}
```

关键字段：

- `status`：任务处于哪个阶段（状态机的「状态」）。
- `current_step`：当前所处步骤 / 下一步要做的事（用于断点续跑时定位「从哪继续」）。
- `artifacts`：中间产物落盘后的引用（不是产物本身，见 C13-3 的落盘+引用）。

## 3. 为什么放外部，而不是放上下文

| 放上下文 | 放外部状态 |
|---|---|
| 进程挂就丢 | 独立存储，进程挂了还在 |
| 占用 token，每轮重复付费 | 不占上下文 |
| 无法审计、无法人工干预 | 可读、可改、可审计 |
| 只能「从头跑」 | 可暂停、可恢复、可回退 |

这也是三类记忆的第三条边界（见阶段 README）：**「压根不该放上下文的东西」——任务进度、中间产物——放外部状态**。

## 4. 状态机 vs 消息的职责分工

- **消息数组**：给模型看「当前该做什么」的工作记忆。
- **状态机**：给系统看「任务进行到哪、还能不能恢复」的事实记录。

两者要同步，但**不能互相替代**：状态机是真相源（source of truth），消息是从它派生的「视图」。

## 5. 最小可用状态机

先别上状态机框架，从「一个 JSON 文件 + 几个状态字段」开始：

```
pending（待开始）→ running（进行中）→ done（完成）
                          └→ paused（暂停，可恢复）→ running
                          └→ failed（失败，可重试）→ running
```

状态不用多，够用就行。**能表达「现在在哪、下一步去哪、能不能恢复」就够**。

## 6. 小结

- 进度别隐含在消息里，要写成独立存储的显式状态机。
- 状态字段：`status` / `current_step` / `artifacts`（中间产物落盘引用）。
- 状态机是真相源，消息是派生的视图；放外部才能恢复、审计、干预。
