# C15-3 · 按需加载与上下文分区
> 阅读约 12 分钟。目标：用「按需加载」和「上下文分区」两个手法，把上下文花在刀刃上。

## 1. 按需加载：先给目录，要用再取

默认思路是「把相关资料全塞进上下文」。更好的做法是**分两步**：

1. 先给模型一个**目录 / 摘要**（便宜，几行）。
2. 模型判断需要哪个，**再取详情**。

例子：让 Agent 读一份 50 页的财报，别一开始把 50 页全塞进去，而是先给目录 + 每章一句话摘要，模型说「我要看第 3 章营收」，再单独把第 3 章取进来。

这和 C13-3 的「落盘 + 引用」是同一招：**先给句柄，按需取数据**。收益：

- 省 token（大部分内容根本不会被用到）。
- 模型注意力不被无关内容稀释。

代价是要「多一次工具调用去取详情」，但这点延迟换来的是大幅降本和更准的回答。

### 1.1 目录必须带「判断依据」，否则模型无从下手

这是按需加载最常见的失败：给了目录，模型却乱取或者不取。原因是**目录只写了"有什么"，没写"什么时候需要它"**。

对比两版：

```
❌ 只写有什么：
1. 公司概况
2. 经营分析
3. 财务数据
4. 风险提示

✅ 带判断依据：
1. 公司概况 —— 需要了解主营构成、股权结构时读
2. 经营分析 —— 需要分业务/分地区的收入变化时读
3. 财务数据 —— 需要具体数字（营收、毛利、现金流）时读
4. 风险提示 —— 需要评估不确定性、诉讼、政策风险时读
```

第二版让模型能**用自己的任务去匹配**，而不是猜"经营分析"和"财务数据"哪个更相关。额外的成本只是每章多十来个字。

再加一条经验：**目录里带上规模信息**（「第 3 章，约 4000 字」）。模型会因此更谨慎——如果它只需要一个数字，看到"4000 字"可能会先想想有没有更省的路。

### 1.2 一个可落地的接口

```python
CATALOG = [
    {"id": "ch1", "title": "公司概况", "desc": "主营构成、股权结构", "chars": 2200},
    {"id": "ch2", "title": "经营分析", "desc": "分业务/分地区收入变化", "chars": 4100},
    {"id": "ch3", "title": "财务数据", "desc": "营收、毛利、现金流具体数字", "chars": 3200},
]

def get_chapter(chapter_id: str) -> str:
    """工具：按 id 取整章原文"""
    return load(f"report/{chapter_id}.md")
```

调用方（system prompt）里写一句：「先读目录，判断需要哪章再取；不要一次取超过 2 章。」——**这句限制很重要**，否则模型倾向于"全取了再说"，按需加载就退化成了全量加载。

## 2. 上下文分区：三段式

把每次请求的上下文，按「变动频率」分成三段：

| 分区 | 内容 | 特征 |
|---|---|---|
| **稳定前缀** | system prompt + 工具定义 | 几乎不变，吃缓存（见 C2-5） |
| **动态中段** | 检索到的内容、任务中间信息 | 会变，但每步相对稳定 |
| **最新尾部** | 最近几轮对话 | 每步都在变 |

三段分区的意义在于**缓存命中**（见 C2-5）：前缀越稳定，命中率越高，成本越低。所以：

> 尽量把「每步都变的内容」往后放，「几乎不变的内容」固定在前。

分区还有个**超出缓存之外**的好处：它让"什么东西该放哪"变成一个可以讨论的规则。团队里常见的争论是"这段要不要塞进去"，有了分区就可以问："它属于哪一段？"——属于中段的东西可以压缩、属于尾部的东西不能动，判断立刻清楚。

## 3. 两个容易做错的地方

1. **别在循环中动态增删工具**（同 C13-3 第 4 节）。工具定义属于「稳定前缀」，若每次循环动态改，前缀就碎了，缓存全废。工具集要按任务类型**静态划分**。

2. **检索内容的插入位置**。检索结果属于「动态中段」（会变），插在 system 之后、历史之前能让模型更早看到关键信息；但要意识到：检索结果一变，其后的历史消息缓存会整体失效，牺牲一部分缓存命中。成本敏感时，可把检索内容放得更靠后。

第 2 点其实是个真实的取舍，用一句话概括：

> **靠前 = 更容易被注意到，靠后 = 缓存命中更高。**

一个折中的做法是：**把检索内容放在历史之后、当前问题之前**。这样它前面的一切（system、tools、历史）都能稳定命中缓存，而它自己紧邻当前问题——既没牺牲缓存，也没让它掉进"中段"。

## 4. 小结

- 按需加载：先给目录/摘要，模型判断需要再取详情，省 token、保注意力。
- 目录必须写「什么时候需要它」（判断依据）+ 规模信息，否则模型无从下手；system 里要限制"一次别取太多"。
- 上下文三段式：稳定前缀（吃缓存）/ 动态中段 / 最新尾部，按变动频率分区。
- 别动态增删工具；检索内容的最优位置常在「历史之后、当前问题之前」——兼顾缓存与注意力。
