# C15-4 · 子 Agent 隔离上下文
> 阅读约 12 分钟。目标：用「子 Agent」把脏上下文隔离出去，只让结论回流主链路。

## 1. 问题：脏上下文污染主链路

主 Agent 跑着跑着，上下文会被「脏数据」塞满：

- 一次检索返回几万字的原始文档；
- 一个子任务跑了几十步的中间日志；
- 一段和主任务关系不大的长输出。

这些内容占着 token、稀释注意力，还让主任务的目标越来越模糊。**主 Agent 其实只需要「那件事的结论」，不需要过程。**

「目标越来越模糊」值得展开：它不是因为模型忘了目标，而是因为上下文里关于"别的任务"的材料变多了，**模型对"当前该干什么"的判断被这些材料带偏**。典型表现是主 Agent 开始回答子任务的问题、或者把子任务的中间结论当成了主任务的结论。

## 2. 解决：丢给子 Agent，只回传结论

思路：把「脏」的子任务，交给一个**拥有独立上下文**的子 Agent 去跑；子 Agent 在自己的上下文里随便折腾，跑完只把**一句话结论**回传给主 Agent。

```
主 Agent（干净上下文）
   │  "帮我查一下竞品 X 的价格策略，给我结论"
   ▼
子 Agent（独立、隔离的上下文）
   │  检索 → 读几十页 → 分析 → ...
   ▼
回传："竞品 X 主打低价走量，核心价位带 99-199 元，主推订阅制。"
```

主 Agent 的上下文里，从头到尾只多了一句话，而不是几十页。

## 3. 回传什么：定一个契约，别只说"给我结论"

「只回传结论」这句话太模糊，实践中会走向两个极端：要么回传一大段（隔离失效），要么回传一句话丢掉了关键细节（下结论出错）。

正确做法是**给子 Agent 定一个固定返回结构**：

```json
{
  "answer": "竞品 X 主打低价走量，核心价位带 99-199 元，主推订阅制。",
  "evidence": ["官网定价页：标准版 99/月", "渠道访谈：走量策略，毛利较低"],
  "confidence": "high",
  "caveats": ["未覆盖企业版定价", "数据截至 2026-09"],
  "artifacts": ["file://research/comp_x_pricing.md"]
}
```

五个字段各有作用：

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| `answer` | 主 Agent 直接用的结论 | 主链路还得自己去读细节 |
| `evidence` | 让结论可核验 | 主 Agent 无法判断可信度，只能盲信 |
| `confidence` | 支持主 Agent 决定要不要复核 | 高风险结论被当确定事实使用 |
| `caveats` | 明确"这次没覆盖什么" | 主 Agent 以为全覆盖了，结论过度泛化 |
| `artifacts` | 需要细节时的取回路径 | 隔离变成"信息黑洞" |

`artifacts` 这个字段最容易被漏，但它恰恰是解决"结论失真"的关键——**隔离不等于销毁**。主 Agent 平时只读 `answer`，真需要细节时按 `artifacts` 回去取。这样既保住了主链路的干净，又没丢掉原文。

`caveats` 也值得单独说：它防的是"子 Agent 的答案被过度信任"。子 Agent 只查了三个渠道，它自己知道覆盖不全；如果不说，主 Agent 会把"三渠道的结论"当成"市场的结论"往外讲。**让子 Agent 主动声明边界，比让主 Agent 事后怀疑有效得多。**

## 4. 这是「拆分」的最小形态

注意：子 Agent 隔离上下文，**本质上已经是「多 Agent」了**——只是它只有一层、单向调用。阶段 4（多 Agent 与编排）会把这套东西系统化：多个子 Agent、可并行、可编排拓扑。

所以这一节是阶段 4 的**先导**。你现在用「一个子 Agent 隔离一个脏任务」，阶段 4 再学「什么时候拆成多个、怎么编排」。

## 5. 代价要算清楚

隔离不是免费的：

- **多一次完整调用**：子 Agent 要重新起一轮上下文，token 和延迟都增加。
- **结论可能失真**：子 Agent 压掉过程，可能丢了主 Agent 其实需要的关键细节。

所以「该不该隔离」的判断标准是：

> **子任务的上下文有多脏 × 主任务有多依赖细节**。

脏、且主任务只要结论 → 隔离。干净、或主任务需要细节 → 别隔离，直接在主链路跑。

把这个判断做成一张表更直观：

| 子任务特征 | 主任务需求 | 做法 |
|---|---|---|
| 读长文档、多轮检索（脏） | 只要结论 | **隔离**，回传结构化结论 |
| 读长文档（脏） | 需要原文引用 | 隔离 + `artifacts` 回传路径 |
| 一两次工具调用（干净） | 要结论 | 不隔离，直接跑（隔离纯亏） |
| 一两次工具调用（干净） | 要细节 | 不隔离 |

第三行是最常见的误用：为了"架构好看"把所有子任务都包成子 Agent，结果每个任务多一次调用、多一层超时风险，而上下文根本没脏过。

## 6. 一个反直觉的提醒

隔离上下文**不是**为了省 token（它通常反而更贵，因为多一次调用），而是为了**保住主链路的质量**——让主 Agent 的注意力不被稀释、目标不漂移。别拿「省钱」当动机，拿「主链路要干净」当动机。

用错动机的后果很具体：如果你为了省钱去做隔离，就会倾向于"能隔离就隔离"，最后得到一个调用次数翻倍、延迟翻倍、结论层层失真的系统。而如果动机是"主链路要干净"，你会只在真的脏的时候隔离——判断标准完全不同。

## 7. 小结

- 子 Agent 用独立上下文跑脏任务，只回传结论，保住主链路干净。
- 回传要有契约：`answer` / `evidence` / `confidence` / `caveats` / `artifacts`；`artifacts` 保证"隔离不等于销毁"。
- 这是多 Agent 的最小形态，是阶段 4 的先导。
- 代价是多次调用、结论可能失真；动机是保质量，不是省钱；干净的子任务别隔离。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 子 Agent 隔离解决的到底是「成本」还是「质量」？为什么？
2. 回传契约里 `artifacts` 为什么不能省？
3. 什么样的子任务不该隔离？

<details>
<summary>参考思路</summary>

1. 主要是质量：脏任务（读几十页网页、跑长工具链）的中间噪声会污染主链路注意力。代价反而更高（多次调用），所以动机不是省钱。
2. 隔离不等于销毁。中间产物要能被主链路按需取回，否则一旦结论需要复核或补充，就只能整段重跑。
3. 干净、短、结论必需的子任务。隔离它只是多一次调用和一次信息损耗（结论会失真），没有任何收益。
