# C15-5 · 阶段 3 总复习与自测
> 阅读约 14 分钟。目标：把阶段 3 的三类记忆串成一张图，对照出口标准做综合自测。

## 一、阶段 3 串讲

Agent 跑长任务撞三堵墙，对应三类机制：

| 墙 | 机制 | 课程 | 核心手法 |
|---|---|---|---|
| 上下文会爆 | **短期记忆** | C13 | 摘要/删除/保留分界，工具返回落盘+引用 |
| 重启即失忆 | **长期记忆** | C14 | RAG 全链路：切分→Embedding→检索→重排→维护 |
| 进度无依归 | **外部状态** | C15 | 状态机外置、checkpoint 续跑、按需加载、子 Agent 隔离 |

一句话把三类分开：

- **短期记忆** = 还在上下文里的，怎么管、怎么压（本质是上下文工程）。
- **长期记忆** = 不在上下文里的，怎么存、怎么找（本质是检索）。
- **外部状态** = 压根不该放上下文的，放哪（本质是状态管理）。

## 二、一个任务走完三类记忆

三段话分开讲容易记住，但真跑起来它们是**同一条链**。用一个具体任务走一遍：

**任务**：分析某公司 Q3 财报，找三条异常，出一页结论。

| 步骤 | 发生了什么 | 用到的机制 |
|---|---|---|
| 1 | 用户给了目标，写入状态机（`goal` + `status=running`） | 外部状态（C15-1） |
| 2 | 财报 50 页，先给目录 + 每章摘要，按需取第 2、3 章 | 按需加载（C15-3） |
| 3 | 第 3 章 4000 字进来，压成「营收同比 +12%，毛利率降 3 个点」 | 短期记忆压缩（C13-2） |
| 4 | 需要行业均值做对比，检索内部知识库 top 20，重排取 5 | 长期记忆（C14） |
| 5 | 检索结果里有一篇 2025 的旧研报，按 `updated_at` 降权 | 记忆维护（C14-4） |
| 6 | 跑了 15 步，历史超预算，把前 8 步压成结构化状态 | 短期记忆 + 缓存权衡（C13-4 / C7-2） |
| 7 | 中途进程挂了，重启后从 `current_step=compare` 继续 | 断点续跑（C15-2） |
| 8 | 有个「核对财报原文」的脏子任务，丢给子 Agent，只回传结论 + `artifacts` | 子 Agent 隔离（C15-4） |

这张表的意义在于：**三类记忆不是三个并列的知识点，而是同一个 Agent 同一时刻都在用的三套机制**。只做其中一类，长任务还是跑不稳——

- 只压上下文（C13）、不落状态：压完崩一次，从头再来。
- 只落状态（C15）、不压上下文：状态能恢复，但第 30 步的输入已经贵到用不起。
- 只有 RAG（C14）、不压上下文：每次检索 20 块，几轮就爆窗口。

## 三、出口标准对照

1. **会话压缩可用**——C13：跑 30 步以上任务，压缩后仍正确完成，成本可量化（见 C13-4 的及格线）。
2. **长期记忆检索跑通**——C14：有评测集，能量出召回率和「检索错导致答错」的比例。
3. **一个可断点续跑的任务**——C15：进程 kill 再起，从上次状态继续（幂等 + 中间产物落盘）。
4. **一次子 Agent 隔离实践**——C15-4：验证脏上下文隔离后主链路变干净。

四项可以用四个具体动作验收：

| 出口项 | 验收动作 | 通过标准 |
|---|---|---|
| 压缩 | 同一批 20 个任务，压/不压各跑一遍 | token 降 ≥40%，断言通过率降 ≤5% |
| 检索 | 建 50 条「问题→gold chunk」 | Recall@10 有数，且能指出失败样本的归因 |
| 续跑 | 跑到一半 `kill -9`，再启动 | 从 `current_step` 继续，无重复副作用 |
| 隔离 | 对比隔离前后主链路的上下文长度 | 主链路 token 明显下降，且结论未失真 |

第二项的"能指出失败样本的归因"是这条里最容易被放过的部分：**光有个召回率数字没用，得能说清"没捞到的那几条为什么没捞到"**（切分错？权限挡了？Embedding 截断？）。这个能力才说明你真的把链路走通了。

## 四、综合自测

1. 一个 50 步的 Agent，每步查一次库返回 5000 行。它的成本会怎么涨？你至少能用哪两种手法压下去？
2. 「短期记忆」「长期记忆」「外部状态」的本质区别是什么？各举一个「放错了地方」的例子。
3. 你的知识库 10 万篇文档，用户问「型号 AB-123 的规格」。为什么纯向量检索可能漏，混合检索能救？
4. 断点续跑时，你发现某个「发邮件」步骤可能被执行两次。问题出在哪？怎么保证安全？
5. 什么情况下你会把一个子任务丢给子 Agent 隔离执行，而不是在主链路里直接跑？
6. 你的 Agent 在第 20 步开始重复查询已经查过的数据。最可能是哪一类机制缺失？为什么？
7. 一个「能恢复但不省钱」的系统和一个「省钱但崩了要重跑」的系统，哪个更值得先修？判断依据是什么？

## 五、参考答案要点

1. 成本随步数平方增长（每步都要为历史重复付费）。两手法：工具返回「落盘+引用」（C13-3）、会话压缩（C13-2）；更根本的是先把每步返回的量压下来，因为平方增长会把早期的浪费放大到后面每一轮。
2. 短期=还在上下文里怎么管（上下文工程）；长期=不在上下文里怎么存怎么找（检索）；外部状态=不该放上下文的进度/产物（状态管理）。例：把任务进度放消息里（进程挂就丢）、把 3 页文档搭整套 RAG（过度设计）、把中间产物塞满上下文（预算黑洞）。
3. 向量检索不懂「精确字符串匹配」，可能漏掉含「AB-123」的段。混合检索加关键词（BM25）补精确匹配，RRF 融合后重排。
4. 非幂等操作重复执行的风险。做法：执行前/后立刻打「已执行」标记（带幂等键），恢复时先查标记；或让操作本身幂等（如用 `request_id` 去重）。
5. 子任务上下文很脏、且主任务只需要结论时（如「查竞品价格策略给我一句话结论」），用子 Agent 隔离，保主链路干净；干净的子任务别隔离，纯亏。
6. 外部状态缺失（或状态里没记 `steps_done`）。模型在消息里"有记录"，但那埋在中段看不见；状态机里如果有 `steps_done`，每轮把它注入上下文，就不会重复。这也说明"记忆"不是靠塞，是靠结构化。
7. 先修「省钱但崩了要重跑」的那个。因为重跑意味着**已完成的副作用可能重复**（发邮件、下单、扣费），这是正确性问题；而不省钱只是成本问题。**正确性问题的优先级永远高于成本问题。**
