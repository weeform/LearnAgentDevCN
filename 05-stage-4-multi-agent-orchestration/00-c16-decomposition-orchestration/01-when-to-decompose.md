# C16-1 · 拆分信号：先判断该不该拆
> 阅读约 15 分钟。目标：在动手拆之前，先回答「我到底该不该拆」——多数情况下答案是不该；拆错时通常错在哪三种地方。

## 1. 默认答案是「不拆」

多 Agent 听起来高级，但它的成本是实打实的（下一节细算）。所以拆分的**默认立场是「能不拆就不拆」**，只有出现明确的拆分信号时才动手。

这不是保守，是清醒：**大多数任务，一个写好的单 Agent 就够，拆了只会更贵、更难调、更多失败点。**

## 2. 三个值得拆的信号

出现下面任一信号，才考虑拆：

### 信号一：上下文污染

单 Agent 的上下文被不同性质的子任务互相污染——查数据的日志、写文案的草稿、做计算的过程全挤在一起，模型注意力被稀释，目标越来越糊。

> 特征：任务越跑，模型越「顾此失彼」，回答质量随步数明显下滑。

这正是阶段 3 的 C15-4 讲过的「子 Agent 隔离」的规模化场景。

### 信号二：需要并行

任务里有**可以同时做、互不依赖**的部分。单 Agent 只能排队，多 Agent 能同时开工，省的是墙钟时间。

> 特征：任务可以清晰切成几个「互不依赖」的独立子任务。若子任务之间强依赖，并行无从谈起。

### 信号三：职责互斥、需要权限隔离

不同子任务需要**不同的权限或工具集**，硬塞给一个 Agent 会权限过大、风险集中。例如「读数据的」和「能花钱的」不该是同一个 Agent。

> 特征：部分操作敏感（扣款、发信、删库），需要最小权限隔离（呼应 C8 与阶段 5 安全）。

## 3. 一条判断清单

动手拆之前，逐条过：

1. 这个任务，一个单 Agent 真的搞不定吗？（先试单 Agent，别默认它不行）
2. 有「上下文污染 / 可并行 / 职责互斥」中的哪一条？
3. 拆开后，每个子 Agent 的任务边界是否**清晰到一句话能说清**？
4. 拆分的收益（质量/速度/安全）是否**大于**下一节要算的四项成本？

**第 1 条和第 4 条答不上来，就先别拆。**

## 4. 一个反直觉的事实

拆分最大的收益往往**不是更快，也不是更准，而是「每个 Agent 更简单、更可控」**——单一职责的 Agent 更好写、更好测、更好调。如果你的单 Agent 已经简单可控，拆分的理由就更弱了。

## 5. 拆错的三种典型形态

信号没对上就动手，通常会掉进下面三个坑。它们的共同点是：**拆完第一步就发现不对，但已经付出了全部成本。**

### 形态一：把「串行依赖」拆成「并行」

「先查数据 → 再写报告 → 再审核」看起来像三个岗位，其实是**一条链**：写报告必须等数据，审核必须等报告。拆成三个 Agent 后，你还是得排队等，只是每次交接多了一次 LLM 调用来「转述」上游结果。

**净效果**：墙钟时间不减，token 与失败点都涨了。这属于「用多 Agent 的代价，买单 Agent 的收益」，最纯粹亏本的一种。

> 判据：如果去掉任意一个环节，后面的环节就没法开始，那就是串行链。串行链**只能在链路内部优化**（合并环节、换更快模型），不能靠拆分提速。

### 形态二：按「形容词」拆，而不是按「职责」拆

「一个 Agent 负责质量，一个负责速度」「一个负责严谨，一个负责创意」——这类边界听起来合理，实际无法执行：**没人说得清模型具体该做什么**，两个 Agent 会做同一件事、还会互相推翻。

可执行的边界长这样：「一个只读数据库、不能写；一个只能写报告文件、不能读库」。差别在于**能不能落成工具集与权限**。

> 判据：子 Agent 的边界必须能翻译成「它有哪些工具、它不能碰什么」。翻不出来，就是形容词式拆分。

### 形态三：拆完每个 Agent 都缺信息

为了「干净」，把上下文切得过于干净，结果每个子 Agent 都只知道局部：写报告的不知道数据是怎么来的，审核的不知道报告要回答什么问题。它们各自「合理地」猜，最后拼出一个自洽但错的东西。

这比上下文污染更麻烦——**污染是信息太多，缺失是信息不够**，后者连补救方向都更难找。

> 判据：每个子 Agent 拿到的信息，够不够它独立把这件事做完？不够就得补「交接包」（结论 + 依据 + 不确定性，见 C18-1）。

## 6. 先试单 Agent，试到哪一步算「真搞不定」

「先试单 Agent」不是一句口号，得有个停手标准，否则容易陷在调试里出不来。三条够用：

1. **能不能跑通**：端到端至少成功 3 次，别拿一次偶然成功当通过。
2. **失败能不能定位**：失败时你能说清是「模型不会」还是「信息不够」。说清不了，拆了也一样查不出。
3. **上下文够不够**：把任务最长的输入塞进去，看模型是否开始「忘了开头」。这一条是 C15 的预算问题，不是拆分问题——**先试裁剪与摘要，再考虑拆**。

三条都过了还是不行，才说明问题真出在「一个 Agent 装不下这件事」，这时拆分才有针对性。

## 7. 小结

- 默认不拆；出现「上下文污染 / 可并行 / 职责互斥」任一信号才考虑。
- 拆前先过四问：单 Agent 是否真搞不定、命中哪条信号、边界是否清晰、收益是否大于成本。
- 拆分的最大收益是「更简单可控」，而非单纯的快或准。
- 三种典型拆错：串行链当并行拆、按形容词拆职责、切得太干净导致信息缺失。
- 边界必须能落成「工具集 + 权限」，落不下来就是没想清。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 为什么「默认答案是不要拆」？拆分会立刻带来哪一类问题？
2. 三个值得拆的信号分别是什么？它们为什么是「信号」而不是「理由」？
3. 「边界必须能落成工具集 + 权限」——落不下来说明什么？

<details>
<summary>参考思路</summary>

1. 因为拆分会引入通信损耗、上下文割裂和成本倍数，而单 Agent 在多数任务上本来够用。先拆等于先付税，再考虑要不要收益。
2. 上下文污染（脏活会毁掉主链路判断）、可并行（能压缩墙钟时间）、职责互斥（权限或目标天然冲突）。它们指向的是结构性约束，不是「想让架构好看」。
3. 说明你还没想清职责边界，只是按名字拆了角色。落到工具集和权限上，就知道每个 Agent 到底能看什么、能做什么——这才是真边界。
