# C16-2 · 拆分的代价
> 阅读约 15 分钟。目标：把多 Agent 的四项成本算清楚，并学会用 trace 算出自己任务的真实倍数，避免「拆了才发现更贵更难调」。

## 1. 四项成本

| 成本 | 为什么涨 | 大致量级 |
|---|---|---|
| **token** | 每个 Agent 都要自己的上下文、system prompt、来回消息 | 通常是单 Agent 的 3–10 倍（工程经验值） |
| **延迟** | 多 Agent 之间有通信、串行等待、重复推理 | 明显高于单 Agent |
| **调试** | 失败点数量翻倍，出错时不知道是哪个 Agent 的锅 | 复杂度陡增 |
| **一致性** | 各 Agent 结论可能互相矛盾，需要额外聚合 | 新增一类 bug |

## 2. token 为什么涨 3–10 倍

关键不在「Agent 多了」，而在「**每个 Agent 都是独立的上下文**」：

- 每个 Agent 都要一份 system prompt（重复付费）。
- 每个 Agent 都要重新读一遍任务描述和它的输入（重复推理）。
- Agent 之间来回传递结果，中间消息也计费。

原本一个 Agent 一路读下来只付一份历史，拆成 3 个 Agent，等于把「共享的历史」变成了「各自独立的历史」，重复部分翻了倍。

## 3. 延迟为什么「明显高于」单 Agent

单 Agent 是「一条线」，多 Agent 是「一张图」：

- **通信开销**：Agent 之间传消息有来回。
- **串行依赖**：B 要等 A 出结果才能开始，这条链上的等待是叠加的。
- **并行 ≠ 全快**：只有真正互不依赖的部分才能并行；串行的部分照旧排队。

一句话：**多 Agent 只有在「可并行」的场景下才可能在墙钟时间上赢，纯串行的拆分只会更慢。**

## 4. 调试成本：失败点数量翻倍

单 Agent 出问题，你查一个循环。多 Agent 出问题，你要查：

- 是哪个 Agent 错了？
- 是它的输入不对（上游传错了），还是它自己判断错了？
- 是通信协议的问题（消息没传对），还是聚合的问题（结果没合并好）？

**没有 trace，这个排查基本是噩梦**——这正是阶段 5.1 可观测性要提前到阶段 2 一起做的原因（见阶段 README 与 `00-curriculum-overview.md` 第 5 节）。

## 5. 一致性成本：新增一类 bug

单 Agent 不存在「结论打架」，多 Agent 会有：

- 两个 Agent 对同一事实给出不同答案。
- 聚合时不知道该信谁（这是 C18 的主题）。

这类 bug 是单 Agent 时代完全没有的，属于拆分的「额外税」。

## 6. 用 trace 算自己的倍数

「3–10 倍」是工程经验值，你的任务到底几倍得自己算。算法只有一步：**给每次模型调用打上 `agent_id`，把 token 按 Agent 汇总，再除以单 Agent 版本的基线。**

要记的字段（就是 C19 那套 trace 的最小集）：

| 字段 | 作用 |
|---|---|
| `agent_id` | 区分是哪个 Agent 花的钱 |
| `input_tokens` / `output_tokens` | 必须分开记——输入才是重复计费的重灾区 |
| `duration_ms` | 算墙钟时间，看并行到底省没省 |
| `parent_span` | 还原调用链，定位串行等待卡在哪 |
| `task_id` | 把同一次任务的所有调用串起来 |

一张**示意**对照（数字虚构，看结构）：

| 指标 | 单 Agent | 拆成 3 个 | 倍数 |
|---|---|---|---|
| 输入 token | 40k | 130k | 3.3× |
| 输出 token | 6k | 9k | 1.5× |
| 总成本 | 基准 | 约 3.1× | — |
| 墙钟时间 | 48s | 41s | 0.85× |
| 失败定位耗时 | 10 min | 40 min | 4× |

两个必须看懂的点：

1. **输入涨得比输出猛**。因为每个 Agent 都要重建一遍「这任务是什么」，重复的几乎全在输入侧。
2. **时间可能只省一点**。上表三个 Agent 只快了 7 秒，成本却涨 3 倍——这正是「能并行、但并行度不高」的典型结果。**拆了基本不划算**。

### 三招把倍数压下来

- **共享前缀**：所有子 Agent 用**同一个 system prompt 开头**、顺序一致，让前缀缓存能命中（C2-5、C21-3）。这是最有效的一招，砍掉的正是「重复 system prompt」这块大头。
- **交接包要压缩**：Agent 之间传「结论 + 依据 + 不确定性」三件套，不要传整段对话历史（C18-1、C18-3）。
- **确定性工作别用 LLM 转述**：格式转换、字段搬运，用代码做，别让一个 Agent「总结给下一个 Agent」。

## 7. 一句话结论

> 拆分的账要**先算后拆**：token（3–10 倍）、延迟（通信+串行）、调试（失败点翻倍）、一致性（新增 bug 类）。算不清就默认不拆。

## 8. 小结

- 四项成本：token 3–10 倍、延迟明显升、调试翻倍、一致性新增 bug 类。
- 核心根源：每个 Agent 是独立上下文，重复推理和通信都计费。
- 只有「可并行」场景多 Agent 才可能在墙钟时间上赢。
- 倍数要用 trace 自己算：按 `agent_id` 汇总 token，除以单 Agent 基线，别信经验值。
- 压倍数的三招：共享前缀、压缩交接包、确定性工作走代码。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. token 为什么涨 3–10 倍？「重复推理」和「通信」各贡献了什么？
2. 为什么只有「可并行」场景，多 Agent 才可能在墙钟时间上赢？
3. 倍数为什么要用 trace 自己算，而不是信经验值？

<details>
<summary>参考思路</summary>

1. 每个 Agent 是独立上下文，同一份背景要各自读一遍（重复推理）；交接包本身也是 token，且要往返多次（通信）。两者叠加就是倍数。
2. 串行拆分的总延迟是各段之和加上通信开销，必然更慢。只有真正并行时，墙钟时间才被压缩到最长的那条支路。
3. 任务结构、交接包大小、模型选择差异极大，3–10 倍是范围不是定值。按 agent_id 汇总实际 token 除以单 Agent 基线，才知道自己付了多少。
