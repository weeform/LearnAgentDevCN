# C16-3 · 编排模式一：路由与流水线
> 阅读约 18 分钟。目标：掌握两种「串行」编排拓扑——路由（按类型分发）和流水线（按阶段接力），并写出它们的骨架代码。

## 1. 四种编排模式的全景

多 Agent 系统本质是一张「谁调用谁」的图。四种基本拓扑：

| 模式 | 拓扑 | 一句话 |
|---|---|---|
| **路由** | 一个入口 → 按类型分发到 N 个专家之一 | 把「对的事」派给「对的 Agent」 |
| **流水线** | A → B → C 顺序接力 | 把任务按阶段拆成一条链 |
| **主从** | 一个主 Agent 拆任务 → N 个从 Agent 并行干 → 回收 | 一个拆，多个干 |
| **黑板** | 多个 Agent 共享一块「黑板」读写协作 | 大家围绕共享状态协作 |

多数真实系统是这几种的**组合**，不是纯某一种。先分别吃透，再谈组合。

## 2. 路由（Router）

**拓扑**：一个入口 Agent（或纯规则），判断任务属于哪类，转给对应的专家 Agent。

```
          ┌→ 客服 Agent
用户输入 → 路由 ┼→ 技术 Agent
          └→ 售后 Agent
```

**适用**：任务类型**清晰可枚举、互不重叠**（客服/技术/售后、前端/后端问题）。

**关键**：路由判断本身要便宜——它不该是个「大模型推理半天」的重步骤，最好用轻量模型或规则做，否则入口就成瓶颈。

**失败传播**：路由判错类，任务就从起点错了。所以路由的准确率是这类系统的命门。

### 路由怎么实现：两级判断

别一上来就调模型分类。**规则先筛、模型兜底**，是最省钱也最可预测的写法：

```python
RULES = [                        # 一级：确定性规则，零成本、可解释
    ("退款|退货|发票",  "after_sales"),
    ("报错|502|超时|崩", "tech"),
]

def route(text: str) -> str:
    for pattern, target in RULES:
        if re.search(pattern, text):
            return target
    # 二级：规则没命中才问模型，且只让它输出一个标签
    label = classify_with_llm(text, choices=["after_sales", "tech", "general"])
    return label or "general"     # 判不出就走兜底，绝不硬派
```

三个必须有的细节：

1. **规则优先**。线上大多数请求是「典型句式」，规则能吃掉六七成，模型只处理剩下的长尾——成本和延迟都省一大截。
2. **只让模型输出一个标签**。要结构化输出（C4-3），不要让它「分析一下这属于哪类」再给结论，那是把分类任务做成了推理任务。
3. **必须留兜底分支**。低置信度时落到 `general` 或转人工，而不是硬塞进最像的专家。**硬派是路由系统最大的错误来源**——派错了下游再努力也是白费。

路由的评估要看**混淆矩阵**而不是总准确率：把「技术问题误派给售后」和「售后误派给技术」当成两种代价不同的错误，后者往往更贵（客户已经在生气了，还让他再等一次转接）。

### 怎么判断路由准不准

准备 100–200 条真实请求，人工标好类型，跑一遍看混淆矩阵。重点看两件事：

- **对角线占比**（整体准确率）：低于 85% 先别上线。
- **最贵的那类误派**：比如「技术 → 售后」的错误率。这类错误宁可多走兜底，也别放过。

## 3. 流水线（Pipeline）

**拓扑**：任务按阶段串成一条链，每个 Agent 负责一个阶段，前一阶段的输出是后一阶段的输入。

```
需求 → [分析 Agent] → [设计 Agent] → [实现 Agent] → [审校 Agent] → 产出
```

**适用**：任务有**天然的顺序阶段**，且每个阶段产出可验证的中间物（分析报告 → 设计方案 → 代码 → 审校意见）。

**关键**：

- **阶段边界要清晰**：每个阶段「输入什么、产出什么」要定义清楚，否则阶段之间互相甩锅。
- **中间物要落盘**（呼应 C15-2）：阶段之间的交接物存下来，某阶段失败不必从头跑。

**失败传播**：流水线的失败是**级联**的——A 错了，B、C 全错。所以越靠前的阶段越要稳，前段错误会沿链放大。

### 流水线骨架：三个设计点

```python
STAGES = [
    ("analyze",   analyze),      # 需求 → 分析
    ("design",    design),       # 分析 → 方案
    ("implement", implement),    # 方案 → 代码
    ("review",    review),       # 代码 → 审校意见
]

def run_pipeline(task: str, task_id: str, state: dict):
    for name, fn in STAGES:
        if name in state.get("done", []):     # 断点续跑：跳过已完成阶段
            continue
        state[name] = fn(task, state)          # 每阶段只拿「原始任务 + 上游产物」
        state.setdefault("done", []).append(name)
        save_checkpoint(task_id, state)        # 每阶段落盘（C15-2）
    return state
```

**设计点一：每阶段只传「任务 + 上游产物」**，不传整段历史。这样每段的输入是最小的，既省 token（C16-2），也更容易命中前缀缓存。

**设计点二：中间物必须落盘**。上面每跑完一段就 `save_checkpoint`，第 4 段挂了只重跑第 4 段，不用从头再来。

**设计点三：审校阶段要拿得到原始需求**。这是最容易被写错的地方：

> 假设 analyze 漏掉了一条关键约束（「只允许改配置，不许动代码」）。design 和 implement 都基于错的方案往下做，review 看到的是「代码写得挺好，就是没遵守那条约束」——**但 review 根本没见过那条约束**，它只能挑出格式和风格问题，于是整条链「全员通过、结果错误」。

修法很简单：给每个阶段的输入都带上**原始任务描述**（不只是上游产物），交给 review 时还要附上 analyze 阶段提取的约束清单。多花一点 token，换掉一整类静默失败。

## 4. 两者怎么选

| 你的任务 | 选 |
|---|---|
| 任务可分成互斥的类型 | 路由 |
| 任务有天然的顺序阶段 | 流水线 |
| 两者都有 | 组合：先路由分类型，每类内部走流水线 |

## 5. 小结

- 路由：按类型分发，命门是「路由判断要便宜且准」。
- 流水线：按阶段接力，命门是「阶段边界清晰、中间物落盘」，失败会级联。
- 多数真实系统是组合：先路由、再流水线。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 路由模式的命门是「判断要便宜且准」。便宜了不准会怎样？准了不便宜呢？
2. 流水线为什么要求「中间物落盘」？不落盘会付出什么代价？
3. 为什么多数真实系统是「先路由、再流水线」？

<details>
<summary>参考思路</summary>

1. 便宜但不准 → 大量请求走错分支，后面的昂贵处理全白做；准但不便宜 → 每次都要一次强模型判断，路由本身成了主要成本。实践是用规则/小模型先分流。
2. 某一阶段失败要重跑整条链，之前所有产出全丢。落盘后可以从断点续跑，也能让下一阶段按需取详情。
3. 因为真实任务先要「分类」（这是哪类请求），再在类内按固定步骤推进。纯路由处理不了多步任务，纯流水线处理不了异构输入。
