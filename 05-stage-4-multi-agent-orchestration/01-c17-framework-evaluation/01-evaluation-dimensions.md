# C17-1 · 评判框架的三个维度
> 阅读约 15 分钟。目标：建立一套不随框架变化而失效的评判标准——状态管理、可观测性、逃生舱，每个都能验证而不只是听人说。

## 1. 为什么不能「比谁火」

Agent 框架半年一变：今天热门的，明年可能没人维护；今天的「最佳实践」，几个月后就过时。所以**「哪个框架最好」是个会失效的答案，而「怎么判断框架」是不会失效的能力**。

真正该问的三个问题，对应三个维度：

## 2. 维度一：状态管理模型

问：**这个框架怎么表示「任务进行到哪了」？**

- 是**显式状态**（如图、状态机），你能看到、能持久化、能恢复？
- 还是**隐式状态**（藏在对话历史里），进程一挂就丢？

这直接决定了你能不能做**断点续跑、人工干预、审计**（阶段 3 的 C15 全是在讲这个）。**状态管理模型越显式、越可持久化，越适合长任务和生产环境。**

**怎么验**：把一个跑了一半的任务状态 dump 出来，问三件事——是不是普通 JSON？能不能存进数据库？换台机器读回来能不能接着跑？三个都能，才算「显式且可持久化」。

## 3. 维度二：可观测性支持

问：**出问题时，能不能看到每一步发生了什么？**

- 有没有 trace（每个 Agent、每步、每次工具调用的完整记录）？
- 有没有可视化的执行图？
- 日志和埋点方不方便？

多 Agent 调试的命门就是 trace（见 C16-2 第 4 节）。**一个没有好的可观测性支持的框架，出了问题你只能靠猜。** 这也是为什么阶段 5.1 要提前做。

**怎么验**：别信文档里的截图。跑一个注定失败的任务，计时看你能不能在三分钟内回答：它死在第几步、那一步的输入是什么、模型原样返回了什么。答不出来，就是没有可观测性。

## 4. 维度三：逃生舱（Escape Hatch）

问：**框架不爽时，我能不能直接写原生调用绕过去？**

- 框架是「薄封装」，底层随时能降到原生 SDK 调用？
- 还是「厚封装」，所有东西都被包死，想绕都绕不出去？

「逃生舱」指的就是：**框架不该把你锁死**。一个健康的框架，应该允许你在任何一层「逃」到原生调用——用框架的便利，但保留不用的自由。

**怎么验**：见 C17-3 的 50 行 demo——把 demo 的状态存盘、读回、继续跑。做不到的，逃生舱是假的（C17-3 第 1 节有「三种成色」）。

## 5. 三个维度一句话

> 状态管理决定「能不能跑长任务」，可观测性决定「出了问题能不能查」，逃生舱决定「被框架坑了能不能跑」。

## 6. 不该拿来做依据的三个指标

选型讨论里最常见的三个论据，其实都不可靠：

| 指标 | 为什么不能用 | 该换成什么 |
|---|---|---|
| **star 数 / 下载量** | 反映「有多少人试过」，不反映「长期好不好用」 | 看 issue 里未关的严重 bug |
| **上手速度** | 只影响前两周；框架是要用一年的 | 看三个月后的维护成本 |
| **官方 benchmark** | 厂商自己发的，任务也不是你的 | 自己那几十条评测集（C20） |

一句话：**能被营销影响的指标，都不能当选型依据。**

## 7. 一票否决项

有些信号出现时，三个维度都不用细算了，直接排除：

1. **状态只能留在进程内存里，且无法导出** —— 长任务直接出局（挂了就全丢）。
2. **不支持任何形式的 trace 导出** —— 生产环境别碰，出问题只能重跑。
3. **许可证限制你改源码** —— 逃生舱形同虚设，「能降到原生」只是口号。

这三条之所以叫「否决」而不是「扣分」，因为它们是**上线后无法补救**的——前两项是架构级的，第三项是法律级的。

## 8. 小结

- 别比谁火，比三个维度：状态管理（显式 vs 隐式）、可观测性（trace）、逃生舱（能否降级到原生）。
- 三个维度分别决定：能否跑长任务、能否调试、能否不被锁死。
- 每个维度都有验证动作：状态 dump 成 JSON、跑一次失败任务计时排障、50 行 demo 存盘续跑。
- star 数、上手速度、官方 benchmark 都不该作为依据。
- 三个维度其实是三个「能不能」：能不能续跑、能不能查、能不能逃。任一为否就否决，不必算总分。
- 一句话记住优先级：三维度管「上线能不能扛」，其余指标管「用起来爽不爽」——先能扛，再谈爽。
- 状态不可导出、trace 不可导出、许可证限制改码——三条任一命中，直接否决。
- 这套标准不随框架变化失效，是会保值的能力。

## 思考题

> 先自己答，再展开参考思路。这三问不考记忆，考的是你能不能把它用在自己的项目上。

1. 状态管理、可观测性、逃生舱三个维度，各自决定「能不能」做什么？
2. 为什么 star 数、上手速度、官方 benchmark 都不该作为选型依据？
3. 一票否决项有哪几条？为什么是「否决」而不是「扣分」？

1. 能不能续跑（状态可否导出）、能不能查（trace 是否完整可导出）、能不能逃（能否降级回原生调用）。三个都是上线门槛。
2. star 数反映的是传播度，不是工程质量；上手速度在第二周就不重要了；官方 benchmark 用的是别人的任务，跟你的失败模式无关。
