# C17-3 · 逃生舱与自研取舍
> 阅读约 10 分钟。目标：搞懂「逃生舱」的真正含义，以及什么时候自研比用框架更划算。

## 1. 逃生舱是什么

逃生舱（Escape Hatch）不是「框架留了个后门」，而是**框架的抽象允许你在任何一层降到原生调用**：

```python
# 用框架的便利组织流程
graph = build_graph(...)        # 框架帮你管状态、编排

# 但某个节点里，我可以直接写原生 SDK 调用，不被框架包死
def my_node(state):
    return client.chat.completions.create(...)   # 原生调用，逃生舱
```

判断一个框架有没有好的逃生舱，问一句：

> 当框架的「魔法」不符合我的需求时，我能不能关掉魔法、回到最朴素的代码？

**能，就是好框架；不能，框架就从「工具」变成了「牢笼」。**

### 逃生舱的三种成色

「有逃生舱」不是二值的，它分三档。判断标准很土：**如果明天要换掉这个框架，你要重写多少。**

| 成色 | 表现 | 换框架的代价 |
|---|---|---|
| **差** | 节点里能写代码，但状态、重试、trace 全在框架内部 | 基本等于重写 |
| **中** | 节点能降级到原生调用，但状态是框架私有格式 | 逻辑可留，状态要迁 |
| **好** | 状态就是普通 `dict` / JSON，节点就是普通函数 | 只换调度器，业务逻辑原样搬 |

第三档才是真逃生舱。前两档的区别只是「牢笼有没有窗」——你能看到外面，但出不去。

> 检测方法：写一个 50 行的最小 demo，然后试着把它的**状态** dump 成 JSON 存盘、再读回来继续跑。做不到的，逃生舱不合格。

## 2. 什么时候该自研

自研不是「不信任框架」，而是下面几种情况时，自研的净收益更高：

1. **控制流简单**：你的 Agent 就是「循环 + 几个 if」，框架的图/角色抽象反而是负担（阶段 2 手写的 100 行 ReAct 就是证据——简单任务根本不需要框架）。
2. **需要完全掌控**：有特殊的状态管理、重试、权限需求，框架的默认行为处处和你要的冲突。
3. **想避免锁定**：框架 API 半年一变，团队不想被某个框架的升级牵着鼻子走。
4. **团队已理解底层**：你已经手写过循环（阶段 2），自研的「隐形成本」其实不高。

## 3. 自研的真实成本

别把自研想成「免费」。自研要自己写的东西，框架已经帮你写好了：

- 状态管理与持久化（框架的 checkpoint，你要自己写）。
- 可观测性（框架的 trace，你要自己埋点）。
- 重试、错误处理（框架的容错，你要自己兜）。

所以自研和框架的取舍，本质是：

> **框架帮你省「写这些通用件」的时间，但代价是「你必须按它的方式写」。**

### 自研前先做一次最小实验

别在纸上辩论，花半天做三件事：

1. 手写一个只有「循环 + 工具 + 一次重试」的版本，跑你最真实的一个任务。
2. 再试着加两样：**把状态存成 JSON**、**把每步耗时打出来**。
3. 记下这三步各花了多久。

结果只有三种，对应三个决定：

| 现象 | 说明 | 决定 |
|---|---|---|
| 一天内跑通，状态与日志都顺手 | 你的需求就在「薄 loop」这一档 | 自研，别上框架 |
| 卡在状态持久化 / 重试 / 并行超过两天 | 你需要的正是框架那几件通用件 | 上框架，挑逃生舱好的 |
| 跑通了，但 trace 靠 print | 你缺的不是框架，是观测（C19） | 自研 + 补 30 行埋点 |

## 4. 一条实用的决策路径

1. 先**手写跑通**（阶段 2 已经做过）——理解底层，这是判断一切的前提。
2. 任务**简单、控制流清晰** → 自研，别引入框架的复杂度。
3. 任务**复杂、需要状态/编排/trace** → 用框架，但**只选逃生舱好的**（见 C17-1）。
4. 用了框架后**发现处处别扭** → 别硬撑，用逃生舱降到原生，或干脆自研。

### 反过来说：这三种情况别自研

1. **要跑小时级长任务**，而团队没维护过「进程挂了能续跑」的服务——状态与幂等这两件事，踩坑成本远高于框架的抽象成本。
2. **需要人工介入 + 审计**。HITL（C23-3）与 trace（C19）都是框架白送的，自研要自己补齐。
3. **上线时间紧**。自研的隐形成本不在第一周，通常在第三周（边界条件、重试、并发）集中爆发。

> 命中任何一条，先上薄框架；等你看清它的边界、也看清自己的需求，再谈替换。

## 5. 一个朴素判断

> 框架的真实收益 = 它帮你省的时间 − 它锁死你带来的代价。

很多人只看前半段（「它能帮我少写代码！」），忽略后半段（「但它逼我按它的方式写」）。把这个账算全，多数「框架 vs 自研」的纠结就清楚了。

## 6. 小结

- 逃生舱 = 框架允许你随时降到原生调用；问「能不能关掉魔法回到朴素代码」。
- 自研适合：控制流简单、要完全掌控、想避免锁定、已理解底层。
- 自研要自己写状态/trace/容错；取舍本质是「省时间」vs「被锁死」。
