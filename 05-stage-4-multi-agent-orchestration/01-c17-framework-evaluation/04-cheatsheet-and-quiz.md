# C17-4 · 速查表与自测
> 阅读约 10 分钟。目标：把框架评判的三维度与自研决策固化成一页，并用自测检验。

## 速查表

### 评判框架的三维度

| 维度 | 问什么 | 决定 |
|---|---|---|
| 状态管理 | 状态显式还是隐式？能否持久化？ | 能不能跑长任务 |
| 可观测性 | 有没有 trace、执行图？ | 出了问题能不能查 |
| 逃生舱 | 能否降到原生调用？ | 被坑了能不能跑 |

### 三框架定位（以写作为准）

| 框架 | 定位 | 适合 |
|---|---|---|
| LangGraph | 图/状态机，最显式可控 | 复杂流程、长任务 |
| AutoGen | 对话式协作 | 探索型、自主对话 |
| CrewAI | 角色式高层封装 | 快速搭角色流水线 |

### 自研决策

自研适合：控制流简单 / 要完全掌控 / 想避免锁定 / 已理解底层。
框架收益 = 省的时间 − 锁死的代价。

## 自测题

1. 一个框架「上手很快，但所有 API 都包死了，想绕到原生调用做不到」。用三问判断：它缺哪个维度？会带来什么后果？
2. 你要做一个「多步骤、带断点续跑、需要精细控制每步」的复杂 Agent。按三问，你更倾向哪个框架？为什么？
3. 你的 Agent 就是一个「循环 + 几个 if」，还要不要上框架？为什么？
4. 为什么说「哪个框架最好」是个会失效的答案，而「怎么判断框架」不会？
5. 「逃生舱」的精髓是什么？用一句话说清。

## 参考答案要点

1. 缺「逃生舱」。后果：框架从工具变牢笼——框架行为不符需求时无法绕开，被迫按它的方式写，升级/迁移成本高。
2. 倾向 LangGraph：显式状态 + 内置 checkpoint（满足断点续跑）、trace 完善（可观测性强）、节点可写任意代码（逃生舱好）。
3. 不上。控制流简单时框架的抽象反而是负担（阶段 2 的 100 行 ReAct 就是证据），自研更轻、更可控。
4. 框架半年一变，具体结论会过时；但「状态管理 / 可观测性 / 逃生舱」这套评判标准不随框架变化失效。
5. 逃生舱 = 允许你随时关掉框架的「魔法」、降到原生调用，用框架的便利但不被它锁死。
