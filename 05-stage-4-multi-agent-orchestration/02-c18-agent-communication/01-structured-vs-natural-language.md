# C18-1 · 结构化消息 vs 自然语言
> 阅读约 10 分钟。目标：Agent 之间传消息，选结构化还是自然语言——这个选择决定了后面聚合有多难。

## 1. 两种消息格式

| 格式 | 例子 | 特点 |
|---|---|---|
| **结构化** | JSON 字段：`{"结论": "涨", "置信度": 0.8, "依据": "..."}` | 字段明确、可校验、可聚合 |
| **自然语言** | 一段话：「我觉得市场会涨，因为……」 | 灵活、表达丰富、难程序化处理 |

## 2. 各自的强项与代价

**结构化消息**：

- ✅ 可程序化校验（字段对不对、类型对不对）。
- ✅ 可聚合（多个 Agent 的「置信度」字段直接比大小）。
- ✅ 不丢信息（字段都在）。
- ❌ 要预先定义 schema，灵活度低；表达不了太复杂的意思。

**自然语言消息**：

- ✅ 灵活，能表达复杂、模糊、需要发挥的内容。
- ❌ 难校验（「我觉得还行」到底行不行？）。
- ❌ 难聚合（三段话没法直接「取平均」）。
- ❌ 容易被误读。

## 3. 怎么选：看「谁来消费这条消息」

> **给程序/下游 Agent 处理的，用结构化；给模型「理解、发挥、综合」的，用自然语言。**

- Agent 之间**传递数据、结论、状态** → 结构化（像 API 的返回）。
- 需要模型**综合、润色、判断**的中间内容 → 自然语言。

一个常见错误：**让 Agent 之间互相写大段自然语言**，结果每个下游 Agent 都要「重新读懂」上游的一大段话，既贵又容易误读。

## 4. 一个好用的折中：结构化 + 自然语言摘要

很多场景最优是「两者结合」：

```json
{
  "conclusion": "看涨",          // 结构化：机器可直接处理、可聚合
  "confidence": 0.78,            // 结构化：可比较
  "evidence": ["财报超预期", "资金流入"],   // 结构化：可追溯
  "summary": "财报超预期且北向资金持续流入，短期看涨。"  // 自然语言：供模型综合
}
```

**结论、置信度、依据用结构化字段**（可校验、可聚合），**再附一段自然语言摘要**（供需要综合时用）。

## 5. 小结

- 结构化消息：可校验、可聚合、不丢信息，但要预定义 schema。
- 自然语言：灵活但难校验、难聚合、易误读。
- 原则：给程序/下游处理的用结构化，给模型综合的用自然语言；常用「结构化字段 + 自然语言摘要」折中。
