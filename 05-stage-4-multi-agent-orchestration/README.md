# 阶段 4 · 多 Agent 与编排
**层级**：阶段（阶段 4 共 3 门课）
**规模**：3 门课 / 13 篇正文（另含 3 篇课程索引）
**时长**：约 3–4 小时（含动手时间）
**前置**：阶段 2（Agent 循环）、阶段 3（上下文隔离是拆分的核心动机）
**产出**：一个可拆任务、可并行的小型多 Agent 系统 + 与单 Agent 的成本/效果对比数据

## 这个阶段解决什么问题

单 Agent 跑简单任务没问题，任务一复杂就会退化：

- **上下文污染**：几十步之后，早期无关信息一直占着位置，模型注意力被稀释。
- **目标漂移**：一个 prompt 里塞了 8 条要求，跑着跑着就顾此失彼。
- **无法并行**：单线程循环，本来能同时做的三件事只能排队。

于是自然会想：拆成多个 Agent 各管一摊。但多 Agent 不是免费的：

> token 消耗通常是单 Agent 的 3–10 倍（工程经验值），延迟、调试难度、失败点数量同步上升。

这一阶段的核心不是「怎么拆」，而是**先判断该不该拆**——多数情况下答案是不该。

## 学完你能做到

1. 用具体信号判断一个任务该不该拆成多 Agent，以及拆了要付多少代价。
2. 实现四种编排模式，知道各自适合什么形状的任务。
3. 对主流框架做选型判断，知道什么情况下自研更划算。
4. 设计 Agent 之间的通信协议与结果聚合方式（而不是让它们互相写长文本）。

## 推荐阅读顺序

1. **C16**— 先判断该不该拆，再学四种拓扑——这是本阶段的骨架。
2. **C17**— 有了拓扑，再决定用什么框架/自研来落地。
3. **C18**— 通信与聚合，让多个 Agent 真正「协作」而不是「各说各话」。

## 阶段出口标准

做完这三件事才算过：

1. **一个可拆任务、可并行的小型系统**：至少 2 个 Agent，有明确的编排拓扑。
2. **一份对比数据**：同一个任务，单 Agent vs 多 Agent 的成功率、token 成本、耗时。用数据说话，别凭感觉。
3. **一次负结果记录**：至少记录一个「拆了反而更差」的尝试及原因分析。
