# C19-1 · 为什么 Agent 必须可观测
> 阅读约 12 分钟。目标：认清 Agent 与传统程序在调试上的根本差异，把「可观测性」从上线前补丁升级为第一优先级。

## 1. 一句话结论

> 传统程序出了 bug，你能复现它；Agent 出了错，你可能连「它当时看到了什么、调了什么、为什么这么选」都答不上来。

可观测性不是可选项，是 Agent 能长期维护的**地基**。没有它，后面阶段 5 的评测、成本、安全全都无从谈起——你连「改动是变好还是变坏」都测不出来。

## 2. 三个根本差异

为什么传统程序的经验不能直接照搬？因为 Agent 与传统程序有三处本质不同：

### 差异一：非确定性

同一个输入、同一个 prompt，Agent 的中间步骤可能每次都不同（采样、模型更新、重试）。传统程序里「复现 bug」是第一招，在 Agent 上这招常常失灵——**你复现不出来**。

> 后果：没有 trace，你只能靠「再跑一次碰运气」，而它可能这次又对了。

### 差异二：状态藏在上下文里

Agent 的「程序状态」不是内存变量，而是**消息数组**——system prompt、工具定义、历史、工具返回值全堆在里面。任何一步错了，错误会像滚雪球一样越滚越大（呼应 C11 的失效模式）。

> 后果：崩溃发生在第 8 步，但根因往往在第 3 步的一次工具返回。没有逐步记录，你定位不到第 3 步。

### 差异三：多跳、多工具、多模型

一次任务可能横跨十几个工具调用、换两三个模型、并行几个子任务。任何一个环节出错，都要能回答「它当时想干什么、拿到了什么、据此做了什么决定」。

## 3. 可观测性要回答的三个问题

设计 trace 时，目标是让任何一次任务，事后都能回答：

1. **发生了什么**：完整步骤序列，每一步的输入输出、耗时、token。
2. **它为什么这么做**：每步决策依据什么（哪个工具返回、哪段 prompt）。
3. **结果对不对、贵不贵**：最终结果是否达标、总共花了多少钱。

三条分别对应后面的三个用途：**调试**（发生了什么）、**评测**（结果对不对）、**成本**（贵不贵）。

## 4. 一个反直觉的事实

> trace 的价值不是在「出事」那一刻体现的，而是在「优化」时体现的。

多数人等到线上出问题才想要 trace，但那时已经晚了。真正的用法是：**平时就把每次运行记下来**，改 prompt、换模型、调参数时，能立刻翻出「改动前后的完整对比」。这也是阶段 6 三个项目验收标准里「量化结果」的前提。

## 5. 最小可用版本

在引入任何工具之前，先理解「最小 trace」长什么样。阶段 2 的 C9-3 已经埋了伏笔——在循环里打日志：

```python
print(f"[step {step}] tool_calls: {msg.tool_calls}")
# ... 执行工具 ...
print(f"[step {step}] result: {result}")
```

这已经能回答「发生了什么」。C19-2 会把它升级成结构化的 trace / span，C19-4 再谈要不要上现成工具。**核心是现在就开始记录，别等完美的工具。**

## 6. 小结

- Agent 非确定性 + 状态藏上下文 + 多跳多工具，决定了「复现 bug」这套传统经验基本失效。
- 可观测性要回答三问：发生了什么、为什么这么做、结果对不对贵不贵。
- trace 的价值在「优化」时体现，平时就要记，出事才想起就晚了。
- 最小 trace 只是循环里几行日志，先动起来。
