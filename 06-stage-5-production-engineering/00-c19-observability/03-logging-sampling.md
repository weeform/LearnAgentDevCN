# C19-3 · 日志规范与采样
> 阅读约 12 分钟。目标：让 trace 数据「能查、能存、不泄密」，解决全量记录带来的存储与隐私两个新问题。

## 1. 结构化日志，而不是 print

`print` 是人看的，日志是要被机器**检索和聚合**的。结构化日志（JSON 一行一条）才能支撑「查某个 trace 的全部 span」「按模型聚合耗时」这类操作。

```json
{"ts":"2026-10-22T22:00:01Z","trace_id":"a1b2","span":"llm.call",
 "model":"gpt-4o-mini","tokens":{"in":1200,"out":80},"duration_ms":940,"status":"ok"}
```

三条基本规范：

1. **一条事件一行 JSON**，字段名统一小写下划线，不混用中文键。
2. **每个事件必须带 `trace_id` 和 `span_id`**，否则日志和 trace 对不上，等于白记。
3. **时间统一用 UTC 的 ISO 8601**，跨时区/跨服务才不会错位。

## 2. 采样：数据爆炸后的必然选择

开发期全量记没问题，但线上 Agent 一天几万次运行、每次几十个 span，数据会迅速膨胀。采样是必然的，关键是**采什么、留什么**：

| 策略 | 做法 | 适用 |
|---|---|---|
| 全量（开发/评测） | 一条不漏 | 本地调试、评测跑分，数据量小 |
| 固定比例 | 按 `trace_id % N == 0` 采 1/N | 线上常规流量，均匀、可复现 |
| 按结果偏置 | 失败的、超时的**必留**，成功的按比例采 | 线上生产：错误最珍贵，不能采丢 |
| 按成本偏置 | token 高的必留 | 找「最贵的任务」做优化 |

> 关键原则：**失败的样本永远全留**。你优化 Agent 时最需要看的不是成功案例，而是失败案例——成功案例千篇一律，失败案例各有各的原因。

## 3. 敏感信息脱敏（最容易踩的坑）

trace 会把 prompt、工具返回、用户输入原样记下来。这意味着：

> **trace 库里藏着你系统里最敏感的东西**：用户的隐私、数据库返回、API 密钥、内部 prompt。

三个必须做：

1. **默认假设会泄密**：一切进 trace 的内容，都当作「可能被不该看的人看到」来对待。
2. **密钥零容忍**：任何 API key、token 绝不进日志。用环境变量注入，日志框架里加正则过滤（如匹配 `sk-`、`Bearer ` 的模式）。
3. **用户数据最小化**：PII（姓名、手机号、身份证、地址）在落盘前脱敏或哈希。宁可少记，不可多泄。

一个朴素的脱敏思路：在写日志前过一层 `redact()`，按规则替换。

```python
import re
PATTERNS = [
    (r"(sk-[A-Za-z0-9]{10,})", "[REDACTED_KEY]"),
    (r"(1[3-9]\d{9})", "[REDACTED_PHONE]"),
]
def redact(s):
    for p, r in PATTERNS:
        s = re.sub(p, r, s)
    return s
```

> 这不能替代真正的安全方案，但它兜住了最常见、最致命的几类泄漏（密钥、手机号）。

## 4. 日志分级：别让噪声淹没信号

沿用通用惯例，但按 Agent 场景调整：

- **ERROR**：任务失败、模型调用持续失败、沙箱逃逸尝试——需要人介入。
- **WARN**：重试、降级、超预算、命中限流——自动恢复了，但要关注。
- **INFO**：每次 span 的完成事件（上文的 JSON）——这是 trace 的主体。
- **DEBUG**：完整 prompt 与工具返回全量——**只开在开发环境**，生产关掉。

> 注意：完整 prompt 常含敏感信息，放 DEBUG 而不是 INFO，生产默认不开。

## 5. 小结

- 结构化日志（一行一 JSON）+ 每条带 `trace_id`，才能被检索和聚合。
- 采样要「按结果偏置」：失败的、贵的必留，成功的才按比例采。
- 敏感信息脱敏：密钥零容忍、用户数据最小化，写日志前过一层 redact。
- 完整 prompt 放 DEBUG，生产默认关，别让噪声淹没信号。
