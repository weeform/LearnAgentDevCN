# C19-5 · 速查表与自测
> 阅读约 13 分钟。目标：把可观测性的核心结论固化成一页，并用自测检验。

## 速查表

### 为什么要可观测

- Agent 非确定性 → 复现 bug 常失灵。
- 状态藏上下文 → 崩溃在 8 步、根因在 3 步。
- 多跳多工具多模型 → 任一环节都要能回看。

### trace / span

| 概念 | 含义 |
|---|---|
| trace | 一次任务全程，唯一 `trace_id` |
| span | 一个阶段（一次 LLM / 工具调用），父子成树 |

### span 九个字段

ID/父子 · 名字 · 起止时间 · 输入 · 输出 · token · 模型名 · 状态 · 错误。

> 最易漏：`model`（换模型对比）、完整 `input`（理解决策依据）。

### 一个 span 长什么样

```json
{
  "trace_id": "tr_8f21c9", "span_id": "sp_03", "parent_id": "sp_01",
  "name": "tool.search",
  "start": "2026-10-31T10:12:03.114Z", "end": "2026-10-31T10:12:03.268Z",
  "input":  {"q": "退货政策", "top_k": 5},
  "output": {"hits": 0},
  "attributes": {"tool.name": "search", "prompt.version": "v3", "retry": 0},
  "status": "ok", "error": null
}
```

`hits: 0` 就是 C19-1 那个案例的根因——**一眼可见，不用猜**。这就是「字段设计对了，排查只需要看一眼」的意思。

### 排查时先看哪个字段

| 症状 | 先查 |
|---|---|
| 答非所问 / 编造 | 检索 span 的 `output.hits`、工具返回原文 |
| 同样的活有时好有时坏 | `attributes.retry`、temperature、`model` 是否变了 |
| 慢 | 各 span 耗时占比，先看最长的那个，别平均 |
| 突然变贵 | 单次 `input_tokens` 是否跳档、`prompt.version` 是否换了 |
| 中途断掉 | 第一个 `status=error` 的 span，看它的 `error` |

### 采样策略

失败的、超时的、贵的**必留**；成功的按比例采。开发/评测期全量。

### 敏感信息

密钥零容忍、用户数据最小化、写日志前过 `redact()`；完整 prompt 放 DEBUG，生产默认关。

### 落地路径

| 场景 | 选择 |
|---|---|
| 个人/阶段 6 demo | 手写最小 trace |
| 上线、要标准化 | OpenTelemetry + 自托管后端 |
| 团队协作、要评测闭环 | LangSmith 类托管 |
| 数据敏感、不许出域 | OTel + 自托管，不走托管 |

## 自测题

> 答对 6 道以上，进入 C20。

1. 为什么 Agent 的 bug「复现」这一招经常失灵？这决定了 trace 的哪个设计原则？
2. 一个 span 只记了 `name`、`start/end`、`tokens`，漏了什么会致命？为什么？
3. 线上采样时，为什么「失败的必留、成功的按比例采」而不是反过来？
4. 把完整 prompt 打进 INFO 级别日志有什么风险？应该怎么放？
5. 什么时候手写 trace 就够了，什么时候必须上 OTel 或托管平台？
6. trace 里只有模型调用、没有业务维度（prompt 版本、检索命中数），会带来什么具体麻烦？
7. 「按 10% 随机采样」在排查失败时为什么特别危险？该怎么改？

## 参考答案要点

1. 因为非确定性：同输入不同中间步骤，复现不出来。这决定了「平时就全量记录、别等出事才想要 trace」的原则。
2. 漏了 `input`/`output` 和 `status`/`error`。没有输入输出，不知道它「看到什么、得到什么」；没有状态，分不清成败。还容易漏 `model`，导致无法做换模型对比。
3. 优化 Agent 时最需要看的是失败案例（失败各有原因），成功案例价值低且量大。所以失败的、贵的必留，成功的才按比例采。
4. 完整 prompt 常含用户数据、内部指令甚至密钥，打进 INFO 会长期留存且易被检索。应放 DEBUG，生产默认关闭；并先过 `redact()` 脱敏。
5. 手写 trace 只适合「回看单次任务步骤」的原型/学习期；当开始要「检索、聚合、告警、跨服务关联」时手写到头了，需要 OTel；需要「trace 一键转评测样本」的协作闭环时上托管平台。
6. trace 会退化成一堆长得一样的 HTTP 调用记录：能看出「调了模型、花了多少 token」，看不出「是哪一版 prompt、检索命中了没有」，于是无法回答「改动前后差在哪」——而这正是 trace 最主要的用途。业务维度必须在 span 上手动 `set_attribute`。
7. 因为请求开始时不知道这次会不会失败，随机采样会把失败样本同样按比例丢掉，恰好在最需要证据时没有证据。改法：错误/超预算的 trace 强制 100% 保留（或做尾部采样），正常请求才按比例采。
