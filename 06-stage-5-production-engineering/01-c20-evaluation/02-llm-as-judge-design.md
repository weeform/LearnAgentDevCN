# C20-2 · LLM-as-judge 评分维度设计
> 阅读约 14 分钟。目标：设计一个能稳定、可复现打分的 LLM judge——rubric 怎么定、用哪种打分尺度、输出怎么保证可解析。

## 1. 为什么需要 LLM-as-judge

人工打分太慢太贵（C20-1 里标注 30 条都嫌贵，每轮改动都人工打分更不现实）。用另一个 LLM 当裁判自动打分，是现在的主流做法，叫 **LLM-as-judge**。

> 一句话：用「一个便宜的、被精心写 prompt 的模型」去替代「一个贵的人」做重复打分。

它的定位不是「绝对权威」，而是「**能复现、能跑量、够便宜**的近似裁判」。承认它是近似，是后面 C20-3 讨论偏差的前提。

## 2. 先定判据，再打分

新手最常犯的错：直接让 judge「给这段回答打个分」。没有判据，judge 只能按自己的口味打分，打分就变成了玄学。

正确顺序：**先把「什么算对、什么算错」写成人话判据，再让 judge 照判据打分**。这组判据叫 **rubric（评分标准）**。

```markdown
判据（节选）：
- 是否调用了 search_weather 工具并传入正确城市名？
- 是否基于工具返回的温度/天气给出带伞建议？
- 是否出现编造的温度数值？
```

> 经验值：rubric 写得越细，judge 越稳定。你连「对不对」都说不清，judge 更说不清——它只是放大你的含糊。

## 3. 三种打分尺度

| 尺度 | 输出 | 适合 | 代价 |
|---|---|---|---|
| 二元通过 | 通过 / 不通过 | 判据明确、非对即错的硬任务 | 信息量少，看不出「差多少」 |
| 李克特分级 | 1–5 分 | 质量有梯度、要比较改动 | 4 分和 5 分的边界靠人定，易漂移 |
| 成对比较 | A 比 B 好 / 平 | 两版 prompt 选谁 | 每次只能比两个，成本翻倍 |

选尺度的原则：**能用二元就不要用分级**。二元判据最清晰、最不容易被 judge 的「口味」污染（呼应 C20-3 的偏差）。

> 反直觉：5 分制听起来更精细，实际 4 分 5 分之间的 judge 主观性远大于信息增量。先上二元通过，跑顺了再考虑分级。

## 4. 输出要结构化，解析要容错

judge 的输出要逼成 JSON，机器才好解析聚合。一个最小 judge 输出 schema：

```json
{
    "pass": true,
    "score": 1,
    "reason": "调用了工具，城市名正确，基于 18 度给出带伞建议",
    "criteria_hits": ["工具调用正确", "无编造数值"]
}
```

但 LLM 的输出不是 100% 合法 JSON——它会多打一个逗号、包一层 markdown 代码块、漏一个引号。所以解析必须容错，这直接呼应 C4 的结构化输出容错：**先尝试标准解析，失败再做清洗重试，再失败降级为「本次不计分并告警」**。

```python
def parse_judge(raw: str):
    for fn in (json.loads, strip_code_fence_and_load, extract_first_json):
        try:
            return fn(raw)
        except Exception:
            continue
    raise JudgeParseError(raw)   # 三次都失败，别硬猜
```

> 容错的目标不是「猜出它本来想说什么」，而是「能救就救，救不了就明确报错」，别把 parse 失败静默当成「不通过」——那会让评测分失真。

## 5. judge 的 prompt 也要写得和被评测任务一样严谨

很多人对被评测的 Agent prompt 反复打磨，对 judge prompt 却随手一写。这是错的。

> judge 的 prompt 应该享受和主任务 prompt 同等的严谨度：明确角色、明确判据、给 few-shot 示例、要求输出格式。这正是 C6 讲的 prompt 工程在「裁判」这个特殊任务上的应用。

一个 judge prompt 的最小骨架：

```markdown
你是评测裁判。请严格按下面的判据，判断「助手回答」是否合格。

判据：
1. ...
2. ...

助手回答：
{answer}

只输出 JSON，格式：{"pass": bool, "reason": "一句话"}
```

> few-shot 对 judge 尤其重要：给它 2–3 个「该过 / 不该过」的示例，比写一百字规则更管用——它靠示例校准「及格线」。

## 6. 小结

- LLM-as-judge 是「便宜、能复现、能跑量」的近似裁判，不是绝对权威。
- 先定 rubric（对/错判据），再打分；rubric 越细越稳。
- 三种尺度：二元、李克特 1–5、成对比较；能用二元就别用分级。
- 输出逼成 JSON，解析要三层容错，救不了就明确报错。
- judge prompt 和主任务 prompt 同等严谨，few-shot 校准及格线。
