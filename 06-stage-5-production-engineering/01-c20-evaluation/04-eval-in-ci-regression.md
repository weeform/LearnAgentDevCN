# C20-4 · 评测接入 CI 与回归
> 阅读约 12 分钟。目标：把评测从「手动跑一次」变成「每次改动自动跑」，并定清回归通过线与成本、频率。

## 1. 为什么评测要进 CI

评测如果只是「想起来才跑一次」，那它和没造没区别——因为 Agent 的改动极其频繁（改 prompt 是家常便饭），靠人自觉跑评测必然漏。

> 结论：评测的价值不在「跑一次」，而在「每次改动都跑」。把它接进 CI，让改动过不了线就不许合并。

## 2. 一键跑对比

评测脚本要做到一件事：**对同一个评测集，跑两个版本，输出一张对比表**。通常是「当前分支 vs 主分支（baseline）」或「新模型 vs 旧模型」。

```python
for case in eval_set:
    baseline = run(case, prompt=BASELINE, model=MODEL)
    candidate = run(case, prompt=NEW_PROMPT, model=MODEL)
    row = {
        "input": case["input"],
        "baseline": judge(case, baseline),
        "candidate": judge(case, candidate),
    }
    # ...逐条记录，最后按类别汇总
```

> 关键：对比要**逐条对拍**，而不是只比总分。总分涨了 2 分，可能是「高频题全对了」也可能是「一个类别崩了被别的类别拉平」——不逐条看，你会被总分骗。

## 3. 回归通过线

回归的意思是：**改动不能让它变坏**。通过线要量化，不能「感觉差不多」。

| 指标 | 经验值 |
|---|---|
| 整体通过率 | 不允许跌过 N 个点（如 2 个点） |
| 单类别 | 任一类别不允许跌过更大阈值（如 5 个点） |
| 失败路径 | 失败恢复类用例**只许增不许减**，一条都不许退 |

> 经验值：给「失败路径」设最严的线——线上真正出事的就是这些 case，它们退一步，比你整体跌 5 个点更危险。

通过线的本质是**权衡**：设太严，团队不敢改，迭代停滞；设太松，等于没门禁。2 个点是个常用起点，按你团队的承受度调。

## 4. 评测的成本：judge 也要钱

很多人忽略：评测不是免费的。每跑一轮 = 每个 case 一次主模型调用 + 一次（甚至两次）judge 调用。

> 100 条 ×（1 次候选 + 1 次基线）×（1 次 judge）≈ 200+ 次 LLM 调用。成对比较、位置对调取平均还会翻倍。这是实打实的钱，归入 C21 的成本口径。

省钱三招：

1. **judge 用便宜模型**：判据清晰的打分任务，小模型通常够用（见 C22 的模型分级思路）。
2. **分层跑**：PR 只跑「30 条冒烟集」，每晚定时跑「100+ 全量集」。
3. **缓存结果**：prompt 和模型都没变的部分不重复跑。

## 5. 评测频率：PR 触发 vs 定时

| 触发方式 | 跑什么 | 目的 |
|---|---|---|
| PR 触发 | 30 条冒烟集 | 快速挡住明显改坏，秒级分钟级反馈 |
| 每晚定时 | 100+ 全量集 | 抓慢变量（模型更新、数据漂移） |
| 手动 | 任意指定集 | 深度排查某个 case |

> 经验值：PR 用「小集挡大错」，定时用「大集抓慢变」。两者职责不同，别拿全量集堵 PR——慢到没人愿意等。

## 6. 结果要留存，供 trace 回放对比

每轮评测的结果（每条的输入、两版输出、judge 打分、耗时 token）要**留存**，而不是打完就扔。

> 留存的意义：当你发现「某条用例这轮突然挂了」，你能立刻回到 C19 的 trace 里回放这条样本的完整运行过程，看它在第几步走偏。评测告诉你「哪里变差了」，trace 告诉你「为什么变差」。

所以评测产物要带 `case_id` 和 `trace_id` 的关联，让「评测结果 → trace 回放」这条链路能一键跳转。

## 7. 小结

- 评测的价值在「每次改动都跑」，接 CI 才是真正的门禁。
- 对比要逐条对拍，别只看总分；失败路径通过线最严。
- 评测要花钱：judge 用便宜模型、PR 小集 + 定时大集、结果缓存。
- 结果留存并关联 trace_id，才能从「哪里变差」追到「为什么变差」。
