# C21-1 · 单位任务成本核算
> 阅读约 12 分钟。目标：把「一次任务花了多少钱」算清楚，理解 Agent 实际成本为何远高于直觉。

## 1. 为什么按「任务」而不是「调用」算账

C3-3 教的是**单次调用**怎么算：四个计价桶乘以各自单价。但 Agent 的一次任务 = 几十次调用。只盯着单次调用的几美分，会得出「Agent 很便宜」的错误结论。

> 成本核算的最小单位是「任务」，不是「调用」。调用便宜，任务不便宜。

## 2. 一次任务的边界

先定义清楚「一次任务」从哪到哪，账才有的算：

- **起点**：用户发出一条输入（消息、指令、附件）。
- **终点**：Agent 给出最终答案，或宣告失败/超时/降级。
- **中间**：所有 LLM 调用 + 工具调用 + 重试 + 子任务，全部计入。

> 边界定在「用户输入 → 最终答案」，中间无论调多少次模型、多少次工具、重试几次，都算同一笔任务的账。这条边界是后面所有预算、告警、分级的地基。

## 3. 核算公式（复用 C3 的口径）

单次调用四桶计价公式见 C3-3，这里不重复 BPE 和分词，直接复用。一次任务的成本 = 任务内所有 LLM 调用之和：

```
task_cost = Σ 每一次 LLM 调用
            ( in_full  / 1e6 × P_in
            + in_cached / 1e6 × P_cached
            + in_write  / 1e6 × P_write
            + out       / 1e6 × P_out )
```

四个桶里，**工具调用本身不花钱**（它只是你本地/远程的函数），但工具返回会回填进上下文，变成下一次调用的输入，**重新计费**。这是 Agent 成本最容易漏算的一块。

## 4. 三个放大因素

为什么「一次任务」远贵于「一次对话」？三个放大器：

1. **多轮**：每步都把前面全部历史重发一遍（API 无状态），输入平方增长（C3-3 的 `n·B + S·n²/2`）。
2. **工具返回回填**：每个工具结果都塞回上下文，且往往很长（数据库查询结果、网页全文），下一步原样重发。
3. **重试**：失败、超时、死循环打断后重来，前面的 token 全白花。多 Agent 编排还会让每个 Agent 各自独立上下文、重复付费——这正是 C16-2 说的「token 3–10 倍」的来源。

> 反直觉事实：一个「看起来只有 3 步」的任务，可能实际烧掉 30 次调用、每步都在重发几 KB 的历史。成本不是「聊了几句」，是「把这几句重发了三十遍」。

## 5. 核算脚本

不引入库，用 C19 埋点攒下的 trace 直接算账：

```python
PRICES = {  # 美元/百万 token，快照价，以官方定价页为准（见 C3-3）
    "gpt-5-mini": {"in": 0.25, "cached": 0.025, "write": 0.31, "out": 2.00},
}

def task_cost(trace):
    """trace：C19-2 埋点产出的、一次任务内每次 LLM 调用的 token 用量"""
    total = 0.0
    for span in trace["llm_calls"]:
        p = PRICES[span["model"]]
        total += span["in_full"]   / 1e6 * p["in"]
        total += span["in_cached"] / 1e6 * p["cached"]
        total += span["in_write"]  / 1e6 * p["write"]
        total += span["out"]       / 1e6 * p["out"]
    return total
```

> 关键不在脚本，在**数据来源**：`in_full / in_cached / in_write / out` 必须来自响应的 `usage` 字段（C3-2 说过，那是唯一真实值），而不是自己估算。没有 C19 的 trace，这个脚本就是空壳。

## 6. 小结

- 成本核算最小单位是「任务」，不是「调用」。
- 一次任务 = 用户输入到最终答案之间的全部调用、工具、重试。
- 公式复用 C3-3 四桶口径；工具返回回填是「重新计费」不是「免费」。
- 三个放大器：多轮、工具返回回填、重试；多 Agent 下还会 3–10 倍（C16-2）。
