# C21-2 · token 预算与告警
> 阅读约 14 分钟。目标：给任务装上预算上限和告警，让「花多少钱」从被动对账变成主动控制。

## 1. 预算的三层粒度

预算不是拍一个总数就完事，要分层设，各有各的作用：

| 层 | 粒度 | 作用 | 典型值（示例） |
|---|---|---|---|
| 按任务 | 单次任务 token / 金额上限 | 防单次失控，熔断最灵敏 | 50K token 或 ¥0.5 |
| 按用户 | 单用户一段时间内上限 | 防刷、防单用户拖垮全局 | 每日 ¥5 |
| 按天（全局） | 全系统每日总预算 | 防整体跑飞，触发全局降级 | 每日 ¥500 |

> 经验值：**先设「按任务」和「按天」，最后才加「按用户」**。前两个解决 90% 的问题；按用户主要为了公平性，不是成本本身。

## 2. 实时告警：逼近先告警、超限再熔断

告警分两级，别把「告警」和「熔断」混成一步：

1. **逼近阈值**（如预算的 80%）：发告警，**不断请求**，让模型继续但通知人/记录日志。
2. **超限熔断**（100%）：**立刻停**，不再发起新的 LLM 调用，返回降级结果或转人工。

```python
BUDGET_PER_TASK = 50_000  # token

def check(used, budget):
    if used >= budget:
        raise BudgetExceeded("熔断")   # 不再发起任何 LLM 调用
    if used >= budget * 0.8:
        warn("逼近预算上限")            # 告警但继续
```

> 两级的意义：逼近时告警让你「早发现趋势」，超限时熔断让你「绝对不超」。只有一级的话，要么来不及反应，要么频繁误杀正常任务。

## 3. 超了是「停」还是「降级」

很多人以为超预算只能停。实际上有第三条路——**降级**：

| 策略 | 做法 | 适用 |
|---|---|---|
| 停 | 立即终止，返回失败/转人工 | 任务价值低、或再跑也大概率失败 |
| 降级 | 换便宜模型、砍工具、缩短上下文后继续 | 任务仍值得完成、只是不配用贵的 |
| 硬收口 | 禁止再调工具，强制给最终答案 | 已经拿到足够信息，只差一句总结 |

> 反直觉结论：**「降级」往往比「停」更好**——很多任务在步数/预算将尽时，其实已经拿到了 80% 的信息，就差一次「收口」。C11-3 讲的末步 `tool_choice="none"` 就是这里「硬收口」的现成手段。

## 4. 预算不是孤立参数，要和另两个配合

预算单设是「形同虚设」的重灾区。它必须和另外两个机制咬合：

- **C11 的循环步数上限**：步数 × 每步 token = 成本。步数上限是预算的**物理兜底**——预算再松，步数一到也得停。两者同时生效，才是双保险。
- **C23 的权限**：预算和权限是「能花多少」和「能干什么」两条线。花钱的操作（写库、调付费 API）不该只靠预算约束，还要走 C23 的人工确认；预算控制的是「量」，权限控制的是「质」。

> 一句话：**步数上限兜「跑多久」，预算兜「花多少」，权限兜「能不能碰」。**三者缺一个，Agent 都可能在某个维度失控。

## 5. 预算必须「事前」判，不是「事后」记

最常见的实现错误：调用完拿到 `usage`，累加，发现超了才熔断。问题是——**这一次已经花掉了**。

Agent 的单步成本不是常数：第 1 步 input 可能 2K token，第 10 步可能 30K（历史 + 工具结果滚雪球）。所以「超了再停」在最坏情况下会超出一整步，而那一步往往正是最贵的。

正确位置是**每次 LLM 调用之前**，用「已用 + 本步预估」判断：

```python
def begin_call(state, est_input_tokens, max_output=1024):
    projected = state.used + est_input_tokens + max_output
    if projected > state.budget:
        raise BudgetExceeded(f"已用 {state.used}，本步将达 {projected}")
    return projected
```

`est_input_tokens` 不需要精确，估个上界就行——你要挡的是「再来一步就爆」，不是精确记账。

### 别漏掉「看不见的钱」

三类常被漏算的开销：

- **失败的调用也可能计费**：部分厂商按实际处理 token 收费，超时、中断、流式中途取消都不例外。
- **流式响应拿不到完整 usage**：`usage` 通常在最后一个 chunk 才返回，中断时只能按已输出长度估。
- **judge / embedding / rerank 都是钱**：它们不在「主模型调用」的账单里，很容易被当成零成本。

三项加起来常占总成本的 10–20%。只统计主调用，预算会系统性低估，然后你在月末对账时才发现。

## 6. 避免「预算形同虚设」的三个坑

1. **只记不算**：埋了点却没人看，预算只在代码里躺着。要让告警**主动触达**（日志报警、消息推送），而不是等人翻看板。
2. **阈值拍脑袋且永不调**：上线后从不根据真实数据回看。正确做法是每月看一次「预算命中率」——太高说明误杀，太低说明形同虚设，据此回调。
3. **只限单次、不限累计**：单次任务都便宜，但一个用户刷 1000 次照样烧穿。**累计预算**（按用户、按天）才是防刷的关键。

## 7. 小结

- 预算三层：按任务（防失控）、按用户（防刷）、按天（防全局跑飞）。
- 告警分两级：逼近 80% 告警不打断，超限 100% 熔断。
- 检查位置在**调用前**：用「已用 + 本步预估」判，事后记账等于让最贵的那一步漏出去。
- 别漏算失败调用、流式 usage、judge/embedding 这些「看不见的钱」。
- 超额优先「降级/硬收口」，其次才是「停」。
- 预算要和 C11 步数上限、C23 权限配合，否则形同虚设。

1. 预算为什么必须在「调用前」判？事后记账会漏掉哪一步？
2. 三层预算（任务/用户/天）各防什么？只做一层会怎样？
3. 「超额优先降级而不是停」——什么情况下才该直接停？

<summary>参考思路</summary>

1. 因为最贵的那一步就是即将发生的这一步。事后记账等于允许它先花完再报警，用户侧看到的是「钱已经花超了」。要用「已用 + 本步预估」判。
