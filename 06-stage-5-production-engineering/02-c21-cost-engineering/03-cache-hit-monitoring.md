# C21-3 · 缓存命中率监控
> 阅读约 13 分钟。目标：把「缓存命中率」变成可监控、可告警的指标，抓住最省钱的杠杆。

## 1. 缓存为什么省钱（一句话）

前缀缓存把「跨请求重复的前缀 KV」存起来复用，命中部分按输入价打 1 折左右计费（原理见 C2-5）。Agent 循环每步都重发 system prompt、工具定义、历史，只要它们是稳定前缀，每一步都白捡便宜。

> 一句话记住：缓存省钱靠「稳定前缀」，省多少由「稳定前缀占总输入的比例」决定（C3-3 的结论）。

## 2. 命中率怎么算

命中率不是「缓存命中次数 / 请求次数」，而是**按 token 算**——否则一次请求里只命中 10 个 token 也算一次「命中」，自欺欺人。

```
缓存命中率 = 缓存命中 token / 总输入 token
          = in_cached / (in_full + in_cached)
```

三个厂商的观测字段见 C2-5（OpenAI `cached_tokens`、Anthropic `cache_read_input_tokens`、DeepSeek `prompt_cache_hit_tokens`）。这些字段都在响应的 `usage` 里，和 C21-1 的成本核算共用同一份数据源。

> 反直觉：**命中率 50% 不等于省钱 50%**。命中部分只打 1 折，所以「命中率 50%」的实际成本约等于「未命中 50% 全价 + 命中 50% 打 1 折」≈ 原价的 55%，只省了约 45%。要估省钱幅度，直接算 C21-1 的 `task_cost`，别用命中率心算。

## 3. 怎么提升命中率

提升命中率的手段，C2-5 和 C7-4 已经给全，这里按「性价比」重排一次：

1. **稳定前缀放最前**：system prompt + 工具定义全局不变、放最前（C2-5 模式一、C7-4 装配原则一）。
2. **易变内容放最后**：用户输入、当轮的动态内容追加在末尾，别插进前缀中间（C2-5 速查表）。
3. **历史只追加不重写**：多轮对话原样追加，不做重排/改写/重新摘要，否则前缀整体作废（C2-5 模式二）。
4. **同一文档连续多问**：RAG 场景把长文档当前缀，一次注入、多次命中，收益最大（C2-5 模式三）。

> 提醒：**别为凑 1024 token 门槛去给 system prompt 注水**（C2-5 模式五）。缓存是锦上添花，正确性优先。

## 4. 命中率告警：暴跌要能发现

命中率平时稳定在某个区间（比如 60–80%），一旦**暴跌**，几乎必然是某个「本该稳定」的东西变了：

- 改了 system prompt 或工具定义的字段 → 前缀从断裂点作废。
- 引入了「每次动态拼接一段 system」的逻辑 → 前缀不再稳定。
- 上线了 compaction/摘要，把历史重写 → 缓存整体打碎（C2-5 模式四）。

告警设计很简单：**监控命中率的时间序列，跌幅超过阈值就告警**。

```
命中率告警：当前命中率 vs 7 日均值
  掉幅 > 20 个百分点 → WARN（可能有改动破坏了前缀）
  掉幅 > 40 个百分点 → 人工介入（大概率 prompt/装配被改坏）
```

> 核心价值：命中率告警本质上是一个**「有人偷偷改了 prompt 却没说」的探测器**。它比人工 code review 更早发现「稳定前缀被破坏」。

## 5. 命中率是过程指标，别当成优化目标

有个反例值得警惕：**命中率 90%，但每个任务依然很贵。**

原因不难拆：它的前缀确实稳定（所以命中率高），但那个前缀有 50K token，每一步都在重发。打 1 折也是 5K 全价等效，20 步就是 100K 的等效量。**它优化了折扣，没优化体积。**

所以要两个指标一起看：

| 命中率 | 单任务成本 | 判断 | 该做什么 |
|---|---|---|---|
| 高 | 低 | 健康 | 别动 |
| 高 | 高 | **前缀太大** | 裁剪上下文（C7）、精简工具定义与示例 |
| 低 | 低 | 无所谓 | 任务短或调用稀疏，不值得优化 |
| 低 | 高 | 前缀不稳定 | 查装配顺序（C7-4）、有没有动态拼接 system |

一句话：**目标是「单任务成本」，命中率只是解释成本为什么高的诊断指标。**

### 一个客观限制：缓存会过期

前缀缓存有 TTL（通常 5 分钟到 1 小时，各厂商不同）。这带来三个必须知道的后果：

- **低频任务命中率天然低**：两次调用间隔超过 TTL，前缀就白存了。这不是 bug，不用修。
- **批处理能显著提高命中率**：把同一任务的多次调用挤在 TTL 内连续发出。
- **评测环境的命中率会虚高**，别拿它代表线上。

因此阈值要按场景分组看：交互式对话、批处理、定时任务三者的正常区间完全不同。混在一起算平均，告警必然误报——而误报几次之后，这个告警就没人看了。

## 6. 小结

- 缓存省钱靠稳定前缀，省多少看稳定前缀占比（C2-5 / C3-3）。
- 命中率按 token 算：`in_cached / 总输入`，别按次数算。
- 提升命中率：稳定前缀放前、易变放后、历史只追加、同文档连续问。
- 命中率暴跌 = 前缀被改坏的信号，要设告警。
- 命中率高不代表省钱：前缀太大时，折扣再低也贵。看「命中率 + 单任务成本」两个数。
- 缓存有 TTL，低频任务命中率天然低；阈值要按场景分组。
