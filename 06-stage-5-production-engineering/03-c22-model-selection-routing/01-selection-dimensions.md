# C22-1 · 选型四维度
> 阅读约 11 分钟。目标：把「选模型」从拍脑袋变成四个可量化维度的比较，并知道每个维度的数据从哪来。

## 1. 一句话结论

> 没有最好的模型，只有最适合「当前这个子任务」的模型。

「选型」的默认答案不是「上最贵的旗舰」，而是回答四个问题：这个任务需要多强、能花多少钱、能等多久、要塞多少上下文。四个维度合起来才构成一个判断。

## 2. 四个维度

| 维度 | 问的是 | 反面典型 |
|---|---|---|
| 能力 | 这个子任务，它做不做得好 | 用旗舰做分类，杀鸡用牛刀 |
| 价格 | 一次任务总共多少钱 | 只看单价，不算任务总 token |
| 延迟 | 用户能等多久 | 快任务上了慢模型 |
| 上下文长度 | 要塞多少东西进去 | 把 1M 当默认，忽略跳档 |

四个维度里，能力是「能不能」，其余三个是「划不划算」。多数人选型只盯能力，上线后被价格和延迟反噬。

## 3. 能力：数据从哪来

能力是最难量化的维度，因为它高度依赖「你的任务」。同一模型在 A 任务上第一，在 B 任务上可能垫底。

> 别信通用榜单（MMLU / Arena 那类）。那些分衡量的是「模型在别人题目上的表现」，不是「在你的 prompt + 你的工具 + 你的数据上的表现」。

正确的做法是**跑自己的评测集**：把你真实遇到的几十条任务沉淀成带标准的用例，每个候选模型跑一遍，直接比通过率（这整套方法就是 C20 讲的东西，选型是它最直接的消费者）。

三个实用提示：

1. 评测集不用大，几十条有代表性的真实任务就够初筛。
2. 重点看「你的任务里最难的 20%」，模型之间的差距往往只在难例上拉开。
3. 能力会随时间变：模型在悄悄更新，评测要能一键重跑（呼应 C20 的回归）。

## 4. 价格：算任务总价，不算单价

厂商报价是「每百万 token 多少钱」，但你要付的是**任务总价 =（输入 token + 输出 token）× 单价**。

> 一个反直觉点：Agent 的任务是「多次调用累加」出来的。一次任务可能调 10 次模型，每次都把历史全塞进输入——输入 token 会被重复计费 10 遍。

所以看价格时，真正的单位不是「每 M token」，而是「每完成一个任务多少钱」，后者要到自己的 trace 里算（C19 记的 token 就是干这个用的，C21 会把它归因到具体任务）。

## 5. 延迟：Agent 里是「累加」不是「单次」

延迟要拆成两个数看：

- **首 token 延迟（TTFT）**：用户发问到看到第一个字的时间，决定「卡不卡」。
- **总时长**：整次任务跑完的时间，Agent 里等于「N 次调用 + 工具等待」的累加。

> 单看模型单次延迟没意义。Agent 里慢的是「调用次数 × 每次延迟」：一个便宜但慢的模型，若被路由多调几次，总延迟可能超过一个贵但快的模型。

延迟数据也从 trace 来：把每个 span 的 `duration_ms` 按模型聚合，就能看到「哪个模型是延迟瓶颈」。

## 6. 上下文长度：看真实可用，不看宣传值

- 宣传的「128K / 1M」是上限，真实可用往往打折（长文中间信息被「遗忘」，见 C2 的上下文管理）。
- 长上下文有**价格跳档**：很多厂商超过 200K 之后，单价不是线性，而是直接翻几倍（具体档位以写作为准，请查最新价目）。
- 上下文不是越大越好，越大 prefill 越慢、越贵（C22-2 第 3 节展开）。

## 小结

- 选型的默认答案不是旗舰，而是「最适合这个子任务」。
- 四维度：能力、价格、延迟、上下文；能力管「能不能」，其余三个管「划不划算」。
- 能力看自己的评测集，不看通用榜单；价格算任务总价；延迟算累加；上下文看真实可用与跳档。
- 四个维度的数据都能从 C19 的 trace 里挖出来——先有观测，才谈得上选型。
