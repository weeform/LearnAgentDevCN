# C22-4 · 长上下文成本曲线与开源临界点
> 阅读约 12 分钟。目标：看清长上下文的真实成本，学会在「长上下文」和「RAG」之间选择，并算清开源自建的临界点；后半部分是速查表与自测。

## 1. 长上下文的真实成本曲线

厂商宣传的「1M 上下文」很诱人，但真实成本不是线性的：

> 多数厂商超过 200K 之后有价格跳档——单价直接翻几倍。把 1M 当默认，等于默认付几倍的价（具体档位以写作为准，请查最新价目）。

更隐蔽的是**延迟跳档**：prefill 时间随上下文近线性增长，塞满 1M 时，光把内容读进去就要几十秒（课程体检 08-review-course-health-check.md 缺口三里提过这一点）。

所以长上下文的真实成本曲线是「台阶状」：

- 0–200K：价格、延迟都平缓，随便用。
- 200K–1M：价格跳档、prefill 飙到几十秒，要三思。
- 超过 1M：通常是为极少数场景准备的，别当日常默认。

> 结论：上下文是「用钱和等待换来的空间」，默认值应该是最小够用，而不是最大能塞。

## 2. 长上下文 vs RAG：什么时候各自划算

C14-1 讲过「什么时候不需要 RAG」——反过来，这里问的是「什么时候不需要长上下文」：

| 场景 | 倾向 | 原因 |
|---|---|---|
| 全文都要精读、跨段推理（合同、论文） | 长上下文 | 切块会打断推理链 |
| 海量文档里找几条相关的 | RAG | 99% 内容无关，塞进上下文是浪费 |
| 文档会频繁更新 | RAG | 重新索引比重新塞上下文便宜 |
| 内容稳定、一次读完 | 长上下文 | 免去搭 RAG 管道的复杂度 |

> 判断口诀：**「需要整体理解」上长上下文，「只需要局部检索」上 RAG**。两者不互斥——RAG 找到的片段，最终还是要塞进上下文里。

还有一个纯成本视角：一次 1M 的 prefill 够你做几十次「检索 + 几 K 上下文」的调用。如果你的任务本质是检索，RAG 几乎永远更便宜。

## 3. 开源/自建的临界点

什么时候「自托管开源模型」比「调 API」划算？很多人只算了 GPU 裸价，漏了隐性成本：

| 成本项 | API 方案 | 自托管 |
|---|---|---|
| 显性 | 按 token 计费 | GPU 租赁/采购（一次性 + 持续） |
| 隐性 | 无 | 运维人力、SLA 保障、模型升级、冷启动 |

> 经验值：**当你的日调用量大到「API 月账单 ≈ 一张 GPU 月租」时，自托管才开始进入候选区**。在这之前，API 的「免运维、随时换模型」几乎总是更划算。

自托管还压着三件事：运维（谁半夜起来修 OOM）、SLA（你能保证几个 9）、模型迭代（开源模型更新快，你要跟吗）。这三样的隐性成本常被低估，却是决定成败的。

> 结论：自建不是「技术洁癖」，是「规模到了之后的经济账」。规模没到，别自建。

一个务实的判断顺序：

1. 先算出你的月 token 消耗（C21 的成本看板）。
2. 对比「API 月账单」和「一张卡月租 + 你的人力成本」。
3. 只有前者明显更大时，才认真评估自托管。

## 速查表

### 选型四维度

能力 · 价格 · 延迟 · 上下文长度。能力看自己的评测集，其余三个看任务总账（不是单价）。

### 四维度打架

- 能力 vs 价格：差距 10–20%，价格差几十倍。
- 能力 vs 延迟：交互任务延迟优先，离线任务能力优先。
- 上下文 vs 价格/延迟：200K 后跳档，1M prefill 几十秒。

### 分级路由

便宜模型干分类/摘要/路由，贵模型干推理/生成；便宜搞不定自动升级，到顶交人工；路由本身要便宜。

### 长上下文 vs RAG

整体理解 → 长上下文；局部检索 → RAG；两者不互斥。

### 开源临界点

API 月账单 ≈ 一张 GPU 月租时才考虑自建；别忘了运维、SLA、模型迭代三项隐性成本。

## 自测题

1. 「选型」的正确起点是什么？为什么不能直接上旗舰？
2. 为什么 Agent 里看延迟要看「累加」而不是单次？价格同理要看什么？
3. 分级路由里「失败升级」为什么是灵魂？它有个必须设的东西是什么？
4. 一个任务要「从 1000 份文档里找和某条款相关的几段」，该上长上下文还是 RAG？为什么？
5. 有人觉得「我有 GPU 了，自托管肯定比调 API 便宜」，这个判断漏了什么？

## 参考答案要点

1. 起点是「这个子任务需要什么」，不是「哪个模型最强」。旗舰能力只多 10–20%，价格却高几十倍，无脑上旗舰性价比极差。
2. Agent 是 N 次调用累加，单次快不代表整体快；价格同理要看「任务总价 = 输入+输出 token × 单价」，输入 token 会被重复计费。
3. 因为「第一次就派对」很难，升级机制保证派错了能兜住而不是直接失败。必须设上限：最多升一两级，到顶交人工，避免无限加钱重试。
4. RAG。任务本质是「局部检索」，99% 内容无关，塞进 1M 上下文又贵又慢（prefill 几十秒）。RAG 找到片段再塞上下文即可。
5. 漏了隐性成本：运维人力（半夜 OOM 谁修）、SLA（几个 9）、模型迭代（开源更新要不要跟）。自建只在「API 月账单 ≈ GPU 月租」后才划算。
