# C23-3 · 人工确认与人在回路（HITL）
> 阅读约 12 分钟。目标：设计确认的介入点与粒度，让「人在回路」真正拦住风险，而不是流于形式。

## 1. 一句话结论

> 人是最强的兜底，也是最贵的资源。介入点设计错了，不是拦不住，就是把人磨到麻木。

权限（C23-1）和沙箱（C23-2）能拦住「机器层面的乱来」，但拦不住「判断层面的错」——比如「价格算错了还照常下单」。这种错，只有人能拍板。

## 2. 什么操作必须等确认

四类高危操作，对应 C23-1 的权限级：

| 操作 | 为什么必须确认 |
|---|---|
| 花钱 | 真金白银，错了收不回 |
| 删数据 | 不可逆 |
| 对外发消息 | 一旦发出收不回，还影响形象 |
| 不可逆的写 | 覆盖、清空这类改不回来的写 |

> 经验值：确认清单和权限清单是一体的——凡是 `spend`、`destroy` 级别默认要确认，`write` 按影响面决定，`read` 一律放行（只留审计）。

## 3. 确认的粒度：问太多 = 形同虚设

如果每个工具调用都弹确认框，人会变成「一直点同意」的条件反射，确认就彻底失去意义。

> 反直觉事实：确认的价值与频率成反比。问得越频繁，单次确认的分量越轻。

控制频率的三招：

1. **批量确认**：把同类型的多次操作合成一次——「这是我要执行的 N 步，确认吗？」，而不是一步一问。
2. **分级**：只读不问；写默认放行但留审计；花钱 / 删数据必问。
3. **计划先审**：大任务先让模型输出「执行计划」，人审计划，执行阶段不再逐步问。

## 4. 中间过程怎么展示

确认前，人需要看到「它要干嘛、依据是什么」。只给一句「删除数据，是否继续」是不合格的，必须给三样：

1. **具体动作**：`DELETE FROM orders WHERE id=42`，而不是「删除数据」。
2. **依据**：它为什么这么判断（哪条工具返回让它这么做的）。
3. **影响面**：影响多少行、要花多少钱。

这三样靠 C19 的 trace 支撑——**没有 trace，你展示不出「依据」**，确认框就退化成「盲点同意」。

## 5. 中断与改向

人中途改主意时，Agent 要能停、能改：

- **可中断**：确认点就是天然的中断点，支持「取消」「改参数」「换方案」。
- **状态可续**：中断后能从确认点继续，而不是重头跑（靠中间状态落盘）。
- **改向**：人给的修正要能覆盖模型原计划，写回上下文，而不是被模型忽略。

```python
def need_confirm(name: str, args: dict) -> dict:
    return {
        "action": f"{name}({args})",          # 具体动作
        "impact": estimate_impact(name, args), # 影响面
        "reason": last_tool_reason(),          # 依据（来自 trace）
    }
```

## 6. 小结

- 花钱 / 删数据 / 对外发消息 / 不可逆写，四类必确认。
- 问太多会麻木，用批量确认 + 分级 + 计划先审控制频率。
- 确认要展示动作、依据、影响面，靠 trace 支撑。
- 确认点是天然的中断点，支持取消 / 改向 / 续跑。
