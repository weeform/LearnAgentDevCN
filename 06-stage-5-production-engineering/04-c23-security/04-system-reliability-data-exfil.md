# C23-4 · 系统级稳定性与数据外泄
> 阅读约 14 分钟。目标：处理长时任务的超时 / 幂等 / 部分失败补偿，并堵住数据外泄的口子。

## 1. 先划清边界：系统层 vs 单次调用层

大纲 5.4 的「稳定性」分两层，容易混：

- **单次调用层**：一次 LLM / 工具调用的超时、限流、重试、幂等——已在阶段 0 的 C5 完整覆盖。
- **系统层**：一个任务跑 10 分钟、跨十几个工具时，怎么不崩、怎么续、怎么补偿——本篇讲的。

> 一句话区分：C5 管「一次调用别挂」，本篇管「一长串调用组起来还别挂」。别重复造 C5 的轮子。

## 2. 长时任务的超时策略

长任务不能只靠「单次超时」兜底——单次都成功，串起来也可能跑到天荒地老：

1. **总预算**：整个任务设硬上限（时间 + 步数），到顶强制停。
2. **分段检查点**：关键步骤落盘，超时后从检查点续跑，不重头来。
3. **心跳**：长工具调用要有心跳，卡死时主动杀，而不是干等。

## 3. 幂等键设计

有些操作「重复执行两次会出事」——下单、发短信、扣款。网络抖动导致的重试，可能让同一个操作被执行两遍。给每个**有副作用的写操作**配一个幂等键（idempotency key），重试时带同一个 key，服务端去重。

```python
def send_sms(phone: str, text: str, idem_key: str):
    if seen(idem_key):                  # 已处理过，直接返回
        return cached_result(idem_key)
    result = do_send(phone, text)
    store(idem_key, result)
    return result
```

> 经验值：幂等键**只给有副作用的写操作**。纯读和纯计算天然幂等，加了是过度设计。

## 4. 部分失败与补偿事务

一个任务「查了三步、写了两步，第三步失败」——已写的那两步怎么办？

- **能回滚就回滚（补偿事务）**：给每个写操作准备一个逆操作，失败时逆序回滚。
- **不能回滚就记状态**：标记「部分完成」，留人工处理（正好接 C23-3 的确认）。

```python
def compensate(steps_done):
    for step in reversed(steps_done):   # 逆序补偿
        step.undo()
```

> 反直觉事实：多数场景补偿比「强一致事务」便宜得多。Agent 任务天生松散，别硬套数据库事务那套 ACID。

## 5. 数据外泄：工具能读到什么就泄什么

数据外泄的源头往往不是「有人入侵」，而是「工具的数据面太宽」：

> 工具能读到什么，prompt 注入或模型幻觉就可能泄什么。

防线三道：

1. **最小化工具数据面**：只读任务需要的那几列，只给只读账号（呼应 C23-1 的「数据面最小化」）。
2. **外发内容校验**：对外发送（邮件、API、写文件）前，过一遍敏感词 / 格式校验，别让模型把内部数据拼进外发内容。
3. **审计日志**：谁、何时、读了什么、发给了谁，全记下来（复用 C19 的 trace，审计是 trace 的一个用途）。

## 6. 小结

- 系统层稳定性管「一长串调用组起来别挂」，与 C5 的单次调用层分工。
- 长任务：总预算 + 检查点 + 心跳。
- 幂等键只给有副作用的写操作。
- 部分失败用补偿事务，逆序回滚；不能回滚就记状态留人工。
- 防外泄三招：收数据面、校外发内容、留审计日志。
