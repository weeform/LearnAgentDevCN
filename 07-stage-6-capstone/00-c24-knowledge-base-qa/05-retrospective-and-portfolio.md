# C24-5 · 复盘与作品集呈现
> 阅读约 10 分钟，建议在电脑前边读边做。目标：把项目里最值钱的三个取舍讲清楚，并包装成别人一眼能懂的作品集。

## 1. 三个关键取舍

复盘不是「我做了什么」的流水账，而是「为什么这么选、代价是什么」。挑三个：

**取舍一：为什么用混合检索而不是纯向量**

> 纯向量检索在「型号、编号、日期」这类精确值上会漏（C14-3 的经典翻车）。而知识库问答恰恰高频出现精确值——「退款周期几天」「版本号多少」。

选了向量 + BM25 混合，代价是多维护一个关键词索引、多一次 RRF 合并。但这个代价几乎可忽略，换来的是精确匹配这条命脉。**这是本项目的性价比之王，别省。**

**取舍二：为什么切分粒度选 300–800 token 而不是更小**

> 切太碎（100 token）会让「一个完整意思」被劈成几片，引用和召回双双失败；切太大（2000 token）会让检索到的块里混进无关内容，浪费生成成本还稀释注意力。

选 300–800 是「召回够准 + 上下文够全」的平衡点，再用 15% 重叠兜住边界。代价是索引 chunk 变多、检索候选变多——但被 rerank 只过 top 50 化解了。

**取舍三：为什么拒答阈值定 0.3**

> 阈值不是拍脑袋，是拿 10 条「应拒答」题校准出来的。调高 → 误拒率升、该答的也拒了；调低 → 编造率升、该拒的硬答。

最终定 0.3：把「编造」压到接近零，接受误拒率略高。**代价不对称时，优先保护更严重的那一侧**——编造比误拒严重得多。

## 2. 如果重做会改哪里

复盘里最诚实、也最值钱的一段。三条真实反思：

1. **评测集该在写代码前就造好**。我做完系统才憋题，结果题目不自觉偏向了「系统擅长的」，漏掉了不少该测的边界。重做会先按 C24-1 的口径把 50 条固定下来，边开发边回归。
2. **拒答阈值该更早引入**。我先只靠 prompt 拒答，发现模型还是会编，回头才加 rerank 阈值兜底。重做会把「阈值兜底」从一开始就设计进去，而不是当补丁。
3. **切分策略该先小规模试错**。我一开始直接对整个知识库跑切分，等发现「退款 7 天」被劈开时，已经索引完了。重做会先拿一个文档试切，肉眼确认边界贴语义，再全量索引。

## 3. 作品集怎么讲这个故事

面试官/评审看作品集，三样东西按这个顺序摆：

1. **README 第一屏**：一句话说清「这是个能点回原文的知识库问答 Agent」，然后是可溯源率、拒答准确率两个数字，再是「怎么跑」（三行命令）。**数字放最前面，别藏在文末。**
2. **评测截图/表格**：50 条评测集的跑分表 + 3 个失败案例分析。失败案例尤其加分——它证明你不是「只挑好看的贴」。
3. **成本表**：单次问答四环成本拆解 + 优化前后对比。哪怕数字很小，也要有「我算过成本」这个动作。

> 一句话总结这个故事：**「我做了个知识库问答 Agent，每个答案都能点回原文；50 条评测可溯源率 96%、拒答召回 90%；单次问答 0.02 元，缓存后降到 0.008 元。」** 三个数字 + 一句能力描述，就是完整的作品集故事。

## 4. 小结

- 三个取舍都要讲「为什么 + 代价」：混合检索补精确匹配、300–800 token 是平衡点、阈值 0.3 是校准出来的。
- 复盘要诚实：评测集该先造、拒答兜底该早加、切分该先小规模试错。
- 作品集顺序：README（数字在最前）→ 评测截图 + 失败案例 → 成本表。
- 完整故事 = 一句能力描述 + 三个数字。
