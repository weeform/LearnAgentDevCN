# C25-2 · 系统设计
> 阅读约 13 分钟，建议在电脑前边读边做。目标：把「问问题 → 得到结论」拆成一条六段流水线，并说清每一段的职责与失败边界。

## 1. 整体架构：一条流水线，两个闭环

```
自然语言问题
   │
   ▼
[1] 生成阶段：schema + 样例注入 prompt → 模型生成 Python/SQL
   │
   ▼
[2] 沙箱执行：代码/SQL 在受限环境运行
   │                    │
   │ 报错               │ 结果
   ▼                    ▼
[3] 错误回传修正 ◄──┐ [4] 独立数值校验
   │  (重试上限 N)  │        │
   └────────────────┘        ▼
                       [5] 结论生成
                              │
                              ▼
                        最终答案给用户
```

六段职责一句话：

| 段 | 职责 | 失败怎么处理 |
|---|---|---|
| 1 生成 | 把问题变成可执行代码 | 生成不出 → 降级给提示 |
| 2 执行 | 沙箱里跑，限制资源 | 越权/超时 → 拦截 + 回传 |
| 3 修正 | 报错回传，让模型改 | 超上限 → 主动终止 |
| 4 校验 | 独立复算，验证数字 | 不一致 → 视为失败 |
| 5 结论 | 用校验过的数字写结论 | 无数字 → 拒答 |

两个闭环要分清：**修正闭环**（3→1，解决「代码跑不起来」）和**校验闭环**（4 不过就整体失败，解决「代码跑起来了但算错」）。后者是大多数新手漏掉的。

## 2. 生成阶段：把 schema 和样例喂进去，让模型少猜

模型生成代码最大的错误来源是**猜**——猜字段名、猜类型、猜取值。你少让它猜一点，正确率就高一点。

做法：把 schema 和 2-3 行样例数据注入 prompt：

```text
你有权访问一张 SQLite 表 orders，schema 如下：
- order_id: int, 主键
- order_date: date, 格式 YYYY-MM-DD
- region: str, 取值 {华东, 华北, 华南, 西南}，约 1% 为 NULL
- category: str, 取值 {电子, 服饰, 食品, 家居}
- quantity: int, 件数
- unit_price: float, 单价（元）
- revenue: float, 营收（元）= quantity * unit_price
- cost: float, 成本（元）

样例数据（前 3 行）：
(1, '2026-09-03', '华东', '电子', 2, 1299.0, 2598.0, 1900.0)
(2, '2026-09-05', '华南', '服饰', 1, 299.0, 299.0, 180.0)
(3, '2026-09-11', '华东', '食品', 5, 39.9, 199.5, 120.0)

规则：
1. 聚合/分组/过滤/趋势类问题，优先写 SQL（只读 SELECT）。
2. 只有 SQL 表达不了（如复杂统计、需要中间变量）才写 Python。
3. 最终必须输出一个 JSON：{"sql": "...", "python": "...", "answer_value": 数字}
```

> 经验值：schema 注入是**性价比最高的一招**。它几乎零成本（多几百 token），却能把「字段名猜错」「类型搞混」这类低级错误砍掉一大半。这个取舍会在 C25-5 复盘。

## 3. 执行阶段：能 SQL 就不要 Python

这是本项目最重要的一个设计取舍：

> **SQL 天然受限**——`SELECT` 在只读 SQLite 上跑，没有文件系统、没有网络、没有进程，安全性接近免费。Python 沙箱再严，也永远比 SQL 多一层「逃逸」风险面。

所以规则很简单：**问题能用 SQL 表达的，强制走 SQL；只有 SQL 表达不了才进 Python 沙箱**。这不仅更安全，还更可复现（SQL 是确定性的）。

Python 沙箱的隔离方案见 C23-2（沙箱执行），本项目的落地在 C25-3 给出代码。核心是四道闸：**非 root 用户 + 无网络 + 只读挂载数据 + 资源上限（内存/CPU/时间）**。C9-3 里的 `ast` 白名单只是第二道防线（防表达式注入），替代不了真正的沙箱。

## 4. 错误回传自我修正：复用 C11-2，但记一个独立的账

执行失败（语法错、列名错、超时、越权被拦），按 C11-2 的套路：**结构化回传 + 有限次修正**。

```python
return {"success": False,
        "error": "no such column: region_id（SQL 报错原文）",
        "hint": "orders 表没有 region_id，可用列见 schema；请改用 region 后重试"}
```

两点本项目特有的提醒：

1. **修正次数和最大步数分开记**（C11-3 的教训）：修正上限设 2，到了还不行就整体失败，别让模型在错误上反复烧 token。
2. **越权被拦也要回传**：模型尝试 `open('/etc/passwd')` 被沙箱拦下后，要把「越权被拦截」回传，让模型换正路——但记录一次「逃逸尝试」，供零逃逸验证统计。

## 5. 独立数值校验：防「算错还很有信心」

这是本项目的**灵魂环节**。它专门解决验收标准里那件最恶心的事：**代码没报错，但答案错了**。

> 反直觉事实：模型「信心」和「正确」几乎不相关。它算错时会用同样笃定的语气说「答案是 128,430 元」。所以**不能信模型的嘴，要信第二条路复算出来的数字**。

校验怎么做——**用另一条路复算**：

| 生成的是 | 校验用 | 为什么是「另一条路」 |
|---|---|---|
| Python 算的 | 用 SQL 直查复算 | SQL 引擎独立于模型生成的 Python 逻辑 |
| SQL 算的 | 用 golden SQL（评测集）或改写后的 SQL 复算 | 不同写法互相印证 |

校验通过才把数字交给结论生成；不通过，整题判失败，把「两条路算出的不同数字」回传给模型再修一轮（但仍受修正上限约束）。

> 一个朴素的兜底：即使没有 golden SQL，也可以对「聚合类」问题做**量级抽查**——比如营收不能是负数、不能超过 `count(*) × max(unit_price)`。先拦住最离谱的错，再谈精确复算。

## 6. 结论生成：让模型只做它擅长的事

结论段只做一件事：**拿校验过的数字，组织成一句人话**，不要让它重新算。因为「写结论」是模型强项，「算数」是弱项——把两者分开，各干各的。

## 小结

- 六段流水线：生成 → 执行 → 修正 → 校验 → 结论；含两个闭环（修错 vs 校验）。
- 生成段注入 schema + 样例，让模型少猜，性价比最高。
- 能 SQL 就不要 Python：SQL 天然受限、可复现，Python 沙箱只留给 SQL 干不了的。
- 独立数值校验是灵魂：用另一条路复算，不信模型的嘴。
