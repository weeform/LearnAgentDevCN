# C25-5 · 复盘与作品集呈现
> 阅读约 12 分钟，建议在电脑前边读边做。目标：把做这个项目过程中真正重要的取舍沉淀下来，并把它包装成一个能打动面试官/评审的作品集故事。

## 1. 三个关键取舍

### 取舍一：为什么用沙箱，而不是裸执行

> 裸执行的诱惑很大：省一个 Docker 依赖、少一层调用、调试快。但它把「模型代码」当成「自己写的代码」来信任——这是本项目最不该省的一层。

代价是每次执行多几百毫秒启动容器 + 一套挂载配置；收益是**把「模型被诱导出恶意代码」从灾难降级成一条可记录的日志**。C25-4 案例 C 证明这不是杞人忧天：注入数据真实发生了，沙箱拦住了它。这个取舍没有讨论空间。

### 取舍二：为什么加独立数值校验

这是被逼出来的。第一版只有「生成 → 执行 → 结论」，结果「算错还很有信心」的案例批量出现——代码不报错，数字漂漂亮亮，错的却毫无察觉。

> 关键认知转变：**模型的信心和正确率无关**。你唯一能信的是「第二条独立路径复算出来的数字」。所以校验不是可选的 QA 环节，而是正确性的唯一定义——校验不过，就是错。

代价是多一道复算（一题多跑一条 SQL，几乎零成本），收益是正确率从「看着还行」变成「可量化 85%，且知道那 15% 死在哪」。

### 取舍三：schema 注入的价值

给模型喂 schema + 样例，单次 prompt 贵几百 token，换来了「字段名猜错」这类低级错误的消失。

> 这是「用便宜的确定性换掉贵的不确定性」的典型：schema 是确定信息，喂进去后模型不用猜；省下来的是猜错后的一次甚至多次重试。**少让模型猜，永远是 Agent 工程里性价比最高的优化。**

## 2. 如果重做会改哪里

诚实的反思，三条：

1. **评测集应该先于代码写完**。我反过来了——先写实现，再补评测，结果评测集不够刁，前 20 题太「聚合」，漏掉了「异常」类的坑。正确顺序：先定 20 题（含 3 道异常类）→ 用 golden SQL 人工跑出答案 → 再动代码。
2. **「结论合理」的判分一开始就想复杂了**。我第一版全用 LLM-as-judge，发现 judge 自己也会判错方向（C20 讲的 judge 偏差）。重做的话：先用规则（数字一致 + 方向一致）兜底，judge 只做「语义是否自洽」的补充。
3. **沙箱应该更早换成 Docker**。我拖到「先跑通」阶段快结束才上，结果中间有几次用裸 `exec` 调试时，差点被一段坏代码写坏本机文件（幸好只是测试环境）。教训：**哪怕本地调试，涉及模型生成代码也要尽早隔离**。

## 3. 作品集故事线：从「会答数」讲到「敢上线」

作品集不要平铺「我做了个数据分析 Agent」，要讲一个**有冲突、有解法、有数据**的故事：

1. **问题**：让模型用自然语言分析数据，但它「算错还很有信心」，你不敢信它的答案。
2. **冲突**：裸执行有 RCE 风险，加沙箱又复杂；模型算错还不报错，肉眼查不出来。
3. **解法**：六段流水线 + 沙箱（四道闸）+ 独立数值校验（第二条路复算）。
4. **数据**：20 题正确率 85%→90%（优化后），零逃逸 7/7 拦截，单题成本 0.005 元。
5. **取舍**：为什么能 SQL 就不 Python、为什么校验是正确性的定义。

一句话版：**「我让模型自己写代码分析数据，并用沙箱和独立校验，把『它说的对』从一句空话变成了可量化的 90%。」**

配套交付物（阶段 6 出口标准四样）：

- 仓库 + README（怎么跑、依赖、限制）。
- 评测集 + 跑分 + 3 个失败案例。
- 成本表（单题成本、优化前后对比）。
- 本复盘（3 个取舍 + 重做反思）。

## 4. 小结

- 三个取舍：沙箱不可省（模型可被诱导）、独立校验定义正确性（信心 ≠ 正确）、schema 注入是「用确定性换不确定性」。
- 重做三改：评测先行、结论判分先规则后 judge、沙箱尽早隔离。
- 作品集讲「冲突 → 解法 → 数据」，用数字收尾，别用形容词。
