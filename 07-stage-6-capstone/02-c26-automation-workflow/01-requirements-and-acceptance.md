# C26-1 · 需求与验收标准
> 建议在电脑前边读边做。阅读约 12 分钟。目标：把「长时任务」说清楚，并把三项验收变成能一键重跑的测试。

## 1. 什么叫「长时任务」

前两个项目（C24 问答、C25 数据分析）一次任务几秒到几分钟，跑完就完。长时任务的本质不同：**任务的生命周期比一次函数调用、甚至比一次进程的存活时间都长**。

典型形态，三个特征同时出现：

| 特征 | 含义 | 例子 |
|---|---|---|
| 多步 | 不是一个 prompt 一个答案，是 N 个阶段接力 | 拉数据 → 逐批处理 → 写库 → 出报告 |
| 跨小时 | 单次要跑几十分钟到几小时 | 500 条数据，每批 20 条、每批约 1 分钟 |
| 需确认 | 中途有「做错了会出事」的敏感步骤，要人点头 | 批量写生产库、给用户群发通知 |

> 判断标准很朴素：**如果一个任务你不能「开着电脑去睡觉、回来还能接上」，它就不算长时任务，也别硬套这套东西。**

本课贯穿示例：**「批量处理 500 条用户反馈并写入系统」**——拉取、AI 逐条分类/抽取、人工确认、批量写入、出报告。后面五篇都用它。

## 2. 三项验收标准

阶段 6 的出口标准要求「可复现的测试」，而不是「我觉得能续跑」。本项目就压三项验收，缺一不算完成：

1. **断点续跑**：任务跑到一半，`kill -9` 掉进程，重启后从 checkpoint 继续，**已完成的批次不重做**。
2. **超预算自动停**：累计 token 成本超过设定的上限，任务立刻熔断，状态标记为「超预算」，不偷偷往下跑。
3. **敏感步骤等人确认**：走到「写库」这类敏感步骤前，任务**必须**停在「待确认」，不点头绝不执行。

> 把这三条当成合同，不是愿望。写成测试（见第 4 节）的好处是：以后每次改代码，跑一遍就知道「续跑有没有被我改坏」。

## 3. 为什么是这三项，而不是别的

长时任务的失败，90% 不在「模型答得不好」，而在**过程失控**：

- 续跑对应「**时间跨度**」：跑一小时，进程被 OOM 杀掉是常态，不能续跑等于白跑。
- 熔断对应「**成本跨度**」：长任务的 token 会滚雪球（每轮历史越堆越长），没有上限可能一夜烧掉几十块。
- 等确认对应「**副作用跨度**」：短任务的副作用小，长任务一旦中间写错了库，恢复成本极高，所以敏感步骤必须设卡。

三项分别压住时间、成本、副作用三个失控点，互相独立。

## 4. 把验收做成可复现的测试

验收不能靠「演示一遍给你看」。每个验收写成一个脚本，能一键重跑：

```python
# test_acceptance.py —— 三项验收，跑通才算交付
def test_kill_and_resume():
    run_until("process_batch_3")      # 跑到第 3 批
    os.system("kill -9 %d" % pid)     # 模拟进程被杀
    resume()                          # 重启恢复
    assert state["steps_done"] == ["fetch"]              # 已完成的没重做
    assert state["progress"]["batches_done"] == ["b1", "b2"]  # 从 b3 继续

def test_budget_breaker():
    run(cap_usd=0.01)                 # 给一个必然超的上限
    assert state["status"] == "failed_over_budget"       # 熔断，不是 running
    assert apply_never_called()       # 且没偷偷执行后续

def test_human_gate():
    run_until("apply")                # 跑到写库前
    assert state["status"] == "awaiting_approval"        # 停在待确认
    assert db_writes() == 0                              # 没写
    resume(approved=True)             # 人点头
    assert db_writes() > 0                               # 才写
```

> 测试的关键不是「能跑」，是**可断言**：每项验收都落到一个具体的、机器能判断的状态字段或副作用计数上。状态字段的定义见 C26-2，实现见 C26-3。

## 5. 需求边界：哪些不算本课范围

- 不做高并发：单任务单进程跑，够用。
- 不做分布式协调：状态放本地文件/SQLite，不上 Redis/ZooKeeper（那是生产规模化的事）。
- 模型调用仍走阶段 0–2 学的那套，不引入新框架。

> 刻意收窄边界，才能把力气花在「状态与恢复」这个难点上，而不是被基础设施淹没。

## 小结

- 长时任务 = 多步 + 跨小时 + 需确认，生命周期长过进程存活时间。
- 三项验收：断点续跑、超预算熔断、敏感步骤等确认——分别压住时间、成本、副作用三个失控点。
- 验收要写成可复现的测试，每条落一个可断言的状态字段或副作用计数。
