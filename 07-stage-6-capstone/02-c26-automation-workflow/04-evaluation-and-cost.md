## 1. 怎么测断点续跑：不是「重启一下」，是「注入故障」

续跑最容易测假——重启一次看着续上了，但可能只是运气好，正好挂在两个 checkpoint 之间。真正的测法：**在多个位置注入 kill，确认每个位置都能安全恢复**。

```python
# 在 step_process 的第 b 批之后，按注入标记杀掉进程
KILL_AFTER_BATCH = 3

def step_process(s):
    ...
    for b in range(len(done), batch_count):
        process_batch(b)
        save_state(s)
        if b == KILL_AFTER_BATCH:        # 注入故障：模拟进程被杀
            os.kill(os.getpid(), 9)
```

重启后断言三件事：

1. `batches_done` 停在 `batch_3`（含），`batch_4` 还没做——**没有多跑**。
2. `batch_0..3` 的幂等键都是 `done`，重启后**没有重复写**。
3. 最终 `status == done`，且数据总条数正确——**没有漏**。

> 只测一次不够。至少测三个位置：第一步之后、中间某批、副作用步骤 intent 之后 done 之前。最后一个位置最险——它专门暴露「执行成功但没来得及打点」的窗口（见 C15-2 第 3 节）。

## 2. 怎么验证成本熔断

给一个必然超的预算上限，断言它「停在该停的地方」：

```python
run(cap_usd=0.02)                        # 只够跑 5 批
assert state["status"] == "failed_over_budget"
assert len(state["progress"]["batches_done"]) == 5   # 第 6 批没跑
assert state["budget"]["spent_usd"] <= 0.02 + 0.004  # 花的不超上限+单跳
```

两个要点：

1. **熔断发生在「花钱前」**，所以 `spent_usd` 最多超上限一个单跳的粒度，不会失控。
2. 熔断是终态，重启后 `main()` 直接 `return`，**不会偷偷继续**——这也是一条要专门测的断言。

## 3. 三个失败案例分析

### 失败案例一：方向错了，靠 dry-run 挡在写库前

用户本意是「抽取反馈里的**情感倾向**」，模型理解成了「抽取**主题分类**」。跑到 apply 前的 dry-run 校验，抽 20 条抽查发现字段对不上，`reject` → `rolled_back`，中间产物全清。**损失：一次 process 的成本，零脏数据。**

> 教训：把「方向校验」放在副作用之前，是回滚成本最低的时机（见 C26-2 第 6 节）。

### 失败案例二：模型中途退化，靠「幂等键 + 精确删」回滚半程

处理到第 200 条，模型开始胡编分类（温度漂移 + 长上下文干扰）。apply 已写入前 150 条，抽查发现第 180 条起全错。回滚脚本按 `batch_id → row 主键` 映射精确删掉第 150 条之后的数据，保留正确的 150 条，调参后从 `batch_8` 续跑。**损失：半程重跑，不是全程重跑。**

> 教训：写的时候记录「谁写的」，回滚才能只删错的那部分——这就是 C26-2 第 4 节说的「写的时候就想好怎么删」。

### 失败案例三：成本估算偏低，熔断救了钱包

单价估少了，实际每批 0.008 而非 0.004，跑到一半 `spend` 累计触发熔断。因为熔断发生在花钱前，任务停在 `failed_over_budget` 而不是烧完整个预算。**损失：0.02 美元而不是预估的 0.06 美元，差了三倍。**

> 教训：熔断的粒度（单跳估算）决定它能不能真的省钱——粗到「任务级」就救不回来了。

## 4. 成本数据：长任务的 token 分布

示例量级（你的任务用自己 trace 的真实数替换，见 C19-2 的字段设计）：

| 阶段 | 占总 token | 说明 |
|---|---|---|
| fetch | ~2% | 拉数据几乎不耗模型 |
| process（逐批） | ~88% | **大头**：每批都要把历史/工具定义重发 |
| apply / report | ~10% | 写库校验 + 出报告 |

> 长任务的成本集中在 process 阶段，且**越到后面单批越贵**——因为上下文越堆越长。这是「预算熔断」和「上下文裁剪（见 C7-1）」必须同时上的原因。

两份附加数据：

- **checkpoint 开销**：每批写一次 state.json（几百字节）+ 幂等键，全程 25 次写，合计 < 0.1 秒，可忽略。
- **熔断省下的钱**：上述案例三里，失控任务原本会烧 0.06 美元，熔断后停在 0.02，**省了三分之二**。

## 小结

- 测续跑要用「故障注入」在多个位置 kill，且至少测「intent 之后 done 之前」这个最险位置。
- 熔断要断言「花钱前停 + 终态不再跑」；它的粒度决定省不省钱。
- 三个失败案例分别对应：dry-run 挡方向错、幂等键精确删半程、熔断挡成本失控。
- 长任务成本集中在 process 阶段，越往后单批越贵——熔断与上下文裁剪要一起上。
