# C26-5 · 复盘与作品集呈现
> 建议在电脑前边读边做。阅读约 10 分钟。目标：把项目沉淀成三个取舍、一份「如果重做」清单，和一段能讲给面试官听的故事线。

## 1. 三个关键取舍

### 取舍一：状态外置，而不是放上下文/内存

> 放内存，进程一挂全丢；放上下文，每轮重复付费还无法审计。**只有放外部存储，才谈得上续跑、审计、人工干预。**

这是整个项目的地基（见 C15-1 第 3 节）。代价是每次状态变更要落盘、代码里处处「读状态 → 干 → 写状态」。但换来的「进程无状态」让 kill -9 从灾难变成常态操作。

### 取舍二：确认点只设一个，而不是每步都确认

确认太频繁，长任务就变成「人肉陪跑」，几小时的任务人要守几小时。**用「这一步做错了，恢复成本高不高」做唯一判据**，本项目只卡「写库」一步。

> 反直觉的点：确认点越少，人越愿意认真看。设十个确认点，人反而会麻木地全点「同意」。

### 取舍三：幂等键用「写前 intent + 写后 done」两点

只在「写后」打一个点，会留下「执行成功但没来得及打点」的崩溃窗口，恢复时要么重复写、要么漏写。**两点打点（见 C15-2 第 3 节）用一次额外的写操作，换掉整个「结果未知」的灰色地带。**

## 2. 如果重做会改哪里

1. **一开始就用 SQLite 而不是 JSON 文件**。JSON 撑到「要查某批到底 done 没」就吃力了，而幂等键和状态本质上就是张表。早换能省掉一次迁移。

2. **dry-run 校验做得更早、更狠**。现在只在 apply 前抽查 20 条；应该每批都做轻量校验，把「方向错」「模型退化」挡在更早的位置，而不是攒到最后一起爆。

3. **预算熔断从「任务级」细化到「步骤级」**。现在只有一个总上限，实际应该给 process 单独设上限、给 apply 单独设上限——这样熔断时能精确说出「钱烧在哪个阶段」，而不是一个模糊的总数。

4. **把状态字段加版本号**。`state` 的 schema 会变（加字段、改名字），没有 `schema_version` 字段，老 checkpoint 恢复时要么崩要么静默错。这是吃过的暗亏。

## 3. 作品集故事线

讲这个项目，按「痛点 → 方案 → 证据」三段：

- **痛点**：一次任务跑两小时，进程被 OOM 杀、成本失控、写到一半发现方向错了——三件事都只能从头再来。
- **方案**：状态外置 + 状态机 + checkpoint；幂等键与补偿兜「部分失败」；成本熔断兜「烧钱」；人工确认兜「不可逆副作用」。
- **证据**：三个注入位置的续跑测试全绿、熔断测试停在花钱前、三个失败案例各讲一个被兜住的坑、一份 token 分布和熔断省下的钱。

> 作品集里最能打动人心的不是「我用了状态机」，而是「**我 kill 掉进程 5 次，它每次都从该停的地方继续，没多写一条、没漏一条**」——把验收当故事讲。

## 4. 阶段 6 收尾：三个项目各压了什么难点

三个项目是刻意选的，各压一个难点：

| 项目 | 难点 | 一句话总结 |
|---|---|---|
| C24 知识库问答 | 检索质量决定一切 | 答案点回原文，检索错了后面全错 |
| C25 数据分析 | 让模型写代码并安全执行 | 模型算错但很自信，必须独立校验 |
| C26 自动化工作流 | 长时任务的状态与恢复 | 进程可以死，状态不能死 |

> 把它们放在一起看，就是「一个 Agent 工程师的三块肌肉」：**检索、执行安全、状态管理**。面试里被问到「你做过最完整的 Agent 项目」，直接讲这个组合，比单讲一个项目立体得多。

## 小结

- 三个取舍：状态外置（地基）、确认点只设一个（判据是恢复成本）、幂等键两点打点（消灭结果未知）。
- 如果重做：早用 SQLite、校验更早更狠、熔断分级、状态加版本号。
- 作品集按「痛点 → 方案 → 证据」讲，把验收测试当故事。
- 阶段 6 三个项目 = 检索、执行安全、状态管理三块肌肉，合起来是完整的 Agent 工程能力。
